# Encryption and trust boundaries

Part of [proposal 5](README.md). These are adopted target requirements with explicit wire-vector/security-review release gates, not claims that the existing NV encryption format supplies them.

## Threat model

Terminology: **encryption recovery key** below means secret unlocking material, not the protocol's deterministic **conflict recovery key**. **Envelope scope** means provider-shareable versus local-store-bound encoding, not an Undo or conflict-disposition scope. See the [glossary](../../CONTEXT.md#2-history-records-and-stored-objects) and [protocol reading guide](Protocol.md#reading-the-terminology); field names in the wire format remain unchanged.

An untrusted provider may read every uploaded byte and filename, change or truncate objects, duplicate/reorder/replay them, omit arbitrary objects, and show different histories to different Macs. The encrypted profile must conceal note bodies, titles, labels, dates, logical note/revision identifiers, and private settings, and reject fabricated operations before they reach a decoder or live store. A party holding the collection key is an authorized writer; v1 provides no per-device signature, device revocation, or protection from a malicious authorized NV client.

The provider still sees opaque collection/key/writer IDs, envelope kinds, sequences, lengths, object count, and timing. No padding or traffic-analysis resistance is claimed initially. It can deny service or conceal the newest valid history. A known local frontier detects missing previously accepted evidence; it cannot distinguish deliberate withholding from ordinary synchronization delay, or prove that a fresh Mac has seen the newest history. These limits remain true after successful authentication.

The public plaintext profile has no provider-confidentiality or malicious-provider authenticity guarantee. Its content hashes detect accidental corruption and identify exact objects; a provider can recompute them. Never silently accept that suite in an encrypted collection, even when the claimed collection ID matches.

## Primitive and implementation choices

- AES-256-GCM with a full 16-byte tag for all encrypted envelopes. Use CryptoKit's authenticated `seal`/`open`, including associated data, rather than composing CBC and a checksum. Nonces are generated by CryptoKit and stored with their ciphertext, as required for decryption. [Apple AES-GCM](https://developer.apple.com/documentation/cryptokit/aes/gcm)
- HKDF-SHA-256 for domain-separated subkeys from a random collection key. HKDF is not a password-stretching function. [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869.html)
- Argon2id version `0x13` for the passphrase-derived wrapping key. Proposed initial profile: 65,536 KiB, three passes, four lanes, 16 random salt bytes, 32 output bytes. These match RFC 9106's lower-memory recommended profile; benchmark both supported architectures without silently weakening the stored profile. [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html#section-4)
- Pin and vendor the required library sources from the [Argon2 reference implementation](https://github.com/P-H-C/phc-winner-argon2), record their revision/license, and build the portable implementation for Intel and Apple Silicon. Run upstream known-answer tests. CryptoKit does not supply this KDF; adding it is a deliberate security dependency, not a proposed new cryptographic implementation.

NV remains Objective-C with manual reference counting at the application boundary. The [portable Swift library plan](plan/swift-storage-implementation-plan.md) owns value encoding and crypto composition, using Swift Crypto's compatible primitives across platforms and a narrow Apple bridge for immutable input/output and native credentials. Keep random generation, key derivation, AEAD and secret-buffer ownership inside that reviewed boundary. Do not convert the application to ARC or move its interaction code into the library. The eventual app bridge/linker needs explicit Swift runtime/link support, with deployment remaining macOS 11; the primitive package is not yet linked into NV.

Do not add PBKDF2 as an automatically selected fallback. An unsupported or failed Argon2 profile is a failed unlock/creation attempt, not permission to create a weaker collection. Existing PBKDF2/CBC readers remain on the explicitly selected legacy migration path.

## Collection keys and key separation

Generate a random 32-byte collection key `CK`, a random 16-byte `collectionID`, and a random 16-byte `keyID` when creating an encrypted collection. They are independent of the passphrase and provider. v1 has one active collection key; `keyID` is an equality identifier, not an ordered epoch number.

For each encrypted object, derive:

```text
Kobject = HKDF-SHA256(
    IKM  = CK,
    salt = collectionID || keyID,
    info = ASCII("NV object key\0v1\0") || kind || writerEpoch || scopeID,
    L    = 32
)
```

`kind` is one byte. `scopeID` is zero for provider objects and the local store UUID for host-private objects. All UUIDs use their 16 raw bytes, not text. Define separate kind values for changes and provider snapshot roots/pages. Private database rows do not use provider envelopes. Never reuse a provider-object key/nonce pair to encrypt local preferences or vice versa.

A fresh writer epoch is created on every editable process session. Restarts, restored backups, and copied local stores never resume allocation from an old epoch. Previously sealed envelopes retain their old epoch and are retransmitted unchanged. A process approaching `2^20` newly encrypted objects in one epoch starts a fresh epoch before further sealing, independently of any provider operation. This is a local namespace/key-usage boundary; it does not rotate the collection key or checkpoint the notes.

CryptoKit generates a fresh 12-byte random nonce for every seal. Sequence numbers and writer paths do not replace nonce generation. Failed, canceled, or ambiguous sealing/install attempts must never be retried by encrypting different plaintext with an earlier nonce. A publication retry always uses the already sealed envelope. Fixed-nonce reader fixtures are assembled independently; writer tests use fresh production nonces and independent cryptographic checks. Production has no caller-supplied nonce API, including a module-internal fixture overload.

## Common object envelope version 1

All numeric NV envelope-header fields in the following table are unsigned big-endian. The enclosed zstd frame follows Zstandard's own byte order and framing. Do not serialize a native C structure, rely on its padding, or allow arbitrary dictionaries to choose field order.

| Field | Bytes | Meaning |
| --- | --- | --- |
| magic | 8 | ASCII `NVSEG1\r\n` |
| version | 2 | `1` |
| kind | 1 | Changes `1`, provider snapshot root `2`, provider snapshot page `3`; `4`/`5` remain reserved private-only tags, not emitted for SQLite current/state rows |
| suite | 1 | Public/hash-only `0`, AES-256-GCM `1` |
| headerLength | 4 | `124` for v1; reject other values |
| collectionID | 16 | Random collection identity |
| keyID | 16 | Random key identifier; all-zero only for the public suite |
| writerEpoch | 16 | Random origin epoch |
| sequence | 8 | Diagnostic/local allocation order, never delivery coverage |
| scopeID | 16 | Zero for provider objects; local store UUID for kinds `4`/`5` |
| compression | 1 | None `0`, independent Zstandard frame `1` (`ObjectCompressionV1`) |
| reserved | 7 | Zero |
| encodedLength | 8 | Payload bytes after optional compression, before encryption |
| plainLength | 8 | Bytes before compression |
| nonce | 12 | GCM nonce; all-zero in public suite |

The exact 124 header bytes, prefixed by ASCII `NV object envelope\0v1\0`, are AEAD associated data. The encrypted suite appends `encodedLength` ciphertext bytes and a 16-byte tag. The public suite appends `encodedLength` clear bytes and a 32-byte SHA-256 of the domain separator, header, and clear payload. A public hash is not a MAC.

`segmentID = SHA256(exact complete envelope bytes)`. Physical filenames contain this ciphertext-envelope hash, never a plaintext body hash or encrypted note title. A locator is `{writerEpoch, sequence, segmentID}`; the receiver derives its leaf from these validated binary values rather than following a path supplied inside data. In the local object store, the hash alone distinguishes same-epoch/sequence forks.

The wire ceiling is 64 MiB decoded payload and 64 MiB + 64 KiB encoded payload per object; the normal change-batch target is much smaller. The complete envelope additionally includes its 124-byte header and 16-byte encrypted or 32-byte public trailer: at most 67,174,556 bytes. Check integer overflow, exact total file length, kind, suite, scope, and all limits before allocating or decrypting. In encrypted mode authenticate before decompressing, interpreting payload counts, decoding RTF, or invoking any archive reader. Enforce the advertised output bound while decompressing; a successful AEAD tag does not make a decompression bomb safe. Optional compression is one stream per envelope, never a shared stream spanning segments. [Concrete limits and worker budgets](plan/remaining-storage-validation.md#resource-limits-and-scheduling) distinguish these validity ceilings from resumable scheduling bounds.

Ciphertext headers expose only the listed metadata. Revision/action IDs, action origins/scopes, scope-parent and operation causal parents, undo/redo/restoration references, merge descriptors, operation payloads, snapshot manifests, file projection claims, body hashes, labels, and dates belong inside the payload. Human-readable origin labels are optional encrypted data, never public writer-directory names. Provider objects reject host-local kinds or nonzero scope IDs. A copying attack between different collections, key IDs, kinds, or local scopes therefore cannot turn a valid envelope into applicable evidence.

### Compression profile

All new NV storage compression uses Zstandard (zstd). Uncompressed encoding
remains permitted. Zlib belongs only to the legacy epoch-4 database/WAL
compatibility path; new envelopes never negotiate or fall back to zlib.
Version 1 is unreleased: compression tag `1` now directly names zstd, with no
decoder for the discarded development zlib format.

A compressed provider payload is exactly one standard zstd frame with magic
`28 B5 2F FD`, an explicitly stored frame-content size equal to `plainLength`,
and a window no larger than 64 MiB. Single-segment frames use their content size
as the window bound. Dictionary-ID fields, reserved/unused frame-header bits,
unknown content sizes, magicless/legacy/skippable frames, concatenated frames and
trailing bytes are rejected. Decoding has no external dictionary; both absent
and valid present content checksums are accepted. A present checksum must verify.
Authenticate the complete envelope before inspecting or decompressing its frame.
Allocate output from the checked outer length, enforce that capacity during
decoding, and require exactly the claimed output and all frame bytes consumed.
These restrictions supplement the
[Zstandard frame format](https://github.com/facebook/zstd/blob/v1.5.7/doc/zstd_compression_format.md)
and [decoder contracts](https://github.com/facebook/zstd/blob/v1.5.7/lib/zstd.h).

The current writer uses pinned zstd 1.5.7 at level 3, with a stored content size
and no dictionary. The compression level and exact encoder choices are not
logical identity inputs or reader restrictions. Semantic operation IDs remain
unchanged across valid encodings; segment IDs hash the exact sealed bytes, which
are retained for retries. Keep both existing encoded/decoded size ceilings.
An output that cannot fit the encoded ceiling fails admission without truncation.

Private current rows use the same zstd implementation with their separately
versioned local dictionary/codec metadata. That selected dictionary optimization
does not add dictionary dependencies to provider envelopes. SQLCipher encrypts
database pages; it does not supply note compression. The Phase 2 raw-current-row
baseline remains uncompressed until that physical codec is qualified.

## Bootstrap and wrapped-key descriptor

An encrypted collection's bootstrap descriptor is immutable. Its bounded canonical header contains a distinct magic/version, encrypted profile identifier, collection/key IDs, required codec version, the genesis segment locator, KDF identifier/version/profile, random salt, wrap nonce, and fixed wrapped-key payload length. Do not put a passphrase verifier, note-derived hint, computer name, root bookmark, or Keychain persistent reference in it.

Creation order avoids a hash cycle:

1. Generate `CK`, identities, and writer epoch locally.
2. Seal the genesis operation segment under `CK`. It contains the immutable collection profile and initial note births; a large initial collection uses dependency-linked genesis/import batches and a snapshot as described in [Protocol](Protocol.md).
3. Derive a 32-byte wrapping key with Argon2id from the user's passphrase and new salt. Passphrase encoding is NFC-normalized UTF-8 with no trimming or case folding, a length limit of 1,024 bytes, and explicit length-delimited input. Confirm the same encoding on every platform.
4. AES-GCM encrypt the 32-byte `CK`; the complete canonical descriptor header, including its genesis locator, is associated data under a separate `NV key wrap\0v1\0` domain. Retain the nonce and 16-byte tag.
5. Name the descriptor with SHA-256 of its exact bytes. Persist/read back it and the genesis locally before publishing either. Each may arrive at another Mac first; neither alone grants editable-bootstrap authority.

The descriptor decoder is separate from the object decoder because the collection key is unavailable until it is opened. Freeze byte offsets and vectors during implementation phase 1; the above field order and primitive choices are required. Descriptor files are at most 16 KiB. Only the specified v1 KDF profile is accepted initially, so a malicious header cannot request arbitrarily many GiB or iterations. Run at most one password KDF at a time. Do not try thousands of candidate descriptors automatically.

The public profile's descriptor explicitly uses no wrapped key and pins its genesis/profile in hash-checked clear data. Once a local association pins an encrypted profile and bootstrap, seeing a public descriptor is an error/foreign collection, not a downgrade path. Concurrent creation of unrelated collection bootstraps in one selected folder is not a merge: present collection selection or require another destination, preserving both.

A new Mac downloads the descriptor, prompts for a passphrase, unwraps `CK`, authenticates the pinned genesis, and loads a complete snapshot/closure. Wrong secret, authentication failure, unavailable key material, unknown required codec, and an incomplete history have separate internal outcomes; none initializes an empty collection. A user-supplied random recovery key can provide `CK` directly, but it must still authenticate and pin the collection bootstrap. Display/save that secret only through an explicit user action.

## Local secret and plaintext handling

For encrypted collections, offer **Remember on this Mac**. This skips repeated password entry; it does not make the collection password-free. Store the collection key in a narrowly scoped generic-password item through `SecItem` with `kSecUseDataProtectionKeychain = YES`, an explicit accessibility class, synchronization disabled, and the app's supported access group. Use `WhenUnlockedThisDeviceOnly` for the initial UI-driven policy. Test the actual signed application on Intel and Apple Silicon; signing/access-group failure disables remembering and leaves passphrase unlocking available. The data-protection and legacy macOS Keychains are different implementations. [Apple TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)

Provision a fresh item add-only, read it back, and compare/validate its key before installing a local association that references it. Identifier collision burns that candidate. Queries specify complete service/account/group identity. A locked or unavailable Keychain item is not corrupt and is never deleted as an error response. Keep old legacy Keychain queries on their legacy path; moving them to a new backend blindly would make existing items appear lost.

The private [SQLite store](LocalStore.md#database-keys-and-password-free-recovery) uses SQLCipher database/journal pages for both profiles, including current values, indexes, pending buffers, settings and receipts. Password-free stores use a documented nonsecret key: this is format uniformity and accidental-corruption detection, **not confidentiality or malicious-tampering protection**. They require neither Keychain nor a separate secret/key file for recovery. Encrypted stores derive their database key from the existing collection key; remembering that key is optional. Current/Local State rows do not use an additional nested provider envelope. Exact sealed provider objects remain unchanged BLOBs. Portable origins, scope parents and compensation relationships remain provider-history payload. The qualified SQLCipher build and production unlock/backup implementation remain release gates. Current-cell format/version is independent of provider/epoch-4 formats; required settings and credentials have their own owners. No plaintext encrypted-profile serialization or temp spill is allowed; encode/compress/seal provider objects in worker memory before writing them. [Qualification findings](plan/sqlcipher-validation.md) distinguish page authentication, password handling and provider keys.

The visible provider directory is `NV Data`, not a hidden directory. Visibility does not weaken payload encryption: names below it remain opaque and no plaintext explanatory file may contain collection titles, secrets or note metadata. A full repository copy preserves available exact envelopes/descriptors and associated text files without requiring Application Support, unpublished work or other Macs. It retains the collection/key/history identities; it does not decrypt/reseal into a new genesis. Validate actual copied bytes and report unavailable objects/dependencies without claiming global freshness. Backup help identifies wrapped-key descriptors plus a passphrase/recovery key as recovery requirements; derived current rows and a device-bound Keychain item are not portable substitutes. Plaintext projection stamps are not written by EncryptedSegmentsV1.

Plaintext is present in NV's unlocked live store and transient encoding buffers, as it is today. Bound lifetimes, avoid `NSString` conversions of key bytes, zero owned mutable secret buffers where practical, and do not claim complete zeroization of all Foundation/Swift copies or swap/crash dumps. The feature does not protect an already compromised unlocked Mac.

Do not index encrypted note contents or titles through Spotlight exports. Audit existing caches, preview/Quick Look material, restore state, diagnostics, temporary filenames, and external-edit paths. Explicit plaintext exports and external-editor sessions require the existing disclosure extended to explain that the other app may retain autosaves/backups. Put any deliberate scratch plaintext outside the provider folder with restrictive permissions; retain the scratch file until its accepted edit is durably segmented, then use the existing owned cleanup. Do not promise secure deletion of APFS/provider snapshots or other apps' copies.

Apply the same rule to history and Recently Deleted, including detached previews, diff buffers, undo entries and indexes. Locking releases view-held decrypted history and disables recovery; background completion cannot redisplay it after lock. Deleting current text or a note retains its old encrypted payloads in v1; this is recovery, not erasure. Do not offer permanent deletion or imply that changing the passphrase removes readable history from any holder of the old key.

## Passphrase changes, key changes, and recovery

A same-profile repository copy is not a key rotation: exact encrypted history and usable descriptors remain intact. The current-state-only key/profile conversion below is a separately disclosed operation, never an implementation shortcut for full repository Save As.

Changing a passphrase and changing the collection key are different operations. A rewrap of the same `CK` creates a new immutable descriptor referencing the same genesis. It can add a new unlocking secret without rewriting segments. Old descriptors may still unlock the same history with an old passphrase; the provider can retain them indefinitely. Present that consequence and do not label rewrapping as revocation. Accepted same-key descriptors form a set, not a last-writer-wins pointer. A returning Mac keeps its pinned key/profile; a different key under the same key ID is rejected.

The initial **Change Encryption Key** or encryption-profile transition uses a fresh destination, collection ID, key, genesis, and complete current-state export. The source remains available until destination verification. Do not implement automatic in-place key-epoch succession, old-device exclusion, or remote credential deletion in v1. Reserving a `keyID` field makes later formats possible but is not a rotation protocol. Unknown key IDs park their objects and expose unlock/unsupported status, never silently discard them.

Migrating from an already plaintext provider folder does not conceal plaintext copies that provider previously observed. Deleting old descriptors or ciphertext does not prove their remote erasure. Losing every usable passphrase/recovery key and every remembered collection key makes encrypted data unrecoverable. The creation UI must make secret recovery a concrete user choice without sending secrets through the provider in cleartext.

## Integrity, replay, and availability

Hash/AEAD verification establishes exact authenticated bytes; causal validation establishes applicability. Never infer newest history from a timestamp, maximum sequence, lexicographically greatest hash, or successful authentication. A duplicate valid object is a set insertion with no new mutation. Conflicting bytes under an existing immutable locator are retained as an integrity/namespace problem and never overwrite the verified local copy.

Keep every accepted local segment in v1. If the provider omits one previously observed, NV retains its local state and can attempt exact republishing once rooted authority remains valid. It reports incomplete synchronization, not a confirmed attack or logical deletion. Fresh devices can accept a complete disclosed branch and later join additional branches, but cannot prove the provider has disclosed all heads. A snapshot with a valid tag is likewise a snapshot of its stated frontier, not proof of freshness.

Before release, pin byte-level vectors for AEAD/header binding, HKDF domains, passphrase normalization/KDF, descriptors, compressed/uncompressed envelopes, tampering, truncation, unsupported suites, and wrong-collection replay. Have a cryptographic review examine the complete envelope/bootstrap protocol; use of standard primitives does not itself review their composition. Detailed implementation and failure tests are in [Verification](Verification.md).
