# Storage protocol: critical obligations and whole-set audit

This audit covers the active proposal-5 model set, including shared components, not just recently edited files. [The specification](../iCloud-Drive-Support-Spec.md), [Protocol](../impl-proposal-5/Protocol.md), [CONTEXT](../../CONTEXT.md) and the ADRs define the required behavior. [Coverage](Proposal5-Coverage.md) identifies model boundaries. Retired proposal-4 models are not evidence for this protocol.

## Most critical properties

An action need not remain the visible Current forever: a later intentional edit, Delete or compensation can supersede its effect. What must remain is its exact durable history, truthful causal/action provenance, and the correct current/conflict/deletion outcome. Delivery order must not invent a different user action or silently discard an independent one.

| Priority | Required property | Compound scenario that must exercise it | Principal requirements |
| --- | --- | --- | --- |
| 1 | **Durable means recoverable, with all dependencies and action metadata.** Every acknowledged operation survives ordinary restart with its complete parent/action closure; an installed operation does not depend on a delivered callback. | A creates/edits, then issues a dependent Delete/Restore before earlier callbacks; B receives descendants before ancestors; either or both crash between installation, retained-pin update, application and receipt. No descendant is applied without its transitive ancestry. | DUR-01, START-01, HIST-01 |
| 2 | **Equal complete history yields equal logical meaning.** After finite input and eventual successful exchange/application, computers agree on live births, represented revisions, conflicts, Deletes and action eligibility independently of arrival order or duplicates. | Concurrent edits, multiple covering Deletes, explicit copies and compensations arrive in opposite orders, with stale cache/restart and later descendants. Exact effect/causal provenance, not merely note count, must agree. | HIST-01, DELETE-01, PUB-01 |
| 3 | **Deletion respects intent, concurrency and birth boundaries.** Unexplained file absence is not a remote NV command; an applicable Delete removes its birth while preserving unobserved concurrent edits. Restore has a fresh birth. | One Mac deletes while another edits offline; a later Delete covers the first edit but not its extension; a restored note and a same-named replacement file exist before the old removal callback runs. Neither restoration nor unrelated bytes are erased. | DELETE-01, IMPORT-01, REC-01 |
| 4 | **Every authored action keeps its exact scope and value.** Note operations, before/after references and action metadata describe the same captured mutation; ordinary edits do not consume unrelated conflict heads. Undo/Redo targets actual compensations, not receipt order. | Two Macs undo the same candidate, each authors further work, one restarts, and the user reviews a compensation after remote changes. Complete groups recover together; siblings and unrelated fields survive; no-op compensation is not a completed action. | HIST-01, PUB-01, DUR-01 |
| 5 | **External-file races never become overwrite/removal permission.** A committed note update and a historical receipt are not proof of what occupies a filename now. | Remote segment arrives while an external editor safely replaces/renames the file and local NV has B→C pending; crash between destination install, source accounting and receipt. Preserve external bytes; advance only the actually settled projection; never clear C with B's completion. | DISC-01, AUTH-01, PUB-01, DELETE-01 |
| 6 | **Admission/retry identity is exact, without replaying consent.** One admitted observation is not repeatedly imported after receipt loss, even if its note is later edited/deleted. A changed preparation needs a new operation identity, not necessarily a new unused birth. | Preview changes during reservation; crash before/after operation durability and twice before receipt; deletion arrives during association review/completion; another file competes for the note. No repeated birth, mutation under an old operation ID, silent re-approval or attachment to a deleted birth. | IMPORT-01, REC-01, HIST-01 |
| 7 | **Private metadata and cleanup cannot lose the only retained input.** Payload/reference/receipt/pin ordering protects both possible complete metadata generations after an uncertain replacement. | New preview becomes durable while an older admitted input remains frozen; Local State replacement or cleanup fails; restart returns old or new metadata. Retained bytes and operation/settlement links remain usable; missing/unreadable source is not abandonment. | DUR-01, CLEAN-01, IMPORT-01, CKPT-01 |
| 8 | **Authority is checked at every actual effect.** Root, store, lifecycle, note, relationship and file generations cannot be transplanted by a delayed callback, pathname reuse or serialized receipt. | Repair/copy/save begins on a valid root, which is replaced while work runs; a same-ID repository or new private store appears at the same path. Stop stale effects while preserving healthy local editing and already retained bytes. | AUTH-01, ROOT-01, PUB-01, REPAIR-01 |
| 9 | **Recovery and repair never manufacture completeness.** Cache loss, missing dependencies, partial copies, unsupported input or inaccessible metadata cannot become editable emptiness or a fabricated successful repair. | Fresh/returning Mac sees a partial snapshot plus later objects, loses private state, or has complementary damaged copies. Repair from exact validated available bytes; activate only with required closure/pin/ownership; preserve displaced evidence. | START-01, CKPT-01, REPAIR-01, BACKUP-01 |
| 10 | **Disposition records only what was actually preserved/selected.** NV conflict-copy attention is separate from source Current; Apple member resolution needs exact durable note/file evidence and only its captured applicable scope. | Reciprocal copies on two Macs, later source/copy edits or Delete, new Apple member, lost completion and dismissal. A disposition cannot delete the original, resolve a later revision or recreate a deliberately deleted copy. | REC-01, HIST-01, WAIT-01 |
| 11 | **Local safety and progress do not depend on provider progress.** Healthy admitted work can become durable offline; waits are bounded/dismissible and never become evidence of absence/newness. | Provider withholds an object indefinitely while local edits, close/cancel and independent pending items continue. Only actual local durability/ownership/key failures close admission; no fair user approval or unconditional network delivery is assumed. | DUR-01, ROOT-01, WAIT-01 |
| 12 | **Storage trust and copy boundaries remain honest.** Authentication, immutable naming, profile/key separation and ownership must precede decoding/use; a repository copy preserves available history but cannot claim undisclosed or unpublished data. | Duplicated/reordered/corrupt envelopes, restored writer state, credential cutover failure, foreign same-named object and provider-only reconstruction. Never reuse nonce/identity for different bytes, downgrade encryption or erase the only usable source/key. | CRYPT-01, BACKUP-01, AUTH-01 |

These are composite obligations, not twelve assertions obtained by renaming a success flag. A chain is only checked end-to-end when the same execution carries the exact captured values/identities through each boundary. Separate passing models with matching vocabulary do not establish that composition.

## Audit method and interpretation

- Inventory every active adopted/shared model and its actual runner/configuration coverage; distinguish retained experiments from adopted behavior.
- Inspect producer actions, environment transitions, recovery and independent assertions, not just summaries. Check that intended races and successful outcomes are reachable.
- Reproduce suspected failures with a stronger property or a missing legitimate environment transition before classifying them. A parser error or timeout is not a counterexample.
- Correct model errors against existing requirements; retain the old broken rule as a designated negative control where practical. If a faithful model contradicts a requirement, retain the failure and reconsider the protocol—never weaken the assertion merely to pass.
- Record known limits as limits, not automatically as spec bugs. Independently verify first-pass findings, implement valid corrections, then run a fresh second audit pass.

## Findings and corrections

Two fresh first-pass reviewers split the adopted/shared families; a third fresh reviewer then challenged the corrected set and read all 38 non-retired modules. The parent independently checked the implicated transitions and written requirements. The first-pass source-review union covers the 27 adopted/shared state machines and `CausalUndoRules`; ten retained identity/binding/retirement/co-add modules are investigative context, not adopted acceptance evidence. The second pass found no adopted-model dependency on their speculative binding/GC/co-add authority: adopted shared reducers are the targeted import classifier and `CausalUndoRules`. See the complete disposition inventory in [Coverage](Proposal5-Coverage.md).

None of the reproduced failures below required relaxing the product contract or selecting a new policy. They were model/spec mismatches, missing legitimate transitions, weak assertions or runner gaps. That does **not** establish that the specification is perfect: the uncomposed obligations below remain unproved.

The combined `SegmentDeletionSafety` fixture additionally permits one crash on **each** host in the same execution, alongside concurrent edit/Delete/Restore, external absence/replacement and actual original-file removal. Its full safety graph has 649,350 states. Its success witness requires all those events and both restored/conflict views, not just a `done` flag. This joins previously separate logical/file-race scenarios without claiming actual projection installation or an unlimited-crash theorem.

### Conditional convergence: check the argument, not only the outcome

The deletion model also checks a finite progress measure on its unchanged safety graph. Remaining pipeline work counts missing durable/staged/received/applied objects, unpublished objects and down hosts. A higher-weight finite budget counts still-possible admissions and crashes. Every change to the actual pipeline/admission/crash tuple must decrease the combined natural-number rank; every other transition must preserve rank and agreement. Disagreement must enable an actual nonstuttering pipeline step. These are independently checked obligations, not guards that prohibit failing transitions.

Under weak fairness of that pipeline, permanent disagreement would eventually have a constant rank with a continuously enabled step that must decrease it: a contradiction. User actions and provider availability are not fair in safety checks. `PerActionFairSpec` retains the original per-action transport premise; `FairSpec` uses aggregate pipeline fairness. Each pipeline action changes the tuple used by fairness. After finitely many rank-decreasing pipeline/admission/crash steps, the remaining auxiliary/stuttering transitions preserve each individual action's guard inputs, so the bounded argument also applies under the original premise. Neither formula promises convergence through infinitely many new user actions or crashes.

`stallDelivery` removes a real receive transition. One control must break progress availability; a separate direct temporal control checks `EventualAgreement` **without** rank assertions and must find a divergent behavior. This prevents the rank oracle from short-circuiting the convergence mutation. Exhaustive rank obligations plus this argument are not a TLAPS proof or a completed direct temporal run; the verification record reports those kinds of evidence separately.

Two narrower interpretation corrections also matter: the shared-window ownership fixture stages a remote value through its local pending path; it does not prove DUR-01 retention of already accepted remote history. `SeparateFileDeletionSafety` supplies a positively independent replacement token; its fresh-note branch is not the adopted classifier for every external replacement. `RepositoryCopySafety`'s disjoint private-token invariant declares copy scope; its separate progress check and private-required mutation provide the substantive no-private-store-prerequisite evidence.
