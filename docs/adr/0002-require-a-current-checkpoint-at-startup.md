# Require a provider-current checkpoint at startup

When the provider explicitly reports the canonical `Notes & Settings` or this Mac's mandatory recovery journal as stale or unmaterialized, NV will show startup progress instead of presenting the database as complete. If updating fails, the user may quit, choose another notes directory, or—only when the complete checkpoint and every mandatory legacy, active, or same-host retained journal whose covering checkpoint differs from the accepted checkpoint can be materialized, validated, and recovered—work offline and accept later reconciliation. A retained claim whose covering checkpoint exactly equals the accepted checkpoint supplies the fast-path coverage test; checkpoint identities have no ancestry or ordering semantics. Recovery checkpoint versions and unclaimed provider-managed journals do not block startup; there is no read-only mode.

Neither `ENOENT` nor an apparently empty existing cloud folder creates an empty collection implicitly. Silent initialization is limited to a root NV created in the current new-collection operation; otherwise the user must explicitly choose **Create a New Notes Collection Here**. One complete coordinated parent catalog plus fixed-name version classification establishes the startup choice; actual creation rechecks expected absence in the canonical checkpoint transaction. New collection creation installs and verifies its initial checkpoint before publishing a fresh journal or editable UI. If no acceptable canonical checkpoint can produce a startup store, including when absence was authoritatively classified while readable note files remain, **Rebuild from Note Files** is available for any NV-readable separate-file root whose applicable stable snapshot can be established. Exact-capable provider roots use complete current-known note-catalog/version fencing, confirmed ordinary-local roots use their complete coordinated current note snapshot, and `CAP-01` may use the narrower current-visible double-catalog fence with session-continuous limited-history status. Rebuild maps the existing built-in plaintext/RTF/HTML extensions deterministically and requires an operation-local decoder or Ignore decision for every other extension group; it never guesses from content. Safe defaults do not select storage format: provider-managed rebuild finishes in unencrypted plain text, uniform ordinary-local input retains its recognized format, and mixed ordinary-local input requires an explicit target and complete detached conversion. Transient, ambiguous, incomplete, or unreadable inputs cannot publish a rebuild. Installation uses expected absence or the exact classified predecessor, and any appearance or mismatch restarts discovery without mutation. Every successful path remains an all-or-nothing bootstrap reconstruction installed before the fresh journal and editable UI.

Normative requirements: `START-01`, `WAIT-01`, `CKPT-01`.
