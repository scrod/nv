# Reuse the existing sync quit barrier for provider upload

Provider-managed checkpoint availability and upload status will participate in `SyncSessionController`'s existing uncommitted-change waiting, status, error, and explicit quit-override behavior rather than introduce a second quit UI. Termination first rejects new edits and sync work, lets already admitted model mutations finish, drains presenter callbacks and provider work through a stable final reconciliation barrier, settles journal and separate-file durability, and installs at most one exactly verified root-closing checkpoint. It then uses `waitForUncommitedChangesWithInvocation:` to await upload confirmation. `CAP-01` may use the separately fenced current-visible fallback to settle visible work, but transient failures still block the pre-checkpoint barrier.

On macOS 26 and later, NV prefers an explicit ordering path when the provider-managed checkpoint advertises pause-sync and fail-upload-on-conflict support: attempt to pause `Notes & Settings`, install it through a short coordinated replacement, explicitly upload that stable version with fail-on-conflict policy, verify its returned `NSFileVersion` and `checkpointID`, resume with preserve-local-changes behavior, and only then coordinate deletion of the WAL. Advertisement authorizes the attempt; the actual operation results establish success. The network upload never runs inside a coordinator accessor. This establishes server acceptance of the database before NV issues the separate WAL deletion without claiming a cross-file cloud transaction.

Unsupported controls or failure to acquire the pause fall back to ordinary coordinated installation and File Provider synchronization rather than failing quit. After a successful pause, NV attempts resume on every path. Upload conflict, upload failure, returned-version mismatch, resume failure, override, or ambiguous status preserves the WAL; after exact local checkpoint verification, an orderly quit converts its active claim into a retained claim tied to that checkpoint. A later exactly qualified complete checkpoint may clean up that journal together with every other same-host retained journal it covers. The same qualified receipt may independently resolve only provider versions already eligible and included in its exact resolution coverage; per-version failure leaves evidence intact and does not block quit. A resume failure may leave the item paused across process death, so startup checks the native paused-state resource value and resumes before evaluating checkpoint freshness; if the user works offline, the existing sync controller retries resume. No custom pause, upload, or resolution ledger is introduced.

Older systems may qualify only a complete post-install not-uploaded/uploading-to-uploaded transition followed by exact coordinated local read-back; this is compatibility evidence rather than documented version-bound server proof, and any ambiguity remains unknown. Each later quit checkpoint provides a new opportunity to observe that transition and retire the entire covered retained backlog. When retained journals exist but no user state changed, the next orderly quit still installs one fresh-ID cleanup checkpoint for this retry. Every failure before checkpoint installation uses the same retry-or-explicit-override result while preserving the previous checkpoint, journal, and active record. Because the checkpoint is currently written later in `applicationWillTerminate:`, that write must move before the provider wait and must not be repeated by a reentrant termination callback or after upload confirmation.

Normative requirements: `WAIT-01`, `CKPT-01`, `QUAL-01`, `CLEAN-01`.
