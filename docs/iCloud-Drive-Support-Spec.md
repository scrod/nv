# Robust iCloud Drive Support

Status: working specification; major design decisions complete

Domain terms follow the project [storage and reconciliation vocabulary](../CONTEXT.md).

## Authority and scope

- iCloud Drive receives first-class support. Dropbox and other File Providers remain best-effort: NV uses compatible coordination behavior but does not promise iCloud-specific materialization, version, or status semantics.
- First-class iCloud mode requires unencrypted `PlainTextFormat` separate-file storage. A database-only, encrypted, RTF, or HTML notes directory must disable encryption when applicable and finish a complete plain-text export before it can operate in this mode.
- The live in-memory store remains authoritative while NV runs. Separate note files are the routine cross-Mac representation of note changes. `Notes & Settings` remains the complete fast-start checkpoint, settings and metadata store, backup artifact, and recovery envelope.
- A noncanonical or conflicting `Notes & Settings` version is recovery evidence, not a routine synchronization input. NV does not merge database branches into the live store during normal startup, background synchronization, or quit.
- The canonical `Notes & Settings` filename and backward-readable keyed archive remain compatible with epoch 4. Epoch 4 need not discover or recover modern uniquely named journals; after a modern crash, modern NV must recover first. NV creates no legacy WAL hard-link, clone, or copied alias.
- NV does not periodically checkpoint `Notes & Settings` or rotate the journal. Ordinary checkpoint installation occurs after editing stops during termination; startup recovery is the only other checkpoint boundary in this specification.
- A possible future RNCryptor-based separate-file format compatible with FSNotes is outside this specification. It will require its own interoperability, key-management, conflict, migration, and recovery contract.

## Product requirements

- A provider-current, materialized `Notes & Settings` opens directly into the complete in-memory store; search and editing then remain synchronous and immediate.
- Provider and network work never runs on the main thread.
- Local work is made journal-durable without waiting for a provider.
- Concurrent external note-file edits are merged when the existing file snapshot supplies a trustworthy base; otherwise every differing version is preserved.
- Network realities appear at startup, while explicitly working offline, on actionable synchronization failure, and while quitting with an unconfirmed checkpoint. Routine local save stages do not appear in the UI.
- File operations retain NV's atomic installation, expected-snapshot conflict detection, transactional reconciliation, path independence, external-move tolerance, and no-`PATH_MAX` goals wherever the filesystem permits them.
- Plain-text separate files remain interoperable with ordinary editors and plain-text iOS applications. Their contents, filenames, and provider metadata are intentionally not protected by NV's database encryption. NV does not require every note file to remain materialized for the process lifetime.

## Reconciliation evidence terms

- **Provider-version representation** exists only when the selected provider state is the candidate original, an ordinary conflict note, an identity-bound intentional tombstone, or an explicitly recorded input to a successful merge or one-sided local-win decision. Equality of a filename, path, timestamp, or output bytes alone does not establish representation. A complete transaction must represent every selected version and every differing pretransaction live state. This is the implementation contract formalized by `AllSelectedRepresented` and `CompleteFence` in [ReconciliationInterface.tla](tla/ReconciliationInterface.tla) and by `EveryProcessedVersionIsRepresented` in [ReconciliationDecisionSafety.tla](tla/ReconciliationDecisionSafety.tla).
- **Preservation** copies a readable state into a conflict note or intentional tombstone without publishing the transaction as complete. Preservation from a partial, failed, or canceled transaction does not confer provider-version resolution eligibility and always leaves reconciliation dirty. The complete-publication and partial-preservation paths are separate in [ReconciliationFencingSafety.tla](tla/ReconciliationFencingSafety.tla).
- A provider version gains **provider-version resolution eligibility** only through a complete exact transaction: enumeration was complete; every selected version was readable and represented; both provider fences matched; and the root session incarnation, structural generation, and affected UUID/LSN inputs were unchanged. Resolution additionally requires the provider-version representation to reach the applicable separate-file, checkpoint, and upload durability. A later complete transaction may confer provider-version resolution eligibility on previously preserved evidence, but preservation alone never does so. `ResolutionRequiredHistoricalEligibilityAndDurability` in [ReconciliationSafety.tla](tla/ReconciliationSafety.tla) and `PartialOrFailedRunsDoNotGainResolutionEligibility` in [RecoveryEvidenceSafety.tla](tla/RecoveryEvidenceSafety.tla) encode these boundaries.
- An **intentional tombstone** records deletion of a stable note UUID or deterministic recovery-note UUID. It is bound to that identity, not to any filename or path, and therefore continues to represent the deletion across local or remote renames. The name-independent representation rule is exercised by `Represents` and the `localRenameRemoteDelete` fixture in [ReconciliationDecisionSafety.tla](tla/ReconciliationDecisionSafety.tla).

## Startup

- On macOS 26 and later, before checking checkpoint freshness, NV reads `NSURLUbiquitousItemIsSyncPausedKey` for the canonical `Notes & Settings`. A paused checkpoint is treated as an interrupted prior transaction: NV resumes synchronization with `NSFileManagerResumeSyncBehaviorPreserveLocalChanges` and then continues the ordinary provider-current startup check. Resume failure follows the existing startup choices, and working offline leaves the sync controller responsible for retrying resume; no custom persisted pause marker is required.
- NV asynchronously coordinates and checks the canonical `Notes & Settings` before loading it.
- If iCloud reports that checkpoint as current, it can be decoded, and mandatory legacy/active-journal discovery finds no unrecovered journal-durable work, NV shows the notes immediately. Unresolved database conflict versions and unclaimed iCloud journals do not block startup because both are recovery evidence.
- Normal current-checkpoint startup does not wait for a note-directory catalog, note contents, historical-version enumeration, Spotlight, or `NSMetadataQuery`. Routine reconciliation begins in the background after the UI and fresh process journal are ready.
- An explicitly stale or unmaterialized canonical database checkpoint item shows startup progress while NV requests it. `ENOENT` is never itself treated as a new empty database; a coordinated, provider-current parent catalog is required even to classify the checkpoint and its known versions as absent rather than unavailable.
- Absence never proves that an existing cloud folder is an empty notes collection. NV may initialize silently only a directory that it created during the current new-collection operation. For any preexisting selected directory with no known checkpoint or versions, the folder chooser must make **Create a New Notes Collection Here** an explicit action; a saved folder that merely appears empty stays in startup recovery. Files or versions arriving after explicit creation are preserved and reconciled as external or recovery evidence rather than silently discarded.
- If updating fails, NV offers quit, choose another notes directory, or—only when complete local checkpoint bytes and every mandatory recovery journal can be materialized, validated, and recovered—work offline. Mandatory inputs are the legacy exact-name journal and the one active journal claimed by this Mac; unclaimed iCloud journals do not block startup. There is no read-only mode.
- Working offline loads those locally complete bytes and recovered journal state, permits edits, and persistently reports offline status until current-known note-file reconciliation succeeds. An unavailable or invalid mandatory journal cannot be bypassed because it may contain journal-durable work newer than the checkpoint.
- A legacy exact-name journal is recovered first. Only after its result is installed does NV classify and recover this Mac's modern active journal against the replacement checkpoint. A journal-recovery-eligible unclaimed journal restored into a confirmed ordinary local directory may also be recovered automatically as described below.
- If no canonical database checkpoint version can be decoded but first-class iCloud plaintext files can be cataloged, startup additionally offers **Rebuild from Note Files**. This bootstrap reconstruction uses a coordinated shallow catalog plus exact version enumeration for the authoritative candidate-URL set, materializes one complete current-known snapshot with progress, creates a replacement live store using safe default database settings, imports every distinct readable file state without inferring deletions, and repeats its exact provider fence if the directory changed. It publishes no partial store: cancel, crash, an incomplete catalog/version snapshot, or failure leaves the original artifacts untouched and requires a later retry. After a stable rebuild, NV atomically installs and verifies one complete checkpoint, creates and publishes a fresh journal, and only then presents the normal editable UI. Corrupt database versions remain recovery evidence for the ordinary **Recover Notes** action. Spotlight results cannot establish rebuild completeness.

## Routine separate-file reconciliation

- A directory catalog reads names and cheap identity/revision metadata without requesting every note's contents. Only new, changed, and unmatched rename candidates require content.
- A current-known transaction begins with a successful coordinated shallow catalog on the provider lane. Its authoritative candidate-URL set is the union of current direct children, the live model and last accepted catalog, names or URLs supplied by presenter move/version callbacks, and fixed checkpoint/journal/recovery artifact names. For each candidate URL, NV combines its current version, locally known other and unresolved versions, and asynchronously reported nonlocal versions, deduplicating them by persistent version identifier. Enumeration does not read note content; only selected versions are prepared and materialized. `NSMetadataQuery` and Spotlight results are never authoritative inputs and cannot gate the transaction, establish completeness, or clear dirty.
- Current-known completeness covers every candidate URL disclosed through those sources and every version returned for it by the required `NSFileVersion` calls. It does not claim that Apple has disclosed a historical or remote item absent from the current catalog, retained local identity, presenter callbacks, and fixed artifact names. If the platform cannot satisfy the required candidate/version-discovery contract, enumeration is incomplete and first-class complete publication remains unavailable.
- Failure to enumerate nonlocal versions makes the snapshot incomplete. NV may conservatively process known readable states, but it neither resolves or deletes versions nor reports reconciliation complete. Failed and newly arriving versions remain candidates for a later transaction.
- NV prepares selected URLs with Apple's batch coordination API. Each nested operation uses the accessor URL supplied by `NSFileCoordinator`; nonlocal version contents are accessed only through a coordinated read of the version URL, so provider preparation and materialization occur only for the selected set.
- Detached reconciliation records the model's structural generation plus affected notes' UUID/LSN values. Structural generation changes when a note is added or removed, a rename changes filesystem naming, storage format or serialization policy changes, or the notes root is replaced. UUID/LSN validation separately fences note content, title, and labels.
- A second provider catalog token and exact set of persistent version identifiers form the exact provider fence. The token and identifier set are independent opaque equality values: equality of either does not imply equality of the other, and NV infers no ordering, increment, or freshness from their values. A mismatch in either invalidates complete publication. Main-thread commit additionally requires unchanged model inputs and the same active root session incarnation; it commits the entire candidate transaction and performs no filesystem access. `ExactProviderFence` in [ReconciliationInterface.tla](tla/ReconciliationInterface.tla) and the actions that independently change only the provider catalog token or only the persistent version identifier set in [ReconciliationFencingSafety.tla](tla/ReconciliationFencingSafety.tla) formalize these obligations.
- A partial snapshot may publish only additive represented conflict notes and their decision provenance while the same root session incarnation, structural generation, and affected UUID/LSN inputs remain current. It may retain an already-existing tombstone but may not create or apply a deletion, replace the original note or name, resolve or delete provider versions, or report reconciliation complete, and it always retains the dirty follow-up obligation. Otherwise NV discards the whole detached candidate. See `CommitPartialPreservation` and `EveryPartialCommitWasConservative` in [ReconciliationFencingSafety.tla](tla/ReconciliationFencingSafety.tla).
- The provider lane records each notification in one dirty-generation high-water mark. Notifications received after a transaction starts establish a newer obligation and cause one coalesced follow-up transaction; the active transaction may not clear that obligation, even if an immediate catalog still appears unchanged. A generic external-change callback also retains a coalesced pre-callback catalog/version projection for its affected names; a later transaction may discharge it only after a stable exact observation differs from that projection, while a version callback may discharge it only when its persistent identifier appears in the exact version set. Failed fencing, partial preservation, discard, cancellation, unreadability, incomplete enumeration, and an unwitnessed callback always retain dirty with bounded-backoff retry. The state-history requirements are `EveryCompleteCommitSetCorrectDirtyState`, `EveryRetryPathKeptDirty`, and `LateProviderChangeKeepsDirty` in [ReconciliationFencingSafety.tla](tla/ReconciliationFencingSafety.tla); callback-before-catalog-visibility is an explicit implementation refinement outside that model rather than a reason to weaken its dirty invariant.
- User edits update the live store immediately, enqueue journal durability, and coalesce each note's separate-file write obligation to its latest generation. A provider completion never overwrites a newer in-memory generation.
- Existing expected-byte compare-and-swap remains the note-write conflict detector. A concurrent external and local content change uses the last reconciled separate-file bytes as its merge base; `NVMergedText` handles plain text. If the base is unavailable or the merge is unsafe, NV preserves the alternate as an ordinary conflict note with a fresh UUID. When external content still equals the base and local content wins unchanged, NV nevertheless records both the live snapshot and external version as decision ancestry before that version can gain provider-version resolution eligibility; `LocalWinsRecordsBaseAncestry` in [ReconciliationDecisionSafety.tla](tla/ReconciliationDecisionSafety.tla) prevents output equality from erasing that evidence.
- Plain-text files carry no NV UUID field or extended attribute. Identity-first matching means stable local filesystem identity when available, followed by the existing unambiguous filename and content matching. If a version cannot be associated with an existing UUID, NV treats its readable state as a new ordinary note instead of inventing a shared file identity.
- In iCloud, the selected candidate set includes every known unresolved `NSFileVersion` of a changed note item, not only its canonical version. NV resolves a version only after a complete exact transaction conferred provider-version resolution eligibility and its provider-version representation reached the applicable durability chain. A conflict note or tombstone written by a partial transaction is preservation evidence, not permission to resolve that version.
- Deletion of an externally unchanged note is selected transactionally. Deletion concurrent with changed content or a rename preserves an identity-bound tombstone for the original note and the changed or independently renamed state as a new conflict note. A rename cannot evade or invalidate an existing tombstone.
- Renames coordinate source and destination together and remain serialized with note writes. Paths and timestamps alone never establish identity.
- Changes to `Notes & Settings` while NV runs only refresh recovery-candidate metadata. They do not mutate the live store or delay routine note reconciliation.

The following decision matrix is normative. Fixture names correspond to `Scenarios`, `ExpectedCanonicalOutcome`, and `ExpectedCanonicalArtifact` in [ReconciliationDecisionSafety.tla](tla/ReconciliationDecisionSafety.tla). Iterating canonical, unresolved, and nonlocal versions in a different order must not change the final candidate, conflict artifacts, tombstones, or recorded ancestry. Exact duplicate states are deduplicated; every differing unresolved or nonlocal state is preserved rather than selected as the original solely because of arrival order.

| Conflict condition | Model fixture | Required result |
| --- | --- | --- |
| Remote content changed; local content and name remain at the base | `fastForward`, `filenameContentIdentity` | Select the canonical remote content. Filename/content fallback is valid only when both identify one unambiguous note. |
| Local content changed; remote remains at the base | `localEditRemoteUnchanged` | Keep local content and record both local and remote/base ancestry. |
| Both sides changed content with a trustworthy, safe merge base | `twoEditsMerge` | Publish the merged content and record both inputs. |
| Both sides changed content without a base or without a safe merge | `missingBase`, `unsafeMerge` | Keep the local original and preserve the remote state as an ordinary conflict note. |
| Only the remote side renamed | `remoteRenameOnly` | Select the canonical remote name without changing content. |
| Only the local side renamed | `localRenameRemoteUnchanged` | Keep the local name and record both inputs as ancestry. |
| Local rename plus remote content edit, or remote rename plus local content edit | `renameRemoteEdit`, `remoteRenameLocalEdit` | Combine the changed name with the independently changed content and record both inputs. |
| One side renamed while both sides made safely mergeable content edits | `localRenameTwoEditsMerge`, `remoteRenameTwoEditsMerge` | Publish merged content under the independently changed name and record all inputs. |
| Both sides selected different non-base names, with or without a remote content edit | `renameOnlyRace`, `renameRace` | Keep the local candidate and preserve the remote named state as a conflict note; timestamps and arrival order do not choose a winner. |
| Remote deletion races a local edit or rename | `deleteEdit`, `localRenameRemoteDelete` | Tombstone the original identity and preserve the local changed or renamed state as a conflict note. |
| Local deletion races a remote edit or rename | `localDeleteRemoteEdit`, `localDeleteRemoteRename` | Keep the original identity tombstoned and preserve the remote changed or renamed state as a conflict note. |
| Canonical deletion coexists with differing unresolved and nonlocal versions | `multiVersion` | Select deletion of the original identity and preserve every differing additional version. |
| Stable identity is absent, fallback is ambiguous, or only path/timestamp agrees | `unmatchedIdentity`, `ambiguousIdentity`, `pathTimestampIdentity` | Do not attach the version to the existing UUID; preserve it as a new ordinary conflict note with a fresh UUID. |

## Database recovery evidence

- NV catalogs the canonical and unresolved `NSFileVersion` entries for `Notes & Settings` without routinely materializing or decoding noncanonical versions.
- Recovery versions remain discoverable in the existing status UI. Their existence does not produce a modal alert or change the live store. The only recovery actions are **Recover Notes** and explicit **Discard**; NV offers no per-version picker, neither exports nor installs a recovery checkpoint, and does not restore its settings or metadata. The accepted database checkpoint is the sole source of database-scoped settings and metadata; host preferences, Keychain values, and current-host journal claims remain host-local. Preserving concurrent changes to those fields is intentionally unsupported.
- **Recover Notes** takes one coordinated snapshot of the persistent version identifiers for every local and nonlocal recovery version known in that snapshot. It records the provider catalog token and repeats the exact provider fence before declaring the run complete. Completion requires complete enumeration, no failed member, the same exact identifier set and provider catalog token, and representation of every snapshot member; `CompleteRunsHadExactAllVersionSnapshots` in [RecoveryEvidenceSafety.tla](tla/RecoveryEvidenceSafety.tla) captures that boundary. NV reads each version as an immutable snapshot, continues past a version that cannot be materialized or decoded, and reports partial completion while preserving failed and newly arrived versions for a later run. An incomplete nonlocal enumeration permits preservation of readable states but confers no new provider-version resolution eligibility and forbids resolving any candidate or declaring recovery complete. Identical note records and duplicate recovered states across versions are ignored; a missing or differing note state is imported only as a new conflict note, never over an existing note and never as evidence of deletion. This deliberately conservative recovery requires no checkpoint ancestry, retained database merge base, field-level database merge matrix, database tombstone protocol, or whole-checkpoint recovery transaction.
- Each imported recovery note receives an ordinary deterministic UUID in one fixed UUIDv5 recovery namespace. Its name input is the archived source-note UUID followed by a SHA-256 digest of canonical recovery state encoding `v1`: a domain tag; NFC-normalized, length-prefixed UTF-8 title and plaintext body; and the count plus lexicographically sorted NFC-normalized, length-prefixed UTF-8 labels. Dates, selection, filenames, formatting attributes, LSNs, sync state, and filesystem or provider metadata are excluded. Repeating recovery of the same user-authored state therefore finds the same live note or tombstone and does not import it again; a genuinely different recovered state receives a different identity. No recovery UUID field or ledger is added. Existing note UUIDs, including every UUID read from an epoch-4 checkpoint, remain unchanged.
- NV resolves or deletes a recovery version only after the user explicitly invokes recovery or discard. Successful processing alone does not authorize resolution: the version remains unresolved until a complete exact run conferred provider-version resolution eligibility, every note state it contributed has been written as a separate file or is represented by an intentional tombstone, and that complete coverage is included in an exactly read-back-verified, locally durable replacement checkpoint. In iCloud mode, the upload confirmation for that exact local checkpoint version must cover the same checkpoint identity and recovery evidence; a stale, mismatched, or unrelated callback is no evidence. `ResolvedDatabaseVersionsHadFullDurability` in [RecoveryEvidenceSafety.tla](tla/RecoveryEvidenceSafety.tla) formalizes the complete chain. Failed and newly arrived versions remain recovery candidates.
- **Discard** confirms once, captures a coordinated snapshot of persistent version identifiers, and resolves and removes each selected recovery version independently. A version that fails, disappears, changes identity, or arrives after the snapshot remains visible; discard never broadens itself to versions the user did not confirm.
- A recovery version that cannot be decoded remains preserved. No version identity, timestamp, local write order, or arrival order authorizes overwriting live data.

## Journal identity and recovery

- Every modern journal creation attempt generates a fresh random UUID `journalID`. Its path is `Interim Note-Changes.<journalID>` and its integrity-checked header contains the same `journalID` and the base identity of the exact checkpoint bytes it extends. A modern checkpoint contributes its random `checkpointID`; a loaded epoch-4 checkpoint contributes the tagged value `epoch4-sha256:<digest>` computed from its exact archived bytes, without modifying those bytes or creating an intermediate checkpoint.
- NV exclusively creates that path and writes and synchronizes the header. It then writes a top-level preference named `NVActiveJournal.<journalID>` in the exact current-application/current-user/`kCFPreferencesCurrentHost` domain. Its value is the opened `NVRootedDirectory`'s bookmark. NV synchronizes that preference and only then accepts edits. A failed attempt never reuses its ID.
- The prefixed entries form a host-local active-journal registry, not one global `activeJournalID` and not one read-modify-written dictionary. A temporary launch records its own rooted-directory bookmark without changing `GlobalPrefs`' saved default-directory bookmark, so simultaneous NV instances using different folders have independent entries.
- After opening and locking the requested rooted directory, startup enumerates only `NVActiveJournal.` entries in the exact current-host domain. Bookmark bytes are opaque and may change when refreshed, so they are resolved and compared by item identity against the open directory descriptor, never compared or used as keys directly. A candidate must also name an existing journal whose header contains the keyed `journalID` and whose `baseCheckpointID` is journal-recovery-eligible against the accepted database checkpoint. Exactly one candidate identifies the journal this Mac may recover; none makes journals in the directory unclaimed, while multiple candidates are ambiguous and authorize no append or deletion.
- If a matching bookmark resolves as stale, NV replaces only that entry's bookmark with the current `NVRootedDirectory` bookmark and synchronizes it. It never refreshes an unmatched entry because this process neither opened nor locked that folder. An unresolvable entry is preserved because its folder may be offline or disconnected. A matching entry whose journal is absent may be removed only after a coordinated catalog proves that absence.
- One fixed writer-independent file in the notes directory supplies the process-lifetime advisory lock shared by modern NV processes on this Mac. NV refuses writable modern operation when that lock cannot be obtained or the filesystem does not support it. A modern journal inode has no second lock because every compliant local discovery, claim, append, and cleanup already requires the directory lock; inode locking remains only for legacy exact-name journal recovery. Neither lock excludes NV on another Mac.
- Journal recovery validates the header and records sequentially. Every complete integrity-valid record before the first invalid or torn record forms the valid prefix; a torn final record is treated as an interrupted append, while corruption stops replay at that point. NV never truncates or repairs the discovered artifact in place and preserves it until recovered state reaches the required replacement-checkpoint durability.
- Journal recovery eligibility has three cases. A journal whose base identity exactly matches the accepted database checkpoint replays its valid prefix normally. A journal whose valid records are all already represented by the accepted database checkpoint becomes eligible for cleanup after the checkpoint satisfies the applicable local or iCloud durability rule. A base-mismatched journal may not overwrite an existing note, apply a deletion, or restore settings or metadata; recovery may only preserve differing non-deletion note states as deterministic conflict notes. LSN ordering proves order only inside one journal.
- NV never resumes appending to a discovered journal. Startup first recovers a journal-recovery-eligible active journal into a verified replacement checkpoint. If that checkpoint satisfies the root's applicable ordinary-local or iCloud durability rule, NV removes the old journal, clears its active record, and creates a fresh journal.
- If the user chooses to work offline before a recovered iCloud checkpoint is confirmed uploaded, NV preserves the recovered journal as unclaimed evidence, creates and synchronizes a fresh journal header, publishes the fresh journal's host-local record, removes the superseded record, and only then accepts edits. A crash during this transition may conservatively leave both records but leaves at least one discoverable journal and never reuses an ID.
- If termination was interrupted after checkpoint installation, recovery compares the valid journal records with the accepted database checkpoint under that journal recovery eligibility matrix and treats already represented UUID/LSN states as idempotent. Base identities and LSN values establish no order across different journals.
- A backup restored into a confirmed ordinary local directory does not need the original host preference. If exactly one structurally valid unclaimed journal is recoverable against the restored checkpoint, NV recovers it automatically while holding the directory lock; ambiguous candidates are preserved for explicit recovery.
- An unclaimed journal in iCloud may still be active on another Mac. NV catalogs its current and all known local and nonlocal file versions as recovery evidence but does not routinely materialize, replay, append to, resolve, or delete them. Explicit **Recover Notes** snapshots their persistent version identifiers, reads each valid prefix, and imports otherwise missing or differing non-deletion states with the same deterministic recovery-note identity. It never applies deletions or settings from an unclaimed journal and never resolves or deletes an iCloud journal version that may still have a remote writer.
- In iCloud, only a process whose active-journal record matches the journal may remove it automatically. The confirmed ordinary-local backup-restoration case above is the sole exception because the directory lock excludes every local writer and no cloud writer exists. During ordinary cleanup the record is cleared only after journal removal is durable, so a crash leaves a conservative stale pointer rather than undiscoverable work; the offline recovery transition above instead preserves the old journal before publishing a fresh active identity.

## Execution and file-provider coordination

- A serial durability lane owns append and synchronization through the materialized, process-lifetime open journal descriptor. It does not wait for provider work.
- A separate serial provider lane owns coordinated catalogs, selected content reads, note-file writes and renames, checkpoint installation, version inspection, and journal discovery or cleanup. Serial order preserves NV's logical filesystem order without blocking the UI.
- Each opened root has one root session that owns its provider lane, presenter, cancellation state, and dirty bit. Every activation or reopening creates a fresh, never-reused root session incarnation, including reopening the same bookmark, descriptor, path, provider catalog token, or visible contents. Every asynchronous operation captures that session and may publish filesystem, model, or UI results only while that exact incarnation remains active and uncancelled; pointer-address reuse or equality of visible inputs cannot establish session equality. A numeric global completion generation is unnecessary. `ReplaceRootSessionIncarnationWithSameInputs` and `RootSessionIncarnationsAreNeverReused` in [ReconciliationFencingSafety.tla](tla/ReconciliationFencingSafety.tla) exercise the otherwise-hidden ABA case.
- NV registers one `NSFilePresenter` for the notes directory. Its private serial operation queue updates root identity and coalesces change/version notifications; FSEvents remains the fallback for ordinary editors and non-provider filesystems. Presenter callbacks enqueue provider work only through their captured root session.
- `NSFileCoordinator`, `NSFilePresenter`, and the advisory lock coordinate this Mac and its local provider extension only; none is a cross-Mac lock. Remote convergence comes from provider-delivered versions plus NV's compare-and-swap, merge, and conservative preservation rules.
- Coordinator URLs are transient and mandatory inside accessors. `NVRootedDirectory`'s open directory descriptor, bookmark, and file-reference identity remain authoritative between operations.
- A provider- or Finder-driven root move updates the presented URL, rooted-directory bookmark/file reference, matching active-journal record, FSEvents subscription, and provider classification while descriptor-relative operations continue. NV removes its app-initiated whole-directory relocation command.
- Runtime folder switching first freezes mutations to the old root and performs its durability transaction: synchronize the journal, settle separate-file obligations, run the final provider barrier, install and verify the checkpoint, and apply the root's ordinary local or iCloud journal-cleanup rule. Any unsettled prerequisite or unconfirmed iCloud checkpoint cancels switching unless the journal is durable and the user explicitly chooses to leave that journal and active record for later recovery. Only then does NV deactivate the old root session, drain and unregister its presenter, release the rooted directory, and begin startup for the new root.
- `NSUbiquityIdentityDidChangeNotification` freezes provider mutations, preserves the active journal, marks the root's provider classification unknown, invalidates current-known claims, and starts asynchronous reclassification and reconciliation. NV neither persists nor logs the identity token. Working offline remains available only under the mandatory-recovery-input rule above.

## Checkpoint and quit transaction

- Termination enters a quiescing state: it rejects new user edits and new synchronization work, lets already admitted sync sessions and external-editing work finish mutating the model, and then freezes the final model state.
- The provider lane then reaches one final barrier. It drains queued presenter work, performs current-known reconciliation until the catalog and version snapshots, model generations, and dirty bit are stable, settles resulting note-file writes, and atomically marks the root session closing so no later callback can publish into this transaction. NV then unregisters and drains the presenter. External changes genuinely arriving afterward remain in the separate files for next-launch reconciliation.
- Every failure before checkpoint installation—including catalog or version enumeration, required materialization, reconciliation, note-file settlement, journal synchronization, or the provider barrier—uses one outcome. Retry keeps waiting. **Quit Anyway** leaves the previous checkpoint, active journal, and host-local active record intact and installs no new checkpoint representing unsettled obligations. `applicationWillTerminate:` performs no fallback flush.
- After all prerequisites settle, NV serializes the complete live store with a fresh random `checkpointID`, atomically installs `Notes & Settings`, synchronizes the directory, and coordinates an exact read-back. Every checkpoint installation attempt—quit, startup recovery, rebuild, recovery-evidence preservation, or storage transition—consumes a fresh, never-reused ID; a failed attempt does not make its ID reusable. Installation is verified only when the read-back bytes exactly equal the serialized frozen bytes, those bytes decode successfully, and they contain the expected `checkpointID`; the existing rough structural verifier alone cannot authorize journal deletion. `CheckpointIDsAreNeverReused` is checked independently by [QuitSafety.tla](tla/QuitSafety.tla), [StartupSafety.tla](tla/StartupSafety.tla), [RecoveryEvidenceSafety.tla](tla/RecoveryEvidenceSafety.tla), and [StorageTransitionSafety.tla](tla/StorageTransitionSafety.tla).
- Database recovery versions are not newly reconciled during this transaction and are never marked resolved merely because NV installed a checkpoint. After exact checkpoint durability, quit may finish resolution only for the persistent version identifiers that gained provider-version resolution eligibility through an explicit **Recover Notes** action in this process; that action's set is transient and requires no recovery ledger.
- For a confirmed ordinary local directory, successful exact checkpoint verification and local directory durability make the active journal removable under the existing rule.
- For iCloud on macOS 26 and later, NV prefers an explicit database-before-journal-deletion barrier. When the checkpoint item advertises both pause-sync and fail-upload-on-conflict controls, NV pauses it before checkpoint installation, atomically installs the checkpoint in a short coordinated replacement, and explicitly uploads the stable local version with fail-on-conflict policy. NV gives that request a transaction-local identity and accepts its callback only when it belongs to the still-pending request and its returned `NSFileVersion` identifies the exact installed and read-back-verified local version containing the same `checkpointID`; callback arrival alone or a matching checkpoint field in a different local version is insufficient. NV then resumes synchronization with preserve-local-changes behavior. Only after both exact-version upload and resume succeed may NV coordinate deletion of the active journal. `ExplicitUploadCallback` and `ExplicitConfirmationMatchedRequest` in [QuitSafety.tla](tla/QuitSafety.tla) formalize this correlation. The coordinator accessor never remains open during the network upload.
- Unsupported controls or a pause failure before the item becomes paused are not quit failures. NV installs the checkpoint through the ordinary coordinated path and leaves subsequent transfer to iCloud Drive. A successful pause is followed by a resume attempt on every upload, conflict, cancellation, and error path. Upload failure, conflict, returned-version mismatch, or resume failure likewise falls back to ordinary synchronization when synchronization is running; none prevents explicit quit override, and each retains the journal and active record for that quit attempt. If resume itself fails, the checkpoint may remain paused, and startup repairs it using the paused-state resource key before freshness evaluation. A later successful exact upload may clean up the retained journal through the ordinary recovery transaction.
- The explicit upload callback establishes the required remote ordering without claiming a cross-file cloud transaction: NV does not issue the journal deletion until iCloud has accepted the installed checkpoint. In fallback operation no such ordering is claimed, so an unconfirmed journal remains recovery evidence while the checkpoint and journal synchronize normally.
- On macOS 11.5 through 15, NV uses the strongest available compatibility qualification: after installing the checkpoint it must observe a new not-uploaded or uploading state followed by uploaded, with no intervening local checkpoint write, and then coordinate an exact read-back of the installed `checkpointID` and captured local version. This is not documented version-bound server proof. If the complete post-install transition is missed or any observation is ambiguous, status remains unknown and NV retains the journal. The macOS 26 version-returning contract is normative for long-term behavior.
- iCloud availability and upload status reuse `SyncSessionController`'s `waitForUncommitedChangesWithInvocation:` progress, error, and explicit quit-override behavior. Pending upload waits; override, unknown status, or a surfaced error permits quitting with the journal and active record intact.
- Termination advances monotonically through one attempt. Reentrant callbacks resume the recorded phase and never repeat reconciliation, install a second checkpoint, or perform a later checkpoint rewrite.
- Local file-first ordering is a crash-consistency rule, not a promise about iCloud's cross-file delivery order. NV waits for local separate-file settlement, not upload of every note file; the uploaded complete checkpoint remains recovery evidence if a note-file upload is delayed.

## Provider fallback and user presentation

- Provider classification is confirmed iCloud, confirmed other File Provider, confirmed ordinary local storage, or unknown. NV checks iCloud ubiquity first for the selected item and nearest existing ancestors. It uses File Provider URL-domain identity for the remaining distinction only after that API's consumer-app contract has been independently validated. Confirmed ordinary local storage requires successful exclusion from both systems plus local-filesystem evidence. Missing ancestors, unsupported APIs, permission failures, transient provider errors, or inconclusive answers classify as unknown rather than local.
- First-class behavior is derived at runtime from confirmed iCloud classification, `PlainTextFormat`, and disabled encryption. NV stores no independent first-class-mode preference whose value could disagree with the folder's actual provider or storage format.
- Dropbox and other File Providers receive off-main coordinated access, compare-and-swap writes, transactional scans, and generic retry/error reporting. NV does not promise their materialization status, remote upload confirmation, or conflict-version enumeration.
- Unknown and other-File-Provider classifications retain the journal and use coordinated access without claiming iCloud or local-only durability. Only confirmed ordinary local storage uses the ordinary local-durability cleanup rule.
- A current startup checkpoint opens without synchronization UI. Required materialization shows progress. Working offline remains visible. Ordinary background reconciliation reuses the existing synchronizing indicator.
- Successful text merges are silent. Preserved alternatives become ordinary conflict notes and produce one coalesced notification. Database and unclaimed-journal recovery candidates remain discoverable without interrupting normal launches.
- Upload pending/unknown means the checkpoint is durable on this Mac but exact-version upload confirmation is absent. NV does not separately report “saved in journal” and “saved to note file.”

## Migration, security, and compatibility

- Compatibility obligations are determined only by artifacts and behavior represented by commits reachable from `origin/master`. This specification describes one unreleased epoch-5 target; superseded epoch-5 drafts and local implementations absent from `origin/master` require no transitional reader, migration, alias, dual-write, or behavioral compatibility. The epoch-4 compatibility contract remains explicit below.
- Entering first-class iCloud operation explicitly warns that notes will be stored in clear text and requires one controlled restart transaction because disabling encryption changes both the checkpoint and journal keys. NV freezes editing; settles separate-file and journal obligations; installs and verifies a complete old-format, old-key checkpoint; retires the old journal only after its applicable durability barrier; exports every live note through the plaintext writer; verifies a fenced catalog; installs the complete unencrypted checkpoint; and restarts with a freshly created journal before accepting edits. The storage transition is complete only after every phase succeeds. Until the final checkpoint is installed, its old format is the restart marker: cancel or failure leaves that complete checkpoint recoverable, while a retry loads it, reruns plaintext export idempotently, and preserves any divergent file as external work. No migration-phase ledger or compatibility with an intermediate epoch-5 draft is required.
- If a selected folder is already in iCloud, or provider reclassification detects that Finder moved the active folder there, an incompatible format or enabled encryption becomes the same blocking controlled transition. NV keeps admitted edits journal-durable and offers convert and restart, choose another folder, or quit; it neither silently changes format, records a contradictory mode flag, downgrades to best-effort operation, nor runs a read-only mode.
- A legacy checkpoint remains readable and receives a random `checkpointID` only on the next verified modern save. Until then, a new modern journal uses `epoch4-sha256:<digest-of-exact-loaded-bytes>` as its base identity so startup need not rewrite the checkpoint before presenting the UI. Migration never regenerates an existing note UUID. When legacy and modern journals coexist, the legacy exact-name journal is recovered and checkpointed first; only then is the modern journal evaluated against that replacement checkpoint.
- Concurrent epoch-4 and modern editing is unsupported. If a legacy exact-name WAL appears while modern NV is active, NV stops new filesystem mutations, preserves its journal, and asks the user to quit both processes and relaunch modern NV.
- Checkpoint and journal IDs are fresh, never-reused random opaque values; no ordering or ancestry is inferred from them. A synthesized recovery note alone uses the deterministic identity described above. NV records no hostname, hardware serial, iCloud account identifier, or other stable machine identity in shared files.
- Existing checksums—and encryption where used outside first-class iCloud mode—detect accidental corruption and malformed data; they do not authenticate files against a malicious writer. Invalid or mismatched artifacts never authorize append, replay, resolution, or deletion.
- Diagnostics contain no note text, filenames, tags, encryption material, account identifiers, or path-bearing error descriptions. Storage logs are limited to operation, count, error domain, and error code; no telemetry is added.

## Formal-model assumptions and implementation obligations

- The TLA+ modules treat atomic replacement and directory synchronization, immutable persistent version identifiers and immutable coordinated version snapshots, the truth of any implementation assertion that authoritative candidate discovery is complete, correct checksum and decoder results, advisory-lock behavior, and coordinator accessor semantics as environmental assumptions. If the implementation cannot establish one of those assumptions for an operation, it classifies the snapshot as incomplete or the status as unknown, preserves existing artifacts and versions, retains the applicable journal and dirty obligation, and does not publish destructive changes, resolve evidence, or claim completion. The assumption boundary is summarized in the [TLA+ model README](tla/README.md), the Apple behaviors requiring real-system confirmation are enumerated in [Apple API Contract Validation](Apple-API-Contract-Validation.md), and the fail-closed publication boundary is expressed by `CompleteFence` in [ReconciliationInterface.tla](tla/ReconciliationInterface.tla).
- Weak fairness applies only to work NV controls once it remains enabled. NV does not assume that a provider, network, user, unavailable version, or unreadable artifact eventually succeeds. “Current-known” therefore remains a claim about one fenced provider snapshot, never proof that no unseen remote work exists.
- Passing a model does not prove the Objective-C implementation, Apple API behavior, real `NVMergedText` output, filesystem identity stability, UUIDv5 or SHA-256 byte vectors, filename collision and Unicode/case behavior, UI disclosure, thread affinity, redacted diagnostics, or epoch-4 archive compatibility. Those remain implementation review, deterministic vector, integration, filesystem-matrix, and crash-point test obligations; the formal model supplies the required safety contract against which those tests are judged.
