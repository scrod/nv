# Robust iCloud Drive Support

Status: working specification; simplified current-visible/local-WAL design adopted

Domain terms follow the project [storage and reconciliation vocabulary](../CONTEXT.md). The ADRs describe current decision slices under this normative specification; git history records earlier designs.

## Authority and scope

- iCloud Drive receives tested first-class support. Runtime correctness does not depend on identifying a provider vendor. Positive ubiquitous-item or File Provider evidence establishes provider management; absence, failure, or ambiguity leaves the root unclassified rather than proving ordinary-local storage. Dropbox and other providers receive compatible best-effort behavior.
- First-class provider-managed operation requires unencrypted `PlainTextFormat` separate-file storage. Complete plain-text export and the existing formatting-loss disclosure precede entry from database-only, encrypted, RTF, or HTML storage.
- The live in-memory store remains authoritative while NV runs. Separate note files are the routine cross-Mac representation. `Notes & Settings` is the complete fast-start checkpoint and sole database source of settings and metadata.
- Routine synchronization is current-visible. NV does not enumerate provider history to claim completeness, persist provider-version ancestry, recover noncanonical checkpoint versions, or automatically resolve/remove Apple file versions. The exact current checkpoint returned by `NVCheckpointInstallCurrentChanged` is a narrow root-closing input for complete note-set/base-relative-deletion reconciliation, not historical recovery.
- Modern WALs are host-local Application Support artifacts. They protect same-Mac crash recovery and are never provider synchronization inputs. Epoch-4 exact-name journals remain readable for migration, but no new modern journal is written into a notes directory.
- The canonical checkpoint and epoch-4-readable core archive remain compatible with epoch 4. No compatibility is required for unpublished epoch-5 draft journal, claim, ancestry, or receipt formats.
- NV neither periodically checkpoints nor rotates the WAL. One accepted checkpoint and one fresh local WAL precede editing; closing a writable root installs at most one final checkpoint.

## Product requirements

- A provider-current, materialized checkpoint opens directly into the complete in-memory store; search and editing remain synchronous and immediate.
- Provider and network work never runs on the main thread. Local WAL append and barrier synchronization never wait for a provider.
- If local WAL durability becomes uncertain, NV stops admitting new edits. A successful `write` alone is not durability.
- Concurrent visible note-file edits use the existing trustworthy-base merge rules; otherwise every differing visible state is preserved as a conflict note.
- A current `Notes & Settings` replacement detected by the checkpoint compare-and-swap is never overwritten blindly. NV automatically reconciles only its complete note set, base-relative deletion outcomes, and retired deterministic conflict identities against the retained accepted checkpoint and live store; live preferences and database-scoped metadata remain unchanged.
- Conflicts held only in Apple version history are not automatic synchronization inputs. When Apple reports unresolved versions for a visible note, an alert badge lets the user replace that note's editor with a read-only resolver and choose one disclosed body for the original note or save a disclosed body as a separate ordinary note.
- Plain-text files remain interoperable with ordinary editors and plain-text iOS applications. Their content, names, and provider metadata are intentionally outside NV database encryption.
- File operations retain atomic installation, expected-snapshot conflict detection, transactional publication, path independence, external-move tolerance, and no-`PATH_MAX` goals wherever the filesystem permits.
- Provider and root identity are positive-only. A missing path, vnode event, stale bookmark, unavailable provider, or failed lookup never proves deletion or authorizes path retargeting. If positive continuity cannot be established, NV exposes the existing recovery choices and ends the old session only through an explicit user action.

## Normative requirement registry

| Requirement | Claim | Required evidence | What it permits |
| --- | --- | --- | --- |
| `AUTH-01` | Positive-only provider authority and root continuity | One active root-session incarnation, optional positive provider item/domain identity, and positive same-root or changed-authority evidence after a location or authority disturbance | Provider-specific operation, retention of the existing session, or fencing into a provisional successor; an unclassified or unavailable root grants no provider, deletion, or retargeting inference |
| `START-01` | Startup store acceptance | Exclusive lock on the opened root-directory descriptor, exact complete checkpoint bytes, successful decode, recovery of every matching host-local and legacy WAL, and a fresh synchronized host-local WAL | Editable live-store publication |
| `DISC-01` | Current-visible discovery | Two equal complete coordinated shallow note catalogs surrounding all selected current-file reads | Selection of one current-visible reconciliation or rebuild candidate |
| `PUB-01` | Routine publication | `DISC-01` plus unchanged root session, structural generation, and affected note UUID/LSN inputs; every differing pretransaction visible state represented | Atomic publication and consumption of only the serviced dirty generation |
| `REC-01` | Explicit unresolved-version disposition | User action, one visible source file, an operation-local snapshot of Apple-reported unresolved versions, a frozen current body, and a coordinated readable immutable state for each selected member | Use a selected body in the original note or create an idempotent ordinary conflict note; mark only the disposition's disclosed members resolved after the resulting WAL and exact separate-file generations are locally installed; never remove provider history |
| `DUR-01` | Local checkpoint durability | Settled note-file obligations and local WAL, expected-current checkpoint CAS, exact installation, directory durability, read-back equality, decode, and checkpoint identity | Local checkpoint acceptance and retirement of WAL work proven represented |
| `CLEAN-01` | Local recovery cleanup | `DUR-01` or startup proof that a WAL's records are already represented, followed by local Application Support removal and directory synchronization | Deletion of only this Mac's matching WAL; never an Apple version |
| `ROOT-01` | Root-state action gating | Active/available root-session state, validated root/WAL association, local-WAL durability, and lifecycle reasons | Allowed editing, publication, cleanup, positive recovery, and explicit user-directed termination of an unavailable session |
| `CKPT-01` | Checkpoint-caller outcomes | One typed result from the canonical checkpoint transaction under exact expected-current evidence; current-change reconciliation additionally requires exact readable complete current checkpoint bytes, the exact retained predecessor, and unchanged root/model inputs | Caller-specific retry, cancellation, override, retention, publication, or complete note-set/base-relative-deletion reconciliation followed by a fresh attempt |
| `WAIT-01` | Waiting and cancellation | Operation ownership plus unchanged correctness evidence; elapsed time is never evidence | Progress and cancellation choices without manufacturing success or failure |

Principal paths:

- Startup: `AUTH-01` → checkpoint classification/materialization → local WAL recovery → `START-01`.
- Routine reconciliation: `AUTH-01` → `DISC-01` → `PUB-01`.
- Explicit conflict disposition: Apple reports unresolved versions for a visible file → user invokes `REC-01` → the chosen current-note or new-note state becomes locally durable → only the disposition's disclosed members are marked resolved.
- Root closure: settle current-visible work and local obligations → `CKPT-01`; success continues to `DUR-01` → `CLEAN-01`, while `NVCheckpointInstallCurrentChanged` performs one complete note-set/base-relative-deletion reconciliation, unions retired deterministic conflict identities, settles its new obligations, and makes a fresh exact-current attempt.
- Root disturbance: obtain a candidate URL from rooted, presenter, file-reference, or bookmark evidence → validate positive same-root identity and resume, validate positive changed authority and fence into a provisional successor, or enter root-continuity-unavailable state → Retry, **Save Current Collection As…**, **Re-open from Disk**, or quit without manufacturing deletion evidence.

No path removes an `NSFileVersion`. Only an explicit action in the conflict resolver sets `resolved = YES`, after local durability proves the user's chosen contents are represented. Provider upload status is presentation state, not a rung in that durability chain.

## Startup

- Open and validate the rooted directory, then acquire its nonblocking exclusive directory-descriptor lock before registering observers, discovering/recovering WALs, or mutating the collection. Lock contention or failure leaves startup unattached and offers Retry, another directory, or quit; **Work Offline** cannot bypass the lock. Directory open and provider access stay off-main; nonblocking `flock` does not establish a bounded provider-open time.
- NV asynchronously coordinates and checks the canonical `Notes & Settings` before loading it. A provider-current, materialized, decodable checkpoint may be accepted without first cataloging note files or provider history.
- Before publishing editing, NV scans `NSApplicationSupportDirectory/Notational Velocity/Recovery Journals` and validates every modern WAL whose header bookmark resolves to the selected root. It also checks the selected root for the legacy exact-name epoch-4 WAL. Matching artifacts are mandatory local recovery evidence; unrelated Application Support WALs remain untouched.
- Exact-base WAL records replay in order. A WAL whose work is already exactly represented by the accepted checkpoint requires only local cleanup. Base-mismatched nondeletion states may become deterministic conflict notes, but base-mismatched ordinary deletion or settings records never overwrite, delete, or restore. One additive exception applies to every structurally valid, positively root-associated modern WAL: a `DeletedNoteObject` whose UUID has the reserved RFC 9562 version-8 form unions that UUID into the retired deterministic conflict identity set regardless of checkpoint-base relation. Exact-base replay may additionally apply its logical deletion; base-mismatch replay applies only retirement and never removes or suppresses a live note or file. Parsing stops at the first torn, corrupt, undecodable, or semantically invalid record; uncertain evidence remains preserved and blocks a fresh WAL until the user retries, saves the live collection elsewhere, or explicitly abandons that evidence.
- If several local WALs match one root, recovery snapshots all of them. Order is preserved within each WAL and never inferred across WALs; cross-WAL differences are preserved. One exactly verified recovery checkpoint must represent every successfully recovered member before those WALs are deleted and a fresh WAL is exposed.
- If checkpoint materialization fails, the user may retry, quit, choose another directory, or work offline only when complete local checkpoint bytes and every matching local WAL are readable and recoverable. There is no read-only mode.
- `ENOENT` and an apparently empty cloud folder do not create a collection implicitly. Silent initialization is limited to a directory NV exclusively created for the current new-collection operation. Any preexisting selected directory requires explicit **Create a New Notes Collection Here** and expected-absence revalidation inside the checkpoint transaction.
- If no acceptable checkpoint can produce a store, **Rebuild from Note Files** uses one complete stable current-visible snapshot. It decodes current direct-child files only, never Apple history or noncanonical database versions. Built-in extension mappings remain `txt`, `text`, `utf8`, `taskpaper`, `rtf`, `html`, and `htm`; other extension groups require an explicit decoder or Ignore choice. A first-class provider-managed rebuild always targets unencrypted `PlainTextFormat`. Outside that contract, uniform recognized input retains its format; mixed recognized input requires an explicit target format and detached conversion, including the existing formatting/attachment-loss disclosure when conversion selects plaintext. Rebuild is detached, all-or-nothing, and installs an exactly verified checkpoint before creating a fresh WAL or editable UI.
- Normal startup and rebuild never depend on Spotlight or `NSMetadataQuery`.

## Routine separate-file reconciliation

- One coordinated shallow catalog reads current direct-child names and cheap identity/revision metadata without materializing every note. The note projection excludes `Notes & Settings`, the legacy WAL, hidden `.nv-write-<UUID>` residue, and all directories. There is no lock-file artifact; modern WALs cannot appear because they are outside the root.
- The authoritative candidate set combines current note-file children, identities/names retained by the live model and last accepted catalog, and note URLs delivered by presenter move callbacks. A visible `Title (conflict recovery <UUID>).ext` is an ordinary note candidate.
- A transaction captures the first complete catalog, reads only selected current files through `NSFileCoordinator`, and captures a second complete catalog. Equal catalog tokens/current snapshots plus unchanged root session, structural generation, and affected note UUID/LSN values form the publication fence. A callback or elapsed time is only a wakeup.
- An incomplete catalog, unreadable selected file, changed fence, cancellation, or stale model input publishes no destructive change and retains dirty with bounded-backoff retry. Additive conflict notes already made durable may remain.
- User edits update the live store immediately and admit the note or UUID/LSN deletion record to the existing pending WAL/file sets without performing I/O. Its current UUID/LSN when captured names the pending generation; no second generation registry is required. Normal WAL capture and separate-file export are coalesced to the newest generation; resolver, external-editor, and lifecycle durability boundaries force immediate asynchronous capture/barrier. A stale WAL, provider, or write completion never overwrites or clears a newer in-memory generation.
- Existing expected-byte compare-and-swap remains the note-write conflict detector. The last exact accepted note-file snapshot is the preferred merge base. The accepted checkpoint may seed a base only when its installation boundary had settled that note's separate-file obligation.
- Stable filesystem identity is optional equality evidence. A nonzero document ID is usable only with an equal volume UUID; a nonzero file ID is usable only within one active root session; either identifier must be unique on both association sides. Generation count is revision metadata, not identity. NV assumes none of these values survives provider eviction, rematerialization, replacement, or an authority/root-session change. Missing, changed, or ambiguous identity falls through to existing unambiguous filename/content matching. Paths and timestamps alone never establish identity; an unmatched readable current file becomes a new ordinary note.
- Separate note files carry no NV UUID xattr or sidecar. An ordinary UUID reaches another modern client only through a complete accepted checkpoint; an unmatched file always receives a fresh random version-4 UUID and cannot reintroduce a deleted logical UUID.
- Every intentional deletion creates a UUID/LSN `DeletedNoteObject` as a pending/WAL removal record independently of legacy `syncServicesMD`. A verified complete checkpoint represents an ordinary completed deletion by omitting the UUID; the removal record is then covered and may be discarded with its WAL. It is never serialized forward as a permanent general tombstone.
- The user's original delete operation may remove the represented separate file only inside coordinated expected-snapshot revalidation proving that the current file is the note's exact accepted or exactly installed generation. A mismatch records the logical deletion but preserves/imports the visible file state. No pending deletion record, checkpoint omission, or retired deterministic identity may remove a current file because its filename, body/digest, timestamps, or unavailable/changed filesystem identity resemble the deleted note. Such a file is preserved/imported as an ordinary note with a fresh UUID.
- The normative current-visible outcomes are:

| Visible condition | Required result |
| --- | --- |
| Remote changed; local remains at base | Accept the remote current state |
| Local changed; remote remains at base | Keep local and schedule its file write |
| Both content branches changed with a trustworthy safe base | Publish `NVMergedText` output |
| Both changed without a safe base | Keep local and preserve remote as a conflict note |
| Independent rename and content edit | Combine the independent changes |
| Conflicting renames | Keep local and preserve the remote named state as a conflict note |
| Current-file deletion races a still-local changed or renamed state relative to the last accepted file snapshot | Keep the source UUID deleted and preserve the changed state as a conflict note |
| Identity absent or ambiguous | Do not attach to an existing UUID; import as a new ordinary note |

- Routine conflict preservation creates an ordinary note with a fresh random version-4 UUID through the existing creation paths. It does not consult automatic deterministic recovery candidates or their retired identities. A modified, retired, or inconsistent candidate from checkpoint-current/WAL recovery never waives the current-file matrix's preservation requirement or authorizes overwriting that candidate. Visible replacement-recovery artifacts remain ordinary import candidates.
- NV never calls `otherVersionsOfItemAtURL:`, `getNonlocalVersionsOfItemAtURL:completionHandler:`, `removeOtherVersionsOfItemAtURL:`, or `setResolved:` for routine reconciliation. A current local `NSFileVersion.persistentIdentifier`, when available, only supplements the root-session-scoped exact file observation used by checkpoint and note-file compare-and-swap; it is not a generation counter.
- Once an edited separate file has itself become the host's accepted current snapshot, a later provider deletion is indistinguishable from an intentional deletion made after that edit. If the visible current file disappears without Apple disclosing the edited body as unresolved, current-visible reconciliation accepts the deletion and cannot create a conflict note from undisclosed history. Live macOS 14/26 testing exposed this Current/unresolved result for all eight edit/delete races; it does not establish whether the provider retained undisclosed data. A competing complete checkpoint can still preserve a delete/edit branch through the checkpoint-current rule below, but note-file publication alone carries no cross-machine current-visible recovery guarantee for a delete/edit race.

## Embedded unresolved-version disposition

- A positive unresolved-conflict resource value is advisory. A nonempty `unresolvedConflictVersionsOfItemAtURL:` result for a currently visible note shows a persistent alert badge; it never presents the resolver automatically. Clicking the badge swaps `ConflictResolverView` into the editor split-view subview in place of `LinkingEditor`. The hidden editor, its text storage, undo manager, selection, and scroll position remain alive. The resolver owns a separate noneditable `NSTextView` or another text-presentation control with equivalent fidelity, scrolling, selection, copy, and accessibility behavior; it never shares or overrides `LinkingEditor` storage, delegates, undo, or persistence machinery. The resolver is nonmodal, so the note list and search remain usable. Its close **×** is always enabled and swaps `LinkingEditor` back immediately; dismissing the resolver neither cancels nor proves any disposition operation.
- The resolver captures one operation-local snapshot of only the unresolved versions Apple currently returns plus the source note UUID/LSN, structural and root-session generations, title, labels, separate-file format, and a frozen copy of the authoritative in-memory current body, including admitted edits not yet written to disk. The **Conflicts** popup contains **Current** plus those snapshot members; it never lists all history.
- Selecting **Current** shows that frozen body. Selecting a conflicting member asynchronously coordinates and reads its own `NSFileVersion.URL`, decoding those bytes with the source note's captured separate-file format rather than inferring a format from the provider's version URL. The resolver never blocks the main thread, substitutes bytes from the current URL, or mutates the live note merely to preview. The resolver preview is read-only.
- **Use this version** first revalidates the captured note UUID/LSN, structural generation, and root-session incarnation, then applies only the previewed body to the original note through the ordinary note-mutation/save machinery. A mismatch applies nothing and refreshes the resolver. Choosing **Current** performs no body mutation. The original UUID, filename, title, labels, and database metadata remain unchanged. NV does not call `replaceItemAtURL:options:error:` on an `NSFileVersion`.
- Before resolving provider evidence, NV barrier-synchronizes the chosen current-note generation to the host-local WAL and verifies exact local installation of that generation's separate-file write. In a short coordinated `NSFileCoordinatorWritingForMerging` accessor it revalidates the captured root/session and exact installed current-note generation, then sets `resolved = YES` on every still-applicable member of the captured unresolved snapshot, because the user chose the winner for that snapshot. A failed revalidation resolves nothing. Versions reported after the snapshot remain unresolved.
- **Save as new note** is disabled for **Current**. Its stable recovery key is SHA-256 over a fixed versioned domain separator, the source note UUID, and the previewed body in NV's canonical NFC-normalized UTF-8 encoding. Title, labels, extension, and collision-adjusted filename are output attributes, not identity inputs. A candidate note UUID is deterministically derived from that key and a nonnegative recovery-slot ordinal; slot zero is the normal case.
- A candidate UUID is reusable only while it identifies a live note whose canonical body still equals the preview and whose exact current separate-file generation is locally installed or remains an ordinary pending obligation that can be installed without overwriting newer work. A UUID match, filename match, or retired-identity membership alone is never recovery evidence. If an earlier slot was edited or its UUID was retired before resolution, NV neither overwrites it nor resolves the provider member; a later explicit **Save as new note** uses the lowest reusable or unused nonretired deterministic slot and creates an ordinary collision-adjusted `Title (conflict).ext` note with the captured title and labels.
- Before marking that selected member resolved, NV barrier-synchronizes the chosen recovery note's exact WAL generation and verifies exact local installation of its separate file. It then coordinates the source with `NSFileCoordinatorWritingForMerging`, revalidates operation/root identity and member applicability, and marks only that selected member `resolved = YES`; other snapshot members remain unresolved. Deleting the resulting ordinary note after confirmed resolution is an ordinary user deletion and does not cause NV to recreate it from that resolved provider member.
- After either action, NV freshly calls `unresolvedConflictVersionsOfItemAtURL:`. Because the `resolved` setter has no error result and cannot be reversed, this query is the only success test: a nonempty result rebuilds the popup, selects **Current**, and keeps the badge; an empty result clears the badge and restores `LinkingEditor` if the resolver is presented. A nil result or read/query error is retryable ambiguity, never proof of resolution. Partial `resolved` failures are handled by the same fresh query.
- Each preview/member disposition owns its own status and button availability; **Saving chosen version…**, **Saving conflict note…**, **Waiting to write note file…**, and **Checking conflict status…** never become resolver-wide waiting states. The selected in-flight item's disposition buttons are disabled, but the close **×** and selection/preview of other items remain available. On each host, same-source dispositions execute serially on that root session's provider lane; this creates no cross-host lock or shared source-note generation.
- A disposition may continue after the resolver is dismissed. Its automatic provider retry pass is finite; exhaustion parks only that item as **Retry when reopened**. Re-presenting the resolver by clicking the alert badge automatically starts one fresh bounded attempt for every parked item belonging to that note. Running attempts are reattached, never duplicated. The resolver has no explicit Retry action. Retries reuse the already admitted exact generation or deterministic recovery slot. Failure or cancellation leaves unresolved evidence and the alert badge available. Already admitted/durable note changes and ordinary conflict notes remain. No pending resolution intent survives launch and no checkpoint, persistent recovery ledger, provider identifier archive, upload qualification, or provider-version removal is required.
- Dismissing the resolver permits ordinary editing. A newer edit to the source note invalidates a pending **Use this version** operation unless the chosen exact generation had already passed coordinated revalidation; the newer edit is never overwritten and stale work marks no member resolved. A pending **Save as new note** may continue independently, but editing/deleting its recovery note invalidates that candidate's evidence as described above. A global local-WAL durability suspension remains a separate safety gate and is not weakened by per-version UI state.
- NV never calls `removeOtherVersionsOfItemAtURL:` or any individual-version removal API. Resolved versions may remain in Apple's history and consume provider quota. The initial resolver has no **Merge** button; a later reviewed merge may reuse the ordinary mutation path only after a trustworthy base is available, and would gain no broader resolution authority.
- Noncanonical or historical `Notes & Settings` versions are neither decoded nor exposed through this action. The separate `NVCheckpointInstallCurrentChanged` path may decode the exact canonical current checkpoint only to reconcile complete note sets, base-relative deletions, and retired deterministic conflict identities during root closure. There is no **Recover Notes**, database-version picker, automatic historical recovery, or **Discard** command.

## Host-local WAL identity and recovery

- Modern WALs live at the user-domain Application Support URL returned by Foundation, in the exact relative directory `Notational Velocity/Recovery Journals`. The directory and each WAL are mode `0700` and `0600` respectively where supported and are excluded from backup/sync only through documented local filesystem metadata; path prefixes are not used as identity evidence.
- Each editable root session exclusively creates one random `Interim Note-Changes.<journalID>` there, writes and barrier-synchronizes its complete header, synchronizes the Recovery Journals directory, and only then returns an append-capable descriptor. Failed or colliding IDs are burned.
- Version 2 changes the location and header only. Record bodies remain the existing keyed `NoteObject`/`DeletedNoteObject` archives with existing shared compression, per-record encryption, framing, and checksum behavior; an unencrypted collection continues to use the existing fixed nonsecret record key. Preferences, selection, and other database-level metadata are checkpoint-scoped and never become WAL records. The plaintext header contains no note title, body, or labels.
- The header contains the journal UUID, exact checkpoint-base identity, and rooted-directory bookmark. Recovery resolves the bookmark and then validates directory identity; bookmark bytes or path equality alone never associate a WAL with a root. A stale bookmark may be refreshed only by creating the next WAL; the open WAL is not rewritten.
- WAL append and barrier synchronization use one serial durability lane independent of provider coordination. Admission is the main-thread model mutation plus insertion of the note or UUID/LSN deletion record in the existing pending set; it is not a write or durability claim. Normal typing captures and submits the object's latest UUID/LSN generation at the existing coalescing boundary. Resolver actions, external-editor handoff, lifecycle quiescing, and durability suspension force immediate asynchronous capture/barrier without blocking the main or provider lane.
- A pending-journal generation clears only after its exact immutable record leaves the short-write outbox, barrier synchronization succeeds, and the pending UUID/LSN still matches. A newer edit remains pending. A durability failure delivered while an AppKit mutation callback is already executing admits that callback once, then blocks later mutations and urgently submits all pending generations.
- Clean root closure synchronizes the WAL and settles affected note files. If the checkpoint-scoped dirty generation still equals the accepted-checkpoint baseline and the WAL is exactly header-only, it skips checkpoint installation; otherwise it installs and verifies one covering checkpoint. Either successful path closes the descriptor, deletes the local WAL, and synchronizes the Recovery Journals directory. Provider upload is irrelevant to this deletion.
- A crash before checkpoint verification leaves the WAL. A crash after verification but before deletion also leaves it; startup proves its valid records already represented or recovers them conservatively. No active/retained claim, coverage receipt, provider journal version, or upload retry checkpoint exists.
- Local Application Support loss removes same-Mac crash recovery but cannot delete provider note files. Another Mac never sees or recovers this WAL. This is an accepted product trade-off.

## Root-directory descriptor lock

- Apply `flock(LOCK_EX | LOCK_NB)` directly to the validated, already-open read-only, close-on-exec directory descriptor owned by `NVRootedDirectory`. The root session retains that owner. Do not create or use `.nv-root.lock`, lock a per-session WAL as a substitute, or silently fall back to another lock resource on failure or unsupported storage.
- This is exclusion among cooperating local NV writers opening the same directory object, not a provider/server lease or a reservation of its pathname. It is independent of positive root/WAL association and never replaces `NSFileCoordinator`, expected-snapshot checks, or publication fencing. Distinct local replicas on different Macs have independent locks.
- Retain the locked descriptor continuously from startup through recovery, editing, checkpoint installation/read-back, WAL close/removal and Recovery Journals directory synchronization, and final observer/operation teardown. On explicit override or unavailable-root termination, stop/drain the WAL lane and close but preserve the WAL as required before releasing rooted resources. Cancel/retry and provider upload delay are not permission to drop and reacquire a live session's lock.
- Same-object rename/move, catalog scans, URL/bookmark refresh, and controller refresh never close or unlock the owning descriptor. An authority handoff transfers its existing owner and local WAL obligations to the provisional successor without an unlock/reopen gap; the old incarnation cannot later close the transferred resources. Do not duplicate the owner for a second writer or issue `LOCK_UN` from a borrowed/duplicated descriptor.
- Observer cancellation handlers do not close the shared root descriptor. Final session teardown waits for vnode cancellation, presenter/FSEvents/notification removal, and owned operation completions before its single owner closes the descriptor and thereby releases the lock. A canceled close retains it. A controlled same-root storage restart transfers it until the successor is ready; a fresh process acquires its own lock normally.
- **Save Current Collection As…** independently locks the exclusively created destination before writing its bootstrap or exporting notes; the old root's retained resources are not released until its specified covered-WAL cleanup or evidence-preserving close completes. No lock or WAL is transplanted between different roots.
- A different directory recreated at an old pathname can be independently locked; it is not the old root. Replacement, revoke, and an unusable descriptor use the existing positive-continuity/association gates and explicit recovery choices, never silent reopening/retargeting. Directory locks do not supply missing identity evidence. The remaining real-system boundaries are recorded under `AV-16`.

## Execution and root coordination

- `NVRootSession` owns one root-directory `NSFilePresenter` and one serial provider operation queue for its callback ordering, coordinated current-visible/file-write work, FSEvents, and root-vnode events. The presenter observes useful root/direct-child/version/ubiquity changes, acknowledges every accommodation exactly once, and promptly invokes optional reader/writer relinquishment blocks with no reacquirer while NV has no temporary state to surrender. NV does not register per-note presenters. A new `NSFileCoordinator` is created for each logical operation; no coordinator accessor waits for upload or another network completion.
- The local WAL durability queue is independent and remains able to progress while provider work stalls. Completion blocks capture immutable values and the owning root session; every publication checks cancellation and the exact active incarnation.
- A verified move of the same rooted directory retains the root session, structural generation, rooted descriptor, WAL, and in-flight eligibility when any available provider item/domain pair also remains equal. Candidate locations come only from rooted, presenter, file-reference, or bookmark evidence and are revalidated with forward provider identity when available. Path-only change refreshes the root bookmark used for future WALs.
- A provider authority/account change fences the old incarnation, installs a provisional successor around the same rooted local resources, reattaches observation, and promotes only after authority and namespace revalidation. WAL durability may continue while provider publication is frozen.
- A vnode deletion/revoke, deletion accommodation, stale or failed location evidence, or provider lookup failure never establishes deletion. NV freezes provider publication and enters root-continuity-unavailable state unless positive evidence re-establishes the same rooted directory and, when present, provider pair. It never enumerates a provider domain or reverse-resolves an opaque item identifier to search for the root.
- WAL append/barrier failure or inability to validate the WAL/root association selects the durability reason in the single edit-admission gate. A root event triggers that validation and blocks editing only while the association cannot be positively re-established; provider/network uncertainty alone remains nonblocking while rooted identity and the local WAL stay valid. Already admitted records are drained urgently. Positive root/WAL revalidation plus a successful barrier resumes editing.
- Root-continuity-unavailable state is nonterminal. Retry reruns only the existing positive evidence checks: same-root evidence restores the session and changed-authority evidence takes the provisional-successor path. **Re-open from Disk** explicitly ends the old session, preserves its unmatched or unavailable host-local WAL as recovery evidence, and starts fresh. **Save Current Collection As…** constructs an exclusive unattached destination from the frozen live store; after its exact checkpoint and required file export are verified, it explicitly ends the old session and may retire the old host-local WAL. NV never automatically cancels a session because a root appears absent.

## Checkpoint and root-closing transaction

- `NVCheckpointTransaction` is the only checkpoint installer. Each instance is single-use and captures immutable serialized bytes, a fresh checkpoint ID, exact expected-current evidence, settled note-file/WAL obligations, and caller context.
- Existing-checkpoint replacement requires an exact retained predecessor witness: complete bytes plus the existing `NVFileObservation` captured in the same coordinated accessor and the current local `NSFileVersion.persistentIdentifier` when available; creation requires expected absence. The transaction rechecks every captured component inside the coordinated accessor immediately before mutation. Any observable mismatch invokes no replacement and returns `NVCheckpointInstallCurrentChanged` with one exact coordinated checkpoint-current witness. If that snapshot cannot be established, the result remains a no-write failure. The witness is host-local and root-session-scoped; it is never persisted or compared across machines.
- Installation uses the Foundation safe-replacement backend and the requirements in [Foundation Safe-Replacement Migration](Foundation-Safe-Replacement-Migration.md). Success requires exact byte read-back, successful decode, matching checkpoint ID, and the expected local version when available. Ambiguous possible installation authorizes neither publication nor WAL deletion.
- On `NVCheckpointInstallCurrentChanged`, NV decodes the exact current checkpoint into a detached complete candidate and reconciles its note set against the exact retained accepted predecessor and complete live note set. For UUID `u` and complete branch `X`, `u` is deleted in `X` exactly when the base contains `u` and `X` omits it; absence without base membership never infers deletion. Equal and one-sided changes collapse normally. A deletion against an unchanged note deletes the source UUID; a deletion/edit race relative to the same accepted predecessor keeps the source UUID absent and deterministically preserves the edited state as a conflict note. If the edited state has already become the accepted predecessor, a newer complete checkpoint's omission is a later base-relative deletion and may remove the last current-visible copy before the separate-file view receives the corresponding absence. Concurrent nondeletion changes use `NVMergedText` only with a trustworthy record base and otherwise keep the local note while deterministically preserving the current-checkpoint state.
- Before allocating or reusing any deterministic conflict identity, NV unions the live and captured checkpoints' retired deterministic conflict identity sets monotonically. A newly learned retirement participates in the same detached publication and exact-current retry. It is not general database metadata and is the only competing checkpoint metadata other than note states that is imported.
- The competing checkpoint's `NotationPrefs`, selection/UI state, and other database-level metadata are never imported or merged. The live session's values remain authoritative for the retry.
- Every published note or deletion mutation enters the existing pending WAL and separate-file sets. The same publication adds the retired-set union to live state and admits one UUID/LSN `DeletedNoteObject` retirement assertion for every identity in that union; this does not assert that this Mac deleted a live note. Reasserting the whole union is deliberate: the accepted predecessor has already ceased to be current, and the captured current checkpoint or a later concurrent replacement may omit identities known only by the other branch. All note, removal, and retirement records become host-local-WAL durable before another checkpoint attempt. NV then reruns the stable current-visible barrier, settles note-file/WAL obligations, serializes again, and uses the captured current checkpoint as the fresh exact expected predecessor. One root-closing operation performs at most one automatic merge-and-retry cycle; a second current change returns to the user-visible retry/override path without writing, while the durable retirement assertions preserve the complete merged set independently of whichever checkpoint is then current.
- After a crash during that cycle, startup reconstructs from the then-current complete checkpoint plus every valid positively associated local WAL. Any note, removal, automatic-preservation, or version-8 retirement work derived by that recovery reenters the ordinary pending WAL/file machinery and must cross its applicable local barriers before another checkpoint attempt. Prior settlement evidence is reusable only for the same exact captured current version; a newer current checkpoint requires a fresh recovery calculation and settlement. Accepting the current checkpoint after restart does not waive derived-work settlement or turn the interrupted cycle into permission for an unchecked write.
- Quit and ordinary folder switching first quiesce edits, drain admitted mutations, finish one stable current-visible reconciliation barrier while the presenter remains registered, settle note files and WAL, and invoke the single-use transaction for each permitted attempt. `applicationWillTerminate:` never rewrites the checkpoint.
- After local verification, local WAL cleanup proceeds immediately. Provider upload status may keep the existing uncommitted-change UI active, but failure, ambiguity, or user override cannot resurrect or delete a WAL whose local cleanup decision has already become durable.
- An unreadable/invalid current checkpoint, a second current change, or another failure before local checkpoint verification offers Retry, Cancel where applicable, or the existing explicit override. Override preserves the WAL for same-Mac startup recovery. A possible-install ambiguity also preserves it.
- No macOS-version-specific pause/upload/resume protocol, legacy upload-transition qualification, provider-version resolution coverage, represented-journal coverage, retained backlog, or cleanup-only checkpoint remains.

## User presentation

- Startup can show checkpoint materialization or local recovery progress. Delay does not alter correctness evidence.
- Routine provider delay is nonmodal. Offline and provider-unclassified status remain visible without blocking edits while rooted identity and the local WAL are healthy.
- **Conflicting Versions Available** is a persistent alert badge. Clicking it swaps a nonmodal `ConflictResolverView` into the editor split-view subview in place of `LinkingEditor`; the view contains a close **×**, **Conflicts** popup, read-only preview, **Use this version**, and **Save as new note**. The **×** may restore `LinkingEditor` at any time while per-version work continues in the background. Re-presenting the resolver automatically retries its parked items; only a fresh empty unresolved-version query clears the badge and declares the conflict resolved.
- A checkpoint-current note reconciliation during close is automatic and additive. If its exact input cannot be decoded or changes again, the close UI reports checkpoint contention and retains Retry, **Save Current Collection As…**, and the existing explicit override; it never offers preference or database-metadata merging.
- Root-continuity-unavailable status offers Retry, **Save Current Collection As…**, **Re-open from Disk**, or quit. Retry can only restore the session from positive same-root evidence; reopening, saving elsewhere, abandonment, or quit explicitly ends it. Reopening or quit closes but preserves an unavailable host-local WAL for later association; a verified Save As destination may retire it. A separate WAL durability suspension blocks edits while root/WAL association or local append/barrier durability is invalid and offers the same escape choices. Neither state is a persistent read-only mode.
- Diagnostics contain only closed operation identifiers, counts, and error domain/code. They never contain note text, filenames, paths, bookmarks, provider identifiers, account identity, or WAL contents.

## Migration, security, and compatibility

- Entering provider-managed operation uses the existing controlled restart: freeze edits, settle current work, verify an old-contract checkpoint, export plaintext files, verify an unchanged current catalog across export, install the unencrypted target checkpoint, create a fresh local WAL, and restart. The complete old checkpoint remains the restart marker; no migration ledger is added.
- Passphrase changes and encrypted **Save Current Collection As…** retain copy-on-write Keychain provisioning and exact checkpoint cutover. No transaction between Keychain Services and checkpoint replacement is assumed.
- Epoch 4 reads the core modern checkpoint. Modern NV recovers the legacy exact-name root WAL before creating a host-local WAL. No alias is maintained for epoch 4 and no compatibility is required for earlier unpublished epoch-5 formats.
- WALs and bookmark data are private host-local recovery artifacts. They use restrictive permissions and the same file-protection/backup-exclusion policy as other local sensitive Application Support data. Provider roots remain explicitly plaintext.

## Persistence-format appendix

### Checkpoint and base identities

- `FrozenNotation.checkpointID` remains exactly 16 UUID bytes in optional keyed-archive `NSData`; epoch 4 ignores it.
- The external checkpoint-base encoding remains tag `0x01` plus 16 UUID bytes, or tag `0x02` plus SHA-256 of exact unchanged epoch-4 checkpoint bytes.
- No provider-version ancestry or resolution-coverage field is written. Earlier unpublished `providerVersionRepresentationsV1` data is ignored if encountered.

### Pending deletions and retired deterministic identities

- `DeletedNoteObject` remains the UUID/LSN record used by the pending set and host-local WAL. An ordinary UUID records logical removal. A reserved version-8 UUID additionally records an idempotent retirement assertion; checkpoint-current reconciliation may emit that form solely to make the complete merged retired set locally crash-durable even when no live note was deleted on this Mac. Its legacy `syncServicesMD` field is decoded for compatibility but is empty and ignored for modern deletion decisions; it never controls retention or purge. No filename, digest, filesystem identity, provider identity, path, or new record tag is added, and non-keyed epoch-4 decoding remains supported.
- A complete modern checkpoint serializes no general deletion tombstones. Its complete note-set omission represents every covered ordinary deletion. After exact checkpoint verification, the corresponding pending removal records are covered and disappear with the retired WAL. A decoded legacy checkpoint deletion set is normalized to note absence and is not serialized forward.
- RFC 9562 version-8 note UUIDs are reserved for the two specified deterministic conflict-identity algorithms. Deleting such a note admits the ordinary UUID/LSN removal record and also inserts its UUID into `FrozenNotation.retiredDeterministicConflictIDsV1`; replay of that record restores retirement from every valid positively associated modern WAL, while only exact-base replay may apply its deletion meaning. Normal, imported, and unmatched-file notes use random version-4 UUIDs.
- `retiredDeterministicConflictIDsV1` is an optional keyed-archive `NSData` containing unique UUIDs as lexicographically sorted concatenated 16-byte values. Its length must be a multiple of 16, every entry must have the RFC variant and version-8 bits, and ordering must be canonical; malformed data makes the checkpoint invalid rather than weakening non-recreation. Epoch 4 ignores the unknown keyed field.
- The retired set is monotonic and is unioned during checkpoint-current reconciliation. Duplicate retirement is idempotent, and its payload growth is exactly 16 bytes per distinct retired deterministic UUID before keyed-archive overhead. It contains no LSN, title, body, filename, provider identity, or resolution member. Membership only prevents a deterministic candidate from being reused or recreated; it never suppresses or deletes an independently visible plain-text file. General note UUIDs never enter this set, and no garbage-collection rule is required for the initial format.
- After an ordinary deletion is checkpoint-covered, no permanent UUID denial record remains. If a later complete checkpoint or visible file presents note content that cannot be classified as the deletion side of the exact retained base, NV preserves it as current input rather than silently suppressing possible work. A visible unmatched file receives a fresh random UUID; this rule never authorizes deletion of that file.

### Unresolved-version recovery identity version 1

- The 32-byte recovery key is SHA-256 of ASCII `NV unresolved recovery key\0v1\0`, the source note's 16 UUID bytes, the canonical-body byte count as unsigned 64-bit big-endian, and the NFC-normalized UTF-8 body bytes, in that order.
- A slot digest is SHA-256 of ASCII `NV unresolved recovery slot\0v1\0`, the 32-byte recovery key, and the nonnegative slot ordinal as unsigned 64-bit big-endian. The candidate note identity uses the leading 16 digest bytes with RFC 9562 variant and version-8 bits set.
- Implementations pin byte-exact vectors. Title, labels, extension, filename, provider identifier, and collision suffix never enter either digest.

### Automatic conflict-preservation identity version 1

- Checkpoint-current reconciliation and base-mismatched local-WAL salvage use one deterministic identity for each differing nondeletion note state. Routine current-file reconciliation and note-file replacement recovery retain ordinary conflict-note creation/import identities and never apply this algorithm's suppression policy. Explicit unresolved-version disposition retains its separate recovery-key/slot rules.
- The digest is SHA-256 of ASCII `NV automatic conflict preservation\0v1\0`, the source note's 16 UUID bytes, the NFC-normalized UTF-8 title length and bytes, the NFC-normalized UTF-8 body length and bytes, and the label count followed by each NFC-normalized UTF-8 label length and bytes after sorting labels by their encoded bytes. Every length and the label count is unsigned 64-bit big-endian. The candidate note UUID uses the leading 16 digest bytes with RFC 9562 variant and version-8 bits set.
- Dates, LSNs, selection, formatting attributes, filenames, collision suffixes, checkpoint/WAL identities, and filesystem/provider metadata do not participate. An exact live candidate is reused. A changed live candidate or a UUID in the retired deterministic identity set is never overwritten or automatically recreated; retirement records that the earlier preserved note was subsequently deleted. Any other UUID/state inconsistency fails closed rather than allocating a random duplicate. Implementations pin byte-exact vectors.

### Local WAL filename and header version 2

- The filename is `Interim Note-Changes.<journalID>` with canonical uppercase UUID text.
- Header integers are big-endian. The layout is: 8-byte magic `NVJNL5\r\n`; `uint16` version `2`; `uint32` total header length; 16 journal UUID bytes; `uint16` checkpoint-base length and 17/33 base bytes; `uint32` bookmark length and bookmark bytes; trailing `uint32` zlib CRC-32 over all preceding header bytes.
- Readers reject a header shorter than its fixed fields, a total length beyond the file, bookmark length over 1 MiB, a noncanonical base, UUID/name mismatch, unsupported version, or CRC mismatch. Record framing begins exactly at `headerLength` and retains the existing record format.
- Version 2 is the first supported modern host-local layout. Unpublished draft version-1 headers and current-host claim shapes have no compatibility requirement.

- [CrossMachineCurrentVisibleSafety.tla](tla/CrossMachineCurrentVisibleSafety.tla) composes two independently observing hosts across one mutually stale shared-base edit round, the measured delete/edit current-visible ceiling, exact-current checkpoint writes, and retired deterministic identity propagation. Its stronger global branch-recoverability invariant applies only to concurrent nondeletion bodies and is conditional on a displaced current body remaining current or Apple-reported unresolved; the delete/edit configuration deliberately disables that assumption and does not assert recovery of an edited body after provider deletion hides it. Canonical source absence and retired identities are monotonic, and a host that has accepted the canonical checkpoint must honor both; a stale host may temporarily retain a retired identity but cannot publish it through the exact-current checkpoint gate. The separate bounded convergence configuration proves stable host-state equality only for the single-round concurrent-edit scenario under weakly fair enabled delivery, reconciliation, observation, and publication.
- [MultiRoundCrossMachineSafety.tla](tla/MultiRoundCrossMachineSafety.tla) uses causal decision tokens for two hosts and two edit rounds each, with independently ordered current-file/checkpoint delivery, checkpoint publication only after the publishing host's file obligation settles, and permanent loss of one host only after its durable work is provider-published. TLC checks bounded token recoverability and canonical-checkpoint monotonicity under the per-displacement Apple-retention assumption; it does not prove literal body recovery, Apple behavior, arbitrary rounds, convergence, or provider liveness.
- Existing credential-cutover and safe-replacement requirements remain applicable. The current `StorageTransitionSafety` is the host-local-WAL refinement; its former shared-WAL revision is not implementation authority. Models for shared provider journals, active/retained claims, all-version reconciliation/recovery, upload-qualified cleanup, and automatic/provider-wide version resolution are retired design history and are not implementation authority.
- Models assume truthful atomic replacement, directory synchronization, positive bookmark/root-identity validation, WAL checksums/decoding, advisory locking, coordinated current snapshots, `NSFileVersion.URL` remains a readable immutable representation during its coordinated preview, and Apple honors successful `resolved = YES` updates in a later unresolved query. For concurrent nondeletion bodies only, the stronger cross-machine displaced-body property additionally assumes that a stale-base publication displacing a different current body leaves that body current or disclosed unresolved; without that observation NV makes no stronger no-silent-branch-loss claim. The delete/edit model assumes no Current/unresolved disclosure after provider deletion because that is all the current-visible algorithm can consume; it makes no claim about undisclosed provider storage. Failure to establish an environmental input removes the corresponding success action; it never proves root loss or enables destructive behavior.
- Concrete identity-tier uniqueness, identity loss/fallback, `DeletedNoteObject` compatibility fields, compact retired-set encoding, WAL coalescing, presenter conformance, and Objective-C ownership remain implementation/contract tests; they refine existing model inputs without adding a provider-history or deletion-watermark assumption.
- Safety models assume no provider/network fairness. The bounded convergence configuration's explicit weak-fairness premise is a model condition, not proof that a real provider or network supplies it. Passing TLC does not prove Apple API behavior, Objective-C ownership, filesystem identity, bookmark portability, UI text, diagnostics redaction, or epoch-4 compatibility.
