# Pre-implementation gap report: iCloud Drive sync spec + proposal 4

Status: retired historical review of proposal 4. The report's references to the
"current" spec, ADRs and source lines describe that review's starting snapshot.
The adopted [proposal 5](../impl-proposal-5/README.md),
[specification](../iCloud-Drive-Support-Spec.md) and
[implementation roadmap](../impl-proposal-5/plan/swift-storage-implementation-plan.md)
define current requirements and integration gates. Retain these findings for
source/migration comparisons alongside the [retired proposal](README.md).
The earlier `blockers_and_open_design.md` mentioned below was removed before
this audit; its reference records the review's historical context.

**TLDR:** The spec/proposal/ADR/TLA+ set is unusually complete — byte formats, identity algorithms, the checkpoint-current merge, the resolver's four-stage failure table, and the forward-provider matrix are all implementable as written, and the earlier gap review in `docs/impl-proposal-4/blockers_and_open_design.md` has been substantially addressed in the current README (detached decision kernel, `NVNoteFileWriteIntent`, presenter relinquishment, tombstone lifecycle via checkpoint-omission, WAL admission boundary, filesystem-identity tiers, test seams via the pure matrix function). That blockers file is now stale as a review of the *current* proposal. What remains, walking the implementation sequence as a builder, is below. The recurring theme: the proposal is strong on *provider-facing* semantics but repeatedly says "reuse the existing X" for *AppKit/lifecycle* machinery that either doesn't exist, is dormant, or actively conflicts with the new design — and a few of those reuse claims hide product decisions nobody has made yet.

## Tier 1 — I would have to invent structures not in any document, or make undocumented product decisions

**1. The fate of DeletionManager's external-deletion confirmation panel is unaddressed — a silent product decision.** Today, when reconciliation finds that note files vanished externally, `_commitDirectoryTransaction:` calls `reconcileVerifiedExistingNotes:deletedNotes:` ([NotationDirectoryManager.m:439](../../NotationDirectoryManager.m#L439)), which shows a Restore/Delete panel ([DeletionManager.m:200](../../DeletionManager.m#L200)). Under current-visible sync, *another Mac's ordinary deletions arrive as exactly this signal*. Neither the spec's decision matrix, the proposal, the ADRs, nor `CONTEXT.md` mention DeletionManager at all (I grepped). Either the panel stays — and every cross-machine deletion prompts for confirmation on every other Mac, which defeats routine sync — or it's removed/suppressed for provider-managed roots, which quietly deletes an existing safety net against accidental Finder/data-loss deletions and is a real product decision that deserves its own ADR. Related legacy runtime paths with the same problem: `handleJournalError`'s alert + `exit(1)` ([NotationController.m:640](../../NotationController.m#L640)) and `checkJournalExistence` must become the non-fatal durability-suspension state, but nothing says what the user sees when the gate closes mid-session.

**2. The edit-admission gate has no AppKit integration point — typing is currently learned of *after* it mutates the model.** The spec and proposal define admission precisely at the model level ("Acceptance mutates the live model and inserts the record… performs no I/O"), and require that when the gate is closed "NV stops admitting new edits," with undo/redo "rejected before asking `NSUndoManager` to transfer or invoke the stack entry." But NV today has no pre-mutation hook for typing: edits arrive post-hoc through the editor delegate/undo-manager-did-change notifications ([NoteObject.m:1817](../../NoteObject.m#L1817)), and there is no `shouldChangeTextInRange`-style veto anywhere. I would be inventing: the interception point for keystrokes; what a blocked keystroke *looks like* (swallowed? read-only editor? beep?); how this interacts with IME marked-text composition mid-gesture; how `NSUndoManager` group-by-group veto works when undo coalesces typing; and what happens to a paste/drop that's half-applied when the gate closes. This is the single most user-visible structure in the design with zero reusable precedent in the codebase.

**3. The detached decision function's input/output schema is under-specified for what the matrix actually needs, and two matrix rows have no existing implementation.** The proposal's field list — "the two catalogs, selected file snapshots, root/session and dirty/structural generations, and affected live-note UUID/LSN/name/base values" — omits state the current decision phase demonstrably reads from live objects: each note's `shouldWriteToFile`/pending-write membership (today `_stageOrAddDeletedNotes:` consults `pendingFileWrites` specifically to avoid classifying NV's own owed write as an external deletion, [NotationDirectoryManager.m:406](../../NotationDirectoryManager.m#L406)), title/labels/content/format for merge decisions, and the last accepted per-note file snapshot. Concrete filename association and `NVMergedText` behavior require implementation tests; an abstract decision table does not supply the algorithm. Concretely missing rows: "independent rename and content edit → combine" and "conflicting renames" (today's tiers attach a rename only when *content is unchanged* — `processNotesAddedByContent:` requires content equality — so a remote rename+edit currently degrades to delete+fresh-import, losing UUID continuity and, per item 1, tripping the confirmation panel). Also unspecified: how rename combination treats an extension change (which implies a format change) and case-only renames in the case-insensitive namespace; and the commit-side mapping "UUIDs back to still-matching live notes" when a prepared result references a note that was deleted between decision and the (passed) fence check. This is the most safety-relevant data structure in the project, and the proposal describes its shape, not its contents.

**4. Startup becomes an asynchronous state machine with presentation states no document defines.** Today startup is synchronous and app-modal with exactly three outcomes (succeed / choose-folder / quit, [AppController.m:402](../../AppController.m#L402)–437), possibly blocking on a modal passphrase sheet mid-load. The new design requires waiting on checkpoint materialization with "app-owned progress when Apple supplies meaningful progress" — but the only Apple mechanism for ubiquitous-download progress is `NSMetadataQuery`-based KVO, which ADR-0012 and AV-12 exclude from required paths entirely. So the progress mechanism itself is an invention (bounded status polling of `NSURLUbiquitousItemDownloadingStatusKey`? presenter callbacks?). Also undefined: what the window/note list/empty view show during materialization, recovery, and WAL replay (is search interactive? is the table empty-with-spinner?); how the modal `PassphraseRetriever` interleaves with the async flow; and how "Work Offline" / "Create a New Notes Collection Here" / rebuild-decoder-choice sheets chain off it. The outcome *table* is thorough — the *presentation* is not.

**5. Quit-flow integration has a third termination protocol to invent, and the "existing" quit-wait UI is dormant Simplenote code.** The proposal says to keep "`SyncSessionController`'s existing uncommitted-change status, waiting, error, cancellation, and explicit quit-override presentation." That class's session registry is hard-gated behind `#if USE_SIMPLENOTE` ([SyncSessionController.m:60](../../SyncSessionController.m#L60)) — compiled out in the current build — and its wait mechanism is coupled to session-push callbacks and an `NSTerminateCancel` + re-terminate dance ([AppController.m:2132](../../AppController.m#L2132)–2178), while the external-editing leg uses `NSTerminateLater`. The new close sequence (quiesce → drain → stable current-visible barrier on the provider lane → WAL barrier → checkpoint transaction → possible merge-and-retry) is asynchronous provider work that must fit into `applicationShouldTerminate:` — a third leg, with the added wrinkle that the spec only pins "applicationWillTerminate: never rewrites the checkpoint" without saying which phase owns the close. Hosting all this in `SyncSessionController` means inventing a pseudo-session or generalizing the class; neither shape is specified.

**6. `NVRootedDirectory`'s threading contract is undefined once writes leave the main thread.** The proposal confines reconciliation and note-write work to the provider lane, but `NVRootedDirectory` (mutable catalog buffers, cached volume UUID, descriptor state) is called today from many main-thread paths outside the write flow: file import/open (`notesWithFilenames:`/`openFiles:`), export (`ExporterManager`), AlienNoteImporter, trash-relocation, case-collision checks, scratch-file external editing. I'd have to invent either whole-object confinement to the provider queue (migrating every caller) or an internal serialization discipline — under MRC — and the documents are silent on which. The code itself flags the neighboring hazard: the `kFSEventStreamCreateFlagIgnoreSelf` comment ([NotationDirectoryManager.m:322](../../NotationDirectoryManager.m#L322)) says the flag is valid "only while note writes and directory scans remain main-thread serialized."

## Tier 2 — scenarios the spec didn't consider

- **`.nv-root.lock` lives in the provider namespace, and the spec only considers it as a local lock.** On a provider root it can be evicted (Optimize Mac Storage), so the very first startup action — `open()` + nonblocking `flock` — can block on materialization or fail on a dataless placeholder, before anything else in step 1. Two Macs creating it concurrently can also produce an iCloud conflict/versions on the lock file itself. The spec notes "moving the lock host-local is outside this decision" but never discusses provider behavior toward it.
- **Conflicts on notes that aren't selected are undiscoverable.** The badge probe runs only on selection change, successful reconciliation of the *selected* file, and presenter version callbacks "for the selected visible note." A conflict arriving on an unselected note shows nothing anywhere (no list-level indicator is specified), and the spec doesn't say whether that's deliberate. Related unspecified resolver lifecycle: what happens when the user switches notes while the resolver is presented (auto-dismiss? per-note re-present?), and how members are named in the popup (`NSFileVersion` objects have no titles — the PDF layout is the only reference).
- **Decoding a competing checkpoint must be headless.** The checkpoint-current path decodes a full `FrozenNotation`, whose existing decode path can raise the modal `PassphraseRetriever`. Provider roots are plaintext, but `CKPT-01` machinery isn't provider-gated — a non-provider encrypted root can hit it too, and a quit-time close must never spawn a password sheet.
- **Runtime loss of the Application Support WAL file.** The spec accepts Application Support *loss* as a durability trade-off, but while a session is open, the held descriptor keeps appending happily to an unlinked file — crash protection silently disappears and no runtime existence check exists in the new design (today's `checkJournalExistence` → alert + `exit(1)` is the behavior being replaced). Detection and UX are unspecified.
- **Quit during an in-flight resolver disposition.** "No pending resolution intent survives launch" covers relaunch, but whether quit-drain waits for (or abandons inside) the coordinated `resolved = YES` accessor of stage 3 isn't stated.
- **Progress for the blocking plaintext conversion** (potentially thousands of exported files) is unspecified — same mechanism vacuum as item 4.
- A small vocabulary vestige: the spec's base-mismatch rule mentions WAL "settings records," but v2 WALs never contain settings records and legacy journals are note/deletion records only; worth a clarifying edit so an implementer doesn't go hunting for a record type that cannot exist.

## Tier 3 — minor

Coordinator option selection per operation (catalog read vs. note read vs. write-for-merging vs. write-for-replacing) is scattered/inferable but never tabulated. Many new UI strings arrive with no localization plan despite seven `.lproj` languages. Whether "Use this version" being undoable (it goes through the ordinary mutation path) is intentional is unstated. Modal-vs-sheet presentation style for the new sheets is unspecified (existing storage dialogs are app-modal). Structural-generation increment triggers for undo-of-rename/label-only changes need a decision table when implemented.

## What I verified as solid (calibration)

For the record, these claims in the documents check out against the code and would *not* require invention: `NVFileObservation` exists ([NVRootedDirectory.m:265](../../NVRootedDirectory.m#L265)); the expected-snapshot CAS, three write intents, and typed write results exist and are production-used (though not yet for checkpoints — `NVCheckpointTransaction` is entirely new, as the proposal implies); the identity tiers (volume-qualified document ID → session file ID → content) already exist; the double-catalog fence exists; the pending sets, LSN machinery, and 2.7s/15s coalescing cadence exist; `makeNoteDurableForExternalEditing:` exists as the synchronous boundary the proposal converts; and the WAL record codec (framing/CRC/per-record encryption/shared zlib) is exactly what v2 retains. The TLA+ README's model boundaries are honest about what remains "implementation obligations," and my Tier 1 items 2–6 all sit precisely in the gaps those boundaries declare.
