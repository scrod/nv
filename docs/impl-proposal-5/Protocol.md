# Segment protocol and note semantics

Part of [proposal 5](README.md). This is an application protocol over ordinary files, not a transaction protocol implemented by the provider. The provider may deliver any subset in any order, repeat it, evict its local copy, or remain unavailable. Only locally retained, validated evidence supplies durable knowledge.

## Reading the terminology

Use the grouped [glossary](../../CONTEXT.md) as a reference, not a prerequisite reading list. Start with these distinctions:

| Layer | What it describes | What it does not establish |
| --- | --- | --- |
| Collection and note birth | Which logical history and creation a record belongs to | Authority over a physical folder or file |
| Operation and action record | A recorded change, and the meaningful action/undo context grouping changes | One file per operation or action |
| Segment and dependency closure | Exact immutable transport bytes and the evidence needed to interpret them | That every remote branch has arrived |
| Current, derived merge, current materialization | A computed editable value or an acceleration representation of known history | Replacement of every known alternative or permission to discard history |
| Projection and physical observation | A separate note file and locally verified evidence about its current installation | A permanent cross-Mac file identity |

“Graph” means records connected by explicit references, not a timestamp-sorted log. An ancestor is reachable by following a specified relation backward; concurrent records have neither as the other's ancestor under that relation. Maximal records have no later descendant in the evaluated set. A **frontier** names those maxima; an **antichain** means none of its members is an ancestor of another. Always state which records, relation and evaluated history are meant:

| Relation | Question answered | Must not substitute for it |
| --- | --- | --- |
| Operation causal parents | What operation history did this change observe? | Note supersession |
| Note predecessors | Which note revisions does this value replace? | Every alternative known to the author |
| Action `scopeParents` | Which actions were represented in this undo scope when the action was authored? | Receipt order or the originating Mac's stack |
| Compensation targets | Which actual action/effect does this Undo or Redo reverse? | Every scope parent, or always the original forward action |
| Snapshot retention parents | Which accepted snapshot-object closures must remain retained under this root? | Represented note history, reconstruction winner or deletion permission |

For example, NV can know incompatible revisions A and B while Current represents only A. Editing Current produces E that knows both but replaces only A; B remains an alternative. The operation frontier can advance to E without making B superseded. Likewise, observing an Undo through `scopeParents` is not the same as targeting it with a Redo. These distinctions are exercised separately by [SegmentMergeSafety](../tla/SegmentMergeSafety.tla) and the shared [CausalUndoRules](../tla/CausalUndoRules.tla), with execution checks in [ConcurrentUndoExecutionSafety](../tla/ConcurrentUndoExecutionSafety.tla).

Keep similarly named boundaries separate. **Atomic model publication** makes a prepared live result and its indexes visible together; **provider publication** copies an immutable object into the repository. **Root** can mean a physical directory or a snapshot-root object; qualify it. A **projection descriptor** describes intended file bytes, a **merge descriptor** names derived inputs/results, and a **bootstrap/key descriptor** anchors collection/key information; an OS **file descriptor** is an opened filesystem handle, not any of those records. A **conflict recovery key** is deterministic copy identity, whereas an **encryption recovery key** is a secret. An **Undo scope**, **disposition scope** and **envelope scope** constrain different things; matching one never grants authority in the others.

## Identities and the causal graph

Use these identities for different purposes; never substitute one for another:

| Identity | Scope and source |
| --- | --- |
| Collection ID | Random 128-bit bootstrap identity; not physical root identity |
| Writer epoch | Fresh random 128-bit namespace on each editable process session; never resumed after restart/backup restoration |
| Segment ID | SHA-256 of the exact sealed envelope, including ciphertext/tag in encrypted mode |
| Operation ID | SHA-256 of the canonical operation bytes, including its random 128-bit operation nonce, kind, target, full payload, and parent operation IDs |
| Action ID | Random 128-bit identity of one user-meaningful action group, independent of segment boundaries; exact retried bytes keep it |
| Action origin ID | Fresh random 128-bit provenance ID for one editable collection session in a process; stored in each authored `ActionRecordV1`, never used as private ownership, root authority, membership, or authenticated device attribution |
| Note birth | Ordinary 128-bit note UUID allocated at creation; never reassigned to represent restoration after deletion |
| Local generation | Existing note UUID/LSN and operation/root generation captured at an asynchronous boundary; not a cross-Mac clock |
| File observation | Rooted local expected snapshot; expires on replacement, root invalidation, or a failed recheck |

An operation names its immediate causal parents and, where relevant, its note-specific predecessor revisions. Following causal-parent links transitively represents what the operation observed; following note-predecessor links instead establishes supersession. Wall time is display metadata only. Concurrent operations are those for which neither is an ancestor of the other. Retain parent information even when two payloads happen to contain identical text.

**Causal knowledge is not note supersession.** A `Put` supersedes only its explicit note-predecessor set, not every revision in its causal ancestry. An ordinary edit captures Current's represented revision IDs as predecessors, even if the applied frontier includes unresolved alternatives. Body/title/labels/format changes, programmatic edits, external-editor returns and ordinary historical field recovery obey this same rule. Editing Current A to A′ leaves incompatible B and all separate conflict notes untouched; only explicit scoped resolver actions acknowledge alternatives. When Current is an equal-value state or a valid automatic merge, its represented input set is the predecessor set, not additional unresolved heads. Revalidate the captured Current/generation before admission; do not widen its scope when remote work arrives.

Each segment contains ordered operations and an exact dependency-locator table. An intra-segment parent refers backward to an earlier operation index; an external parent references an operation ID and the immutable segment locator containing it. For operation hashing, expand either representation to canonical parent operation IDs; physical locators/indices are transport encoding, not operation identity. External locators never refer to the not-yet-created segment itself. Operation identity does not include the enclosing ciphertext hash, so there is no hash cycle. Repackaging is not needed initially; a duplicate operation disclosed in another valid segment still has one logical effect.

The current applied frontier is the set of maximal operation IDs in the history incorporated into the live model, not all received/parked objects, accepted remote history awaiting model publication, or a maximum sequence per writer. A segment writer captures that frontier plus relevant pending predecessor operations. Dependencies can span writers. Holes cannot be skipped by observing a larger sequence; counters are useful for diagnostics and discovery hints only. Arbitrary frontier growth is an acknowledged v1 cost. Do not replace explicit parent sets with an unsafe high-water mark to shrink an overflowing object.

## Operations and value encoding

The [first-save encoding/runtime contract](plan/first-save-reopen-contract.md) supplies the initial concrete record subset. Its working Swift codec preserves exact UTF-8 title/body and label-token spellings, with raw-byte ordering/equality, and finite binary64 display seconds from the legacy 2001 reference date. Stored label tokens are distinct from the host's case-insensitive label lookup index; ordinary membership merging uses exact stored tokens, while the explicitly versioned conflict-identity transformations retain their NFC rules. The first-subset value/operation/action/payload, envelope, descriptor and initial-snapshot codecs have executable fixtures, and initial-import validation now connects those bytes to their complete initial history. General causal/Current validation, later variants and the storage runtime remain distinct implementation gates; authenticated/decoded bytes alone cannot supply acceptance. A decoded operation's computed ID is not acceptance: its external reference claims and whole action/dependency closure still require validation.

The initial vocabulary is small:

| Operation | Required content and effect |
| --- | --- |
| `Genesis` | Collection profile, required codec, protocol/merge-policy versions, bootstrap/import identity, and expected initial note-set count/value digest; establishes the collection, not an editable empty fallback |
| `ImportComplete` | Initial import's exact count/value digest, with parents covering all import batches; must match the genesis commitment before initial editable bootstrap |
| `Create` / `Import` | Fresh ordinary birth, complete note value, causal parents; explicit Import as New or automatic ordinary-file admission under the decision matrix below. Neither derives identity from a path/hash nor uses a timeout as proof of newness |
| `Put` | Existing birth, complete resulting note value, exact predecessor revision IDs and causal parents; body/title/labels travel together |
| `Delete` | Target birth and causal parents, including every revision the deleting user actually observed; removal is logical, not a filesystem command |
| `RecoverCopy` | Source/conflict recovery key, selected deterministic slot, complete copied note value, and exact source revisions being represented; creates or references the one equivalent recovery birth |
| `RetireConflict` | Deterministic recovery identity explicitly deleted by the user; monotonic even if the original conflicting state arrives again |

Segments also carry canonical `ActionRecordV1` values describing their user-action groups; these are not executable invocations or a second stream of note mutations. User-action member operations include their action ID in their hashed bytes; the record lists their operation IDs, avoiding a record/member hash cycle or dual membership. Their exact membership, before/after references, and compensation references are validated with the operations and covered by the same envelope. An action ID collision with different membership/metadata is invalid, not a new undo entry.

A local UI action may atomically produce several operations in one segment: for example, deleting a deterministic conflict note includes both its `Delete` and retirement, or saving an NV conflicting branch includes its copy and scoped causal disposition. An Apple copy records the note/action only: its ephemeral provider-member disposition is never serialized as a protocol operation or portable identifier. V1 requires an action group's operations and complete action record in the same segment; multiple complete groups may share a segment. Split an oversized bulk operation into disclosed, independently undoable batches before admission, not an incompletely applied cross-segment transaction. A segment is validated completely before any of its operations are published to the live store. A damaged member rejects the segment; do not salvage a valid-looking prefix.

For v1, changes contain complete resulting note values, not diff-match-patch programs that must execute during recovery. Batching still encodes incremental *collection changes*: unchanged notes are absent from an ordinary change segment. Exact parent history remains required even though the changed body is self-contained. Do not discard creation/deletion/restore or completed action boundaries while coalescing edits. Repeated pending typing edits within one open saved-edit group may be coalesced before any dependent operation or durable capture has fixed their identity; a later distinct action cannot consume that group's before/after evidence.

Use a versioned length-prefixed binary value codec, not provider-supplied `NSKeyedUnarchiver` object graphs. Define unsigned big-endian integers, fixed raw identifier widths, operation tags, explicit byte lengths/counts, and lexicographic ordering for sets. Reject duplicate keys/IDs, overflow, cycles, forward intra-segment parents, unknown mandatory fields, incorrect content hashes, conflicting values under one operation ID, and extra trailing bytes. An unknown required version parks the collection branch as unsupported; it is not an empty change.

Note values include title, exact body/content bytes, labels, creation/modification display dates, and a declared content format. Plain text uses UTF-8 with strict decoding. Preserve the user's body rather than silently normalizing its stored spelling; NFC normalization is specifically part of recovery identity/comparison. Rich text is a bounded RTF value plus any explicitly supported embedded data, retained byte-for-byte as received, and decoded through the reviewed rich-text import path. No external resource fetching or arbitrary archived classes are allowed. Rich bodies are opaque to automatic textual merging. Codecs must round-trip every supported migration input; unsupported attachments or an object exceeding the [envelope limit](Encryption.md#common-object-envelope-version-1) require a disclosed conversion/export choice, not truncation. Freeze vectors and exact field offsets before production writes.

## Admission, sealing, and durability without a second WAL

The names below are not one universal timeline. A **local** change is admitted into the live store before capture, sealing and the complete local durability barrier; an **incoming** object can be received and installed locally yet remain parked until its dependencies and validation are complete, before fenced model publication. “Applied” therefore does not by itself imply durable for a pending local edit, and “installed” does not by itself imply applicable for an incoming child. Sealing fixes exact bytes; acknowledgment additionally requires the full local barrier, including the retained-history pin. Projection installation and provider upload are separate outcomes. See [ImmutableSegmentDurabilitySafety](../tla/ImmutableSegmentDurabilitySafety.tla), [SegmentDeletionSafety](../tla/SegmentDeletionSafety.tla) and their [abstraction boundaries](../tla/README.md#reading-model-names-against-the-specification).

```text
main-thread admission → capture immutable operations → encode/seal in memory
    → private SQLite transaction: exact bytes + complete accepted history
        + retained pin + dependency wakeups + exact operation links
    → qualified durable commit
    → exact-generation completion              ↘ asynchronous provider publication
```

The live model and existing pending UUID/LSN sets remain the admission mechanism. Mutations do not wait for provider work and never archive on the main thread. Preserve the existing scheduling baseline: capture after 2.7 seconds without another edit, plus a 15-second timer from the first pending edit that further typing does not reset, and forced capture for lifecycle or externally visible durability obligations. These are scheduling targets, not hard deadlines, input-composition termination, or per-keystroke power-loss guarantees. Keep semantic undo/action grouping separate from capture scheduling and follow the [AppKit input boundary](../iCloud-Drive-Support-Spec.md#input-and-content-scope); no custom draft buffer is required by this protocol. An admitted but not yet durably captured keystroke has the same explicit pending window as today. The retained pin is required private metadata in the atomic acceptance transaction, not a second note-value log. A failed or ambiguous commit leaves the generation pending until exact identity lookup resolves its outcome.

Keep one local sealer in flight per collection. This bounds buffers, simplifies dependency ordering, and avoids a second mutable active log. Edits arriving during encoding remain pending as newer generations. A completed capture clears only the UUID/LSN generations it actually covers, never a newer edit or delete. Admission failure and durability failure are distinct; an already admitted change remains visible and recoverable through Retry or an explicitly scoped current-notes recovery export if local persistence fails. A repository-only Save As is not evidence that pending live text was saved.

**The local barrier covers the entire causal dependency closure.** Every parent must already be durably retained locally or precede its child within the same atomically installed segment. A durable child whose parent exists only in RAM cannot be acknowledged, checkpointed, used to remove a file, or exposed as a durable external-edit result. The [crash model](Verification.md#model-results) found precisely this failure. Enforce the same closure before accepting a remote operation into durable live state; storing an incoming child before its parents is allowed, applying it is not.

The [LocalStore contract](LocalStore.md) maps the complete local barrier to a qualified SQLite commit. Retain exact immutable bytes, validated acceptance membership, pin advancement and dependency-ready work atomically. Stored-but-parked objects remain distinct. Equal exact bytes and operation identities are idempotent; contradictory bytes preserve evidence and fail. Ambiguous completion is retried by checking that exact committed identity, not resealing changed contents. Exclusive final-name/file/directory barriers still apply to provider objects, not to individual private BLOB rows.

Only complete committed objects participate in recovery. SQLite discards or recovers its own uncommitted transaction state; it is not an NV operation stream. Retaining pending text until the barrier closes this gap without a second NV WAL format. Immutable segments remain the recoverable history; SQLite's private journal never becomes transport.

Recovery and publication eligibility come from exact accepted history and its durable dependency closure, never from a prior process's callback, upload flag or undo cursor. A committed segment whose UI completion was lost must still reconstruct its effects and become publishable. The ready queue is transactionally maintained correctness state: acceptance requeues all affected dependents; restart drains startup-required work before editable completion, while independent optional snapshots remain queued for background processing. Healthy launch reuses validated private acceptance, while newly applicable or on-demand object reads verify exact evidence. The older file-installer models establish surrounding obligations, not SQLite refinement; see [the local mapping](LocalStore.md#validation-and-remaining-implementation-work).

## Immutable provider publication and reception

Publish only exact locally durable envelopes and descriptors. `NV Data/v1/segments/<writerEpoch>/<sequence>-<segmentID>.nvseg` is final immutable storage beneath the visible ordinary `NV Data` directory. Exclude that reserved directory from note-file ingestion and reject symlink/non-directory or foreign-content bootstrap collisions without overwriting them. Do not set hidden flags or maintain a second hidden alias. Create owned ciphertext/public-byte staging at the provider root, coordinate the final new-object installation, and verify exact bytes. Use exclusive creation, not an expected-current replacement helper intended for mutable note files. Parent-before-child scheduling is a latency optimization, never a receiver correctness assumption.

An existing equal object is a retry; two different envelopes with the same writer/sequence have different hash names and both must be considered. Restored device copies generate new writer epochs. A genuine complete-locator collision or hash mismatch is an integrity error; choose no winner and do not destroy either available source. Provider-created conflict duplicates may have changed filenames: bounded inspection can recognize a valid envelope and deduplicate by its authenticated/checked identity. Never trust the filename instead of the envelope or traverse paths/symlinks supplied by it.

The [rooted physical boundary](plan/phase5/02-immutable-files-validation.md) renders canonical names from checked identities and retains every traversed parent descriptor. It writes a 0600 owned stage at the root, verifies and synchronizes it, performs native no-overwrite rename, verifies the final descriptor/bytes, synchronizes nested namespaces bottom-up and performs the final hardware-cache request on Darwin. Equal preexisting bytes undergo final verification and all barriers too. Add-only directory creation preserves a competing entry and revalidates its kind/identity. Unsupported primitives produce a capability failure; partial protocol output remains incomplete repository work.

The install result is verified, not-installed or uncertain, with separate protocol-namespace effect and retained-stage accounting. Entered work owns its exact retry input through cancellation and delayed completion. The consumer checks session/generation and object identity; stale completion retains an uncertain result. The bytes factory establishes envelope/descriptor checks, while the later publication caller additionally establishes private accepted membership and dependency closure. Shallow discovery retains raw untrusted leaves, advances one bounded stream turn at a time and revalidates cursor/root context. Every resumed cursor is single-use at its consumer. Nested protocol discovery retains a bounded parent/child stream stack; resuming a parent retires deeper streams, while starting an unrelated stream retires the incompatible traversal. A directory listing is discovery input, never a completeness certificate.

Cleanup addresses only the operation's still-identifiable owned stage under the reserved-stage producer contract. Other producers must preserve owned stages and expose complete immutable finals/atomic safe saves; arbitrary replacement in the check-to-unlink interval is outside that contract. Unknown, displaced, empty-allocation-ambiguous or cleanup-failed stages remain preserved. Required history and foreign entries are never prefix-cleaned. Bounded reads check held/named observations before and after reading; complete envelope validation remains mandatory. Stable intermediate same-vnode writes cannot become a filesystem transaction through timestamp checks or a settling delay.

Use presenters as invalidation hints plus incremental directory discovery. A fresh scan can add evidence; missing entries never retract accepted history. Persist only rebuildable scan hints locally. A large collection must not repeatedly read all old object bodies to discover one new object. Revalidate root/lifecycle generation around every callback and accessor; after root uncertainty, local sealing can continue but provider writes stop. Do not automatically follow a same-ID collection into a different folder.

The required Foundation root reference has a qualified filesystem capability boundary. Fresh opening of an HFS+ root beyond `PATH_MAX` may return unavailable even though descriptor-relative inspection can reach its bytes. Preserve the safe refusal, complete private history and local editing; retain ordinary HFS+ opening and qualified already-owned deep-move/read behavior. Retry or user-directed relocation/reassociation must positively establish the applicable root before provider effects resume. Save Current Collection As… follows its existing complete-source contract. This explicit limitation adds no Work Offline condition or uncoordinated fallback. The [capability ledger](plan/phase5/04-apple-coordination-and-discovery-validation.md#foundation-volume-follow-up-and-approved-deep-hfs-limitation) distinguishes observed refusal from successful acquisition.

Initial open, foreground, settled saves, explicit refresh and continued bounded background turns are ordinary discovery opportunities. A completed or early empty pass leaves later opportunities eligible without another presenter event. Preserve bounded parent-directory progress while inspecting children; invalidation records new work without repeatedly restarting a valid pass. Restart discards cursors, preserving received bytes and queue obligations. An accepted-file hint may reuse a prior object identity only after a fresh rooted observation matches its path and file fingerprint and the selected private store confirms exact accepted membership. Its rebuildable fingerprint covers kind, device/inode, size, link count and modification/change times; live session permissions remain separately checked at every consumer. Reopening alone does not invalidate unchanged-file fingerprints. A hint authorizes neither root association nor completeness, acceptance of new bytes or physical modification. Changed, missing or malformed hints take the normal read/validate/receive path.

Receive into the local object store, verify the full envelope and value schema, durably install it, and fetch named dependencies asynchronously. Keep incoming-but-incomplete evidence distinct from applied history. When a complete validated dependency-closed batch is ready, prepare its reduction off-main-thread and publish it atomically against the captured live generation. A failed generation check recomputes; it does not overwrite a newer local edit. Imported operations retain their IDs; do not emit new local `Put` operations merely because remote changes were applied, which would make an endless echo loop.

Publication, upload status, receiver disclosure, and receiver durability are different boundaries. There is no cloud acknowledgement before local editing or an NV logical delete. No remote receipt protocol exists in v1. A quit-time upload wait can report only the provider's actual item-specific evidence and can always be left with **Quit Without Waiting** once local durability is safe.

### Bounded metadata and accepted-hint lookup

An immutable discovery turn shares ancestor checks around a held-directory metadata
operation, then validates eligible hints in one synchronous database-actor operation.
Darwin uses checked `getattrlistbulk` records; missing type-specific attributes
select fresh no-follow `fstatat`. The portable path uses that same held directory.
Stream-level ENOTSUP/ENOSYS/EINVAL switches once to a new portable enumeration
descriptor; ordinary I/O errors remain failures. Each native refill is bounded to
64 records and a 2,560-byte packed buffer. Across returned turns retain at most
64 raw names/16,320 name bytes per stream and refresh only the selected names.
EOF retains its stream until that tail is consumed. Public names-only listing
keeps its existing single-use cursor behavior.

Hint requests carry ordinals, exact keys/fingerprints and the issuing root/store
incarnation. One bounded joined query verifies existing hint codec, length, digest
and accepted membership after full store/header/required-state checks. Sparse
results default independently to reads; database or integrity failures propagate.
Consumer fences remain mandatory after suspension. Candidate steps and refills
retain the existing discovery budget, while bounded native read-ahead conveys
no extra receive authority. Each miss enters ordinary exact read/receive separately;
a later sibling failure preserves earlier durable input. Schema, hint encoding,
receipt and model-publication meanings remain unchanged.

See [implementation and qualification](plan/phase5/bounded-discovery-batches-validation.md).

## Note reduction, concurrent edits, and intentional deletion

Reduce the dependency-closed operation set, not directory enumeration order. Replaying or delivering an ancestor after its descendant cannot reapply an older note state. Retain complete branch inputs in local history even when a current view selects one.

For a live birth, take maximal note revisions under the transitive **note-predecessor** relation, not the broader causal graph. One head supplies the ordinary note. Identical head values may share one displayed state without forgetting their IDs. For differing heads, apply the conservative rules below; a failure leaves all heads available to the resolver. Choose a stable lexicographic revision-ID order for unresolved presentation once the accepted sets match, not wall time or arrival order. A dirty local editing session may pin its own head until generation-fenced publication finishes; this is a temporary presentation state, not a different persisted winner rule. Common note bases and represented merge inputs also use note ancestry; causal awareness of an unresolved alternative does not make it a merged ancestor.

Releasing a temporary local Current-head pin schedules reduction/publication of
the complete currently applied head set, including locally authored heads; it
does not wait for another remote receipt or filesystem notification. Keep the
displayed value paired with its actual represented inputs while that pin exists.
A changed derived Current can invalidate a prepared command even if the causal
frontier has not changed. Local barrier acknowledgment only settles its exact
captured work; a separate generation-fenced publication may update Current once
eligible, without overwriting newer local work or replaying its old captured
bytes. With stable inputs and available local processing, this pending publication
must complete. `CompensationOverlapBridge` checks the difference between durable
record equality and eventual displayed-value agreement.

### Conservative automatic merge version 1

`NVConservativeMergeV1` is a required, genesis-pinned value algorithm, not the existing asymmetric fuzzy `NVMergedText` helper. Automatic merging initially requires exactly two differing maximal heads of the same live birth, complete durable inputs, and one unique best common note ancestor with a complete value. Multiple best bases, more than two differing heads, incomplete/unsupported inputs, or a Delete of this birth select manual conflict handling. Never fold arbitrary pairs in arrival order. Ancestor elimination and equal-value collapsing remain available without a textual merge.

For scalar field values `B` (base), `L`, and `R`: if `L = R`, use that value; else if `L = B`, use `R`; else if `R = B`, use `L`; otherwise conflict. Apply this rule to title and to each label's membership in the canonical label set. This combines independent adds/removals, but does not pretend to recover coalesced same-label remove/re-add intent. Rich content/format is an opaque coupled value: equality or one-sided change can be accepted, but simultaneous differing rich-content or format changes cannot be text-merged. Keep the birth's creation date; take the maximum input modification date for display only, never for selecting content or ordering operations.

For differing two-sided plain-text body changes with the same plain-text format, use a deliberately narrow exact algorithm:

1. Split each exact UTF-8 body on LF into tokens retaining their line terminators and final unterminated line. No whitespace, CRLF, case, or Unicode normalization is performed.
2. Against `B`, compute each branch's longest equal line-token prefix and then longest equal suffix not overlapping that prefix. The intervening base interval and branch replacement tokens are its single bounding edit. Several changes within one branch are deliberately treated as one bounding interval.
3. Equal edits collapse. Otherwise require strictly separated base intervals: even touching intervals, two insertions at the same boundary, or an insertion at the other's boundary require review. Apply both replacements to the base in descending index order. Require all other user-editable fields to pass their rules; do not publish a partially merged record.
4. Two-sided text merging beyond 10,000 line tokens in any input requires review in v1; equality/one-sided rules still apply. This is an input-defined limit, not a machine-speed or timeout-dependent winner rule.

This merges edits to separated lines/paragraphs and independent fields, but intentionally declines same-line edits and many otherwise mergeable multi-hunk cases. It preserves exact unchanged bytes and never fuzzy-applies a patch to a merely similar location. It does not prove semantic compatibility of two sentences. Freeze cross-architecture vectors for line splitting, interval boundaries, scalar/label rules and limit handling before use. Do not substitute a different diff algorithm under the same version.

An automatic result is a **derived view**, not a randomly identified new `Put` generated by every observing Mac. Identify it by a domain-separated hash of collection/birth, algorithm version, sorted input head IDs, base revision ID, and canonical result-value digest. Its merge descriptor references those inputs; it contains no reference to its own enclosing segment. Repeated discovery/recomputation adds no operation or undo step. Additional heads invalidate the old current merge descriptor and trigger recomputation/review from the new full head set, without discarding any input.

When the user edits, explicitly keeps, or projects an automatic result to a separate file, preserve its descriptor as provenance. A subsequent user `Put` references every input head as predecessors and records that descriptor as its before-state when applicable. A local projection receipt can likewise refer to the descriptor instead of a single revision. Merely receiving a remote projection of those exact known merged bytes must not emit an echo `Put`; an edited/ambiguous file still follows the independent current-file rules. A validated descriptor is reconstructible history evidence, not physical file-install evidence and not permission to resolve Apple versions.

Unknown merge-policy versions cannot silently reinterpret a derived state as an ordinary fully resolved note. Preserve the heads, expose unsupported status, and require a supported implementation before editable acceptance of that policy. The version-1 line bound and scalar rules are protocol inputs, not per-Mac preferences.

An explicit resolver choice emits a normal `Put` with the user's chosen body and the captured unresolved revision set as parents. It only resolves heads that action observed. A concurrently arriving new head remains unresolved. Saving a head as a separate note uses `RecoverCopy`; its causal disposition identifies the exact represented source revision, not all future heads. If that head is already an ancestor of a newer conflicting head, the newer head is not dismissed. The copy and disposition must be in the same locally durable segment (or reference an already durably verified exact copy); never persist disposition first.

Protocol-copy disposition is durable evidence that a selected NV revision was represented, not an Apple member handle and not a Delete. Its schema must bind source birth/revision and exact copy birth/state; later editing/deleting a completed copy does not erase that historical fact. **Save as new note is representation-only.** Its action records the copy and exact selected-revision acknowledgment; it emits no implicit Keep Current, source-value `Put`, source note-predecessor edge or source `Delete`. Causal dependency references to source evidence are knowledge, not source supersession.

Compute two distinct results from the same validated history:

1. **Original note contents:** derive source heads by note-predecessor ancestry, then apply the normal single/equal/merge/stable revision-ID selection rules. Copy dispositions never subtract from this input set, influence its ordering, or create a new source head. The existing temporary dirty-local presentation fence still applies; copying does not pin Current permanently. An applicable source Delete remains independently authoritative.
2. **Unresolved NV attention:** if the source reduction remains incompatible, show its alternative heads not represented by Current and not individually covered by a completed selected-revision copy disposition. Do not treat such a disposition as coverage of ancestors/descendants or all known heads. Keep Current available for preview even when its own revision was previously copied elsewhere. No remaining alternatives means no NV conflict badge, not deletion or blanking of the source. A later uncopied descendant is evaluated anew, even when its predecessor was copied.

For example, reciprocal copies of A and B leave both source revisions as content evidence and leave their new notes independent. With the same source history and no temporary edit pin, both Macs still select the same Current under the existing rules. Both copied conflict entries may disappear while the original remains; one copy can have the same body as Current. Receiving only a copy/disposition cannot change the settled source value. Receiving additional source history can. Modifying/deleting a completed copy does not reopen its old source conflict or recreate that copy; a later explicit recovery uses the existing nonretired-slot rules. Historical evidence, not the copy's current liveness, validates completed disposition on restart. Pre-completion exact-candidate checks are unchanged.

Deletion rules are independent of presentation order:

| Available causal evidence | Result |
| --- | --- |
| `Delete(birth)` observes the current edit | Remove the birth; the deleted edit remains historical, not an automatic conflict copy |
| `Delete(birth)` concurrent with an edit, and no applicable Delete covers that edit | Keep the source birth absent; preserve the uncovered maximal edited state as a deterministic conflict note |
| D₀ concurrent with E, but E precedes another Delete D₁ of that birth | Source absent; E is historical only. Retract its untouched automatic preservation, even if E/D₀ were displayed before D₁ arrived |
| E precedes F; D₁ covers E but is concurrent with F | Preserve F, not a second obsolete E copy; D₁ does not cover F merely because it covers F's predecessor |
| Old edit or creation arrives after known deletion | Never resurrect the birth; only genuinely concurrent unrepresented edited state qualifies for conflict preservation |
| Put causally after a delete of that birth | Invalid same-birth resurrection; the writer must create a fresh restoration birth instead |
| Explicit Restore/undo/re-import | Create a fresh birth, optionally with history pointing to the old one; old deletes target only the old birth |
| Current note file disappears without an applicable `Delete` | Keep the logical note pending external-deletion confirmation according to NV's preference; geography/provider classification is irrelevant |

The edited state concurrent with a delete is available because immutable history carries it, even when the provider no longer exposes its original text file or an `NSFileVersion`. This strengthens proposal 4's current-visible ceiling. It still depends on some surviving replica retaining and eventually disclosing that segment; encryption does not force delivery.

For one deleted birth and accepted dependency-closed history H, an edit E is **covered** iff E is a causal ancestor of any applicable Delete of that birth in H. Eligible automatic preservation comes from the note-predecessor-maximal uncovered edits concurrent with at least one such Delete. This is a predicate over the whole accepted set, not a per-Delete union of copies: one covering Delete defeats an earlier concurrent-Delete reason to preserve E. Same-writer E→D₁ is authoritative because the recorded dependencies establish that order, not because of wall time or writer privilege. Another host's Delete observing E has the same effect. Same complete history must yield the same final live notes/conflicts across all delivery orders; retained history itself never shrinks.

For automatic delete/edit conflict preservation, retain the existing versioned automatic conflict-state digest (source UUID, canonical title/body/sorted labels), extending the domain/format encoding explicitly for any rich-content codec. For user-invoked copies, retain the existing source-UUID + canonical-body conflict recovery key and deterministic slot rule; mutable title/labels/filenames are outputs, not identity inputs. A matching UUID alone is insufficient: verify the exact represented state. Modified candidates and retired identities cannot be overwritten or silently reused.

The reducer treats an eligible automatic conflict state as a deterministic derived birth, so two Macs do not race to mint random copies. Merely displaying, projecting, caching or reopening it emits no `Create`, `RecoverCopy` or retirement. Its first ordinary user edit records full resulting state and references the originating conflict evidence as its birth dependency: validate that evidence against the action's captured history, not the receiver's later full history. That independent work remains valid when a later source Delete covers the original edit. An explicit separately saved copy is likewise independent. Such admitted pending work is protected by the generation fence even before its local barrier; after durability its operation supplies protection across restart. User deletion/retirement of that separate birth still applies normally.

An untouched automatic birth is present only while an eligible source remains and its identity is not explicitly retired. Recompute and retract it when later history covers/supersedes all its eligible source revisions. A cached/displayed/previously projected result is not evidence to keep it permanently. Do not emit `RetireConflict` for this retraction: another uncovered revision with the same canonical state may later justify the same key. A user delete does add monotonic retirement. Preserve the existing automatic-candidate collision/modified-state behavior in concrete tests; retirements never suppress a different key or grant physical deletion authority. Retraction affects the derived live view, not retained segments or a blind unlink. Any leftover text projection is classified from its source evidence as obsolete; changed/unassociated bytes remain surfaced, and exact-file cleanup requires the existing separately authorized physical policy. It must not be re-imported automatically as a fresh note. Explicit later recovery may choose the next free nonretired slot. A late concurrent edit to a recovery note is itself subject to ordinary delete/edit preservation, not silent erasure by UUID matching.

Fence/cancel still-pending projection of a retracted automatic view before installation. If the file was already installed, retain its source association as obsolete derived output rather than interpreting it as an independent user recovery action. A later real external edit to that file must be preserved and reconciled explicitly when its old derived birth is no longer live.

No age cutoff, maximum tombstone count, checkpoint omission, or “all devices probably saw this” heuristic forgets committed deletes or retirement in v1. Their durable storage is the retained history; the checkpoint's compact sorted set/index accelerates reduction but is not the only copy.

## Action records and cross-launch undo

`ActionRecordV1` contains the action ID; action-origin ID; previous action in that origin (or explicit start); one undo scope (a note birth or the collection); the maximal action IDs represented by the captured scope frontier at admission (`scopeParents`); action-kind enum; ordered member operation IDs; affected births and exact before/after state references; and optional `undoOf`, `redoOf`, `restoredFrom`, native-undo coverage, or merge provenance. This frontier includes validated actions represented by the applied live-model frontier and any earlier admitted local action on which the new live value depends; the latter must be earlier in the same complete segment or already locally durable. Encode `scopeParents` as one canonical sorted set of unique IDs and reject duplicates, nonmaximal entries, cycles and cross-scope parents. It is an antichain under validated action ancestry, not an arrival-ordered stack snapshot. Native-undo coverage identifies each affected saved-edit action and its remaining after-state reference. Before-state references identify retained revisions, validated merge descriptors, or explicit fresh-birth absence. Referenced action/state evidence, origin predecessor and scope parents need exact object locators and belong to the validated dependency closure, not an opportunistic filename lookup. If a pending before-state has not yet been recorded, capture its value as a predecessor operation in this segment or a durably retained dependency. Action metadata cannot reconstruct an intermediate body that coalescing already discarded.

Allowed initial action kinds are saved edit, rename, labels, create/import batch, delete batch, historical recovery, conflict choice/copy, undo, and redo. Human-readable names are localized from these enums/counts, not executable remote strings. Optional origin display labels and event dates are informational only and remain inside the encrypted payload. Undo/redo references identify earlier complete actions and are accompanied by the actual new compensating note operations; a pointer alone never changes a note. No serialized `NSUndoManager`, object pointer, selector, or invocation is accepted from disk.

Action validation includes semantic agreement, not only valid IDs and an envelope tag: before-state references describe the exact frozen admission inputs, after-state references describe the actual member-operation results for that same group, every scope parent belongs to the same scope and validated dependency history or an earlier complete group in the segment, and an `undoOf`/`redoOf` target has the required action/compensation relationship. On receipt, validate those references against the writer's declared causal inputs, not equality with the receiver's current note or a local stack. An otherwise authentic envelope with contradictory action/note values is invalid evidence, not permission to select a candidate while loading different note bytes. Freeze these values together; retries must not recapture action metadata against a later live note.

The previous-origin-action chain supplies provenance and definite order within one authoring origin without trusting clocks. The scope-parent graph supplies portable ordering across origins. Neither is a device/person certificate or mutable cursor. Allocate a fresh random action origin for each editable collection session and a fresh writer epoch independently. Restart or activating a rebuilt/copied private store starts a new session; a same-session root move does not. Thus multiple origins may be authored by one process; retries reuse the already captured origin/action IDs. Forked or restored origins remain ordinary preserved history and never force a winner.

Capture `scopeParents` from the live model's applied causal frontier plus its earlier pending local dependencies, not every received/parked segment or the history viewer's loaded rows. Validate that the parent set contains **all** maximal meaningful actions in that scope represented by those declared inputs; a valid antichain which omits a represented maximum is invalid. Startup must reconstruct the compact per-scope frontier needed to author actions before enabling mutation, independently of the slower history/candidate presentation index. Preserve it as derived current-state context with its exact represented frontier, or reconstruct it from retained records. This avoids either blocking typing on history browsing or falsely authoring new actions as concurrent with the history already displayed.

Build the portable causal-undo index from validated complete action records in every origin, using lazily loaded derived database indexes. For a requested note or collection scope and direction, derive applicable candidates from the action/scope-parent/compensation graph and current values. Automatic recomputations, storage receipts and preview-only events are never candidates. Provider arrival order, wall time, writer sequence and origin locality have no role. A single causally maximal applicable candidate may proceed on any Mac. A maximal action whose inverse overlaps Current remains a review candidate; do not filter it out and silently skip to an older safe action. Multiple incomparable candidates, competing compensation/redo descendants, or an otherwise unsafe value reversal require Review Undo/Redo with the alternatives disclosed. Missing evidence leaves a candidate unavailable; it is not treated as an empty branch.

Ambiguity is **command-relative**, not a permanent flag on a note/scope. First derive that direction's maximal candidates, including unsafe candidates needing review. For whole-action chains, a compensation family follows `undoOf`/`redoOf` back to its independent action; `scopeParents` order families but do not join them. Check competing unconsumed leaves in each candidate's family, including siblings eligible in the opposite direction, plus relevant incomparable candidates/current-value conflicts. A historical fork in another family alone cannot require review. Partial-native coverage can involve several saved-action families and must retain its remaining-effect rules, not arbitrarily choose one root. In particular, after concurrent Undo A actions U/V, an independent X observing both has its own family: Undo X, Redo of that compensation, and the next Undo are automatic if their ordinary value/admission checks pass. U/V remain retained, and X still suppresses their older redo eligibility; no historical branch is erased or declared globally resolved.

In-session fine-grained typing undo remains native while its text-state epoch and range operations are valid **and** it implements the selected causal candidate or the newest unrecorded local typing group. The shared router checks causal eligibility before consuming a native entry; `canUndo` and a valid text range alone cannot bypass a later remote action or concurrent candidates. A remote rename may leave native body ranges valid while changing which action is eligible first. Preserve the fine-grained group for when it is applicable; use portable compensation/review for the current candidate. On relaunch or total Application Support rebuild, saved edits have captured-generation granularity and named actions preserve explicit grouping on every Mac; no per-keystroke durability or reconstruction of old Cocoa grouping/selection is promised. Startup may publish current notes before the complete history index, but late index publication unions with newer admitted actions and cannot replace the live candidate graph.

Native typing undo can reverse only part of a previously captured saved-edit group, or span several captured groups within one note. Do not mark a partially reversed group wholly undone or expose it again as a duplicate coarse command. That explicit native compensation records coverage and the remaining after-state reference for each affected saved-edit action, alongside its actual before/after note operations. The next cross-launch coarse undo targets the remaining effect against the original before-state; redo targets the actual compensation, not the entire original saved edit. These remaining-effect indexes rebuild from action records and obey the same atomic barrier. Partial-native coverage is not permission to silently execute only part of a named/bulk undo, and does not require recording every original keystroke or selection.

For each saved group, compare native coverage claims by their action ancestry.
Ordered claims use the newest remaining state. Incomparable maximal claims retain
their alternatives and require command-relative review; the group is fully
consumed only when **every** maximal claim is complete. Prepare its remaining
reversal from the claims represented by actual Current note lineage: one represented
claim supplies its remaining state, a joined Current supplies the combined state,
and a Current still representing the original effect uses that original state.
A complete competing claim alone cannot erase a still-partial claim. Capture and
received-record validation both require the first native step to cover the unique
automatic causal candidate in its declared writer inputs. Actual AppKit attribution
of those steps remains an application integration obligation.

To undo a complete action, capture the requested scope, selected candidate ID, complete maximal candidate set, current action frontier, affected births/heads/live UUID/LSNs and exact values. Prepare compensating values against the selected action's actual before/after states. Preserve fields it did not change. A changed scalar can be reversed automatically when the current value still equals the action's after-value; a conflicting later value requires review. Plain-text reversal may use the same conservative kernel with base = action-after, one branch = action-before, and the other = current, retaining unrelated later edits. Automatic rich-content reversal requires an unchanged after-value; explicit reviewed replacement requires the exact disclosed replacement and compatible format. An already absent effect is no longer applicable, not a blind redo opportunity.

Undoing a Create/Import is not permission to delete a subsequently changed note: require that birth's action result still be its unmodified current state, or ask for an explicit reviewed choice. Undoing Delete or recovery of a deleted birth creates a fresh ordinary birth and records `restoredFrom`; it never removes the old Delete or retirement. Redo reverses the **actual compensating action**, using its resulting birth mapping, not a stale original UUID or replay of the original operation ID. A subsequent Undo targets that actual Redo action with its actual before/after values, not the original forward action. Follow compensation edges separately from scope-parent ancestry: causal parents alone do not say which effect was reversed. These checks concern logical values; physical file removal still requires a separately captured exact current snapshot and the local segment barrier.

For ordered A→B, Undo B (U) then Undo A (V) yields Redo V followed by Redo U; executing the first redo does not clear the remaining redo chain as an independent edit would. An independent action X causally after U suppresses that earlier redo branch even if X is later undone/redone. A concurrent X does not suppress it. Suppression derives from retained independent actions, not only their currently active effects. Competing compensation descendants remain explicit alternatives: reversing one does not consume its sibling or establish a globally unique undo position.

Conservative continuation is required, not automatic compensation deduplication. For A changing 0→1 and concurrent U/V each changing 1→0, reviewed Redo U records R with actual 0→1. Redo V now proposes no change: disable Apply for that attempt, explain that its effect is already absent, and preserve V without a manufactured compensation or cursor advance. The user can dismiss and invoke Undo R, producing S with actual 1→0; Redo S produces T with actual 0→1. These commands remain reviewable while their own family has a competing sibling. There is no requirement that every fork become automatically traversable, but it must not block ordinary editing or contaminate an independent later family's commands. A no-op in one invocation neither consumes a sibling nor disables the opposite command. Review/cancel/reopen recompute from current evidence; only an admitted effect changes derived eligibility.

Equal note values may converge without coalescing action identities or birth mappings. Two concurrent Undos of Delete can create two distinct fresh births. Reviewed Redo of one deletes only that compensation's applicable restored birth; the other remains. Undo of that Redo creates another fresh birth, and its Redo targets that new birth. Neither body equality, a common original target, nor review approval authorizes treating these as one restoration. No additional synced resolution record, branch cursor, or automatic equivalence rule is introduced in v1.

Revalidate the candidate set/frontier and all captured value/root/store inputs before one all-or-nothing action admission. On ambiguity leave the live store and derived eligibility unchanged and offer Review Undo/Redo; staleness requires fresh preparation, not automatic semantic approval. Missing evidence or failed admission prerequisites cannot be overridden in review. Do not silently omit failed members from a bulk action. A causally later independent action in the same scope makes an earlier redo compensation nonmaximal; a concurrent action preserves both alternatives and can require review. Preserve existing note-versus-collection routing and never register one durable action as independently executable in both scopes. Losing redo eligibility never deletes history. Two Macs may concurrently compensate the same action; both immutable records survive, equal results may converge, and later ambiguity is reviewed rather than pretending one global execution or cursor.

Invocation context, not the reused view, determines action semantics. A review reached from Command-Z/Edit Undo or Redo continues that exact captured command and candidate frontier. When several incomparable candidates exist, the review first requires an explicit candidate selection and then shows its exact proposed replacement. Approval admits an `undo`/`redo` action with the corresponding `undoOf`/`redoOf` reference, actual current-before/approved-after values, the current action origin, a fresh action ID, scope parents, and any required native remaining-effect or fresh-birth mapping. It completes that command; it is not a new `historical recovery` action. For causally ordered A→B→C, Undo C followed by reviewed Undo B leaves the corresponding redo chain B then C. The inverse of reviewed Undo B restores the actual state immediately before that approved undo, not B's original after-value. Further Undo/Redo derives and revalidates candidates afresh. Previewing Current, Cancel, or an already absent effect cannot skip a candidate or manufacture redo.

Review approval authorizes only the explicitly disclosed replacement within the captured command's affected fields/members. It does not bypass birth/format/root/store/generation/admission checks, widen a bulk command, consume unresolved alternatives or call Apple's disposition APIs. Revalidate the current undo/redo position and affected inputs immediately before admission; a stale review may not switch to the now-top action, replay old consent against refreshed text, or turn into independent recovery. Opening, previewing, dismissing or abandoning it consumes no action. A fresh user invocation may review the then-current candidate. After admission, dismissal is not cancellation of the ordinary pending compensation; retries persist that same action without registering a second one.

An explicitly invoked Note History recovery that modifies Current is instead an independent action. As a causal descendant in its scope it can make an earlier redo nonmaximal; concurrent redo evidence remains reviewable rather than erased. The conflict-badge resolver retains its independent conflict-choice/copy semantics and separately scoped dispositions; sharing presentation does not turn it into Undo. Separate copies remain independent creation/recovery actions, not completion of a failed current-note Undo. All append immutable history. A receiver validates a reviewed action against its declared parents, actual inputs and member results, not by rerunning automatic reversal against receiver Current. The old action link alone is never replacement authority.

Persist the compensating operations and action record together through the ordinary local barrier. The live derived index may include an admitted pending action, but its eligibility transition cannot be declared crash-durable separately from the resulting note state. Retry retains action/operation identities and sealed bytes; after crash or on another Mac, the complete durable group reconstructs both note effects and causal eligibility, or neither. A stale completion cannot replace a newer candidate graph or clear newer pending generations. Provider receipt/upload never gates the local barrier.

## Historical recovery and deleted-note history

Per-note history is a local projection of validated retained operations, action records, and reconstructible automatic-merge descriptors. Include both known remote and local branches; distinguish concurrent branches rather than claiming wall-clock order is causal order. A displayed remote operation must retain its ID and cannot acquire a fresh local identity merely by being previewed. Missing evidence is unavailable history, not an empty revision. Creating/selecting a new preview never mutates notes, records a logical action, or marks provider versions resolved.

Selective recovery uses normal admission: copying a passage is ordinary clipboard/editor behavior; applying explicitly selected historical body/title/labels makes a new `Put` after comparing against the captured current state. Default body recovery preserves current title/labels. Recovering a full historical note into a separate note creates a fresh ordinary birth with `restoredFrom`, captured attributes, and collision-adjusted output name. One admitted click/retry reuses its action ID; a later explicit copy is a new creation. The deterministic conflict-copy slot algorithm remains specific to conflict recovery, not general historical copying.

Recently Deleted derives entries from applicable logical Deletes and their prior revisions, grouped by birth/deletion action. Unexplained missing files are not entries until a Delete is admitted under the confirmation policy. Concurrent edit/delete preservation remains separate and must not be counted as restoration of the old birth. Its sole recovery control is **Restore**; general Note History and conflict recovery retain their distinct separate-copy actions.

A Restore records the exact source birth, deletion action and selected prior revision in its restoration provenance, binding them to the resulting fresh birth/member operation. Undo of Delete likewise records the deletion entries it restores. These references belong to the complete action record and validated dependency closure and persist atomically with the fresh creation under the existing local segment barrier; no separate synced dismissal record or UI-state journal is introduced. A generic historical-copy `restoredFrom` reference to a birth/revision alone is not evidence that a particular deletion entry was restored.

The default Recently Deleted list excludes a source entry iff complete, validated, locally durable restoration evidence explicitly names that entry. On the originating Mac this becomes true at the restoration's local barrier, without waiting for projection installation, upload or another Mac; a pending/failed barrier leaves the source row with pending/failure status while preserving the admitted new note. A receiver applies the same predicate only after validating and locally persisting the restoration and its required closure. Rebuild this derived index from retained records after restart/index reconstruction, including installation completed before its UI callback. It is not a per-window hidden flag, an origin-local undo cursor, or a test for whether the restored birth remains live.

Later editing/deleting the restored birth never removes the original restoration evidence. A subsequent Delete of that fresh birth produces its own Recently Deleted entry and recoverable prior values; the original entry does not reappear. Guarded Undo of Restore, or Redo of a Delete whose Undo created the fresh birth, follows the same rule. Hide only the explicitly named source entry, not other deletion actions or unrelated conflicts. Its old Delete, prior branches and restoration provenance remain inspectable in history; selecting one prior branch for Restore does not erase the others. Concurrent explicit restores can create two preserved new births while both exclude the same source entry. There is no automatic purge, empty-trash operation, or use of historical filenames/UUIDs to remove a current file.

## Separate text files and the identity limit

The text-file path preserves rooted expected-snapshot reads, double-catalog publication fences, external-edit handoff and safe replacement. Segments supply committed note identity; files supply editable current bytes. A note title, body hash, UUID xattr, file-resource identifier, or provider version identifier alone is not evidence of a permanent cross-Mac file incarnation. PlaintextFilesV1 writes a small advisory projection stamp on NV-generated files where supported; receiving missing/stripped attributes remains supported. It is provenance, not UUID authority or another history log.

Store local associations between a birth, its last represented revision, intended relative filename, exact encoded projection digest, and the rooted local accepted-file snapshot. The portable projection descriptor (path, format, exact expected output digest) may travel with a note value inside a segment; it says which bytes are represented, not that a physical install occurred on another Mac. Local physical snapshots and generation receipts stay in required Local State rows, not rebuildable current-note rows. They still require fresh rooted validation after restart; loss cannot manufacture a completed installation or authorize removal. No additional synced receipt file or per-note sidecar is needed. Projection paths are validated direct-child leaf names: reject separators, NUL, `.`/`..`, reserved protocol/database names including `NV Data`, and symlink traversal. Never concatenate an arbitrary received path into a filesystem operation; rooted helpers apply the validated leaf under a separately authorized root.

### Projection stamp and delayed-history handling

Use the exact OS-independent xattr name `org.notationalvelocity.projection#S` and a bounded `NVProjectionStampV1` value (maximum 4 KiB). Encode version, collection ID, birth, content format, SHA-256 of exact encoded file bytes, and a tagged represented-state reference: ordinary revision ID plus segment locator, or the complete two-input merge descriptor and its input/base locators. An automatic conflict projection additionally identifies its source preservation evidence; it does not claim a user `RecoverCopy`. Freeze binary field/tag vectors before production writes. Do not copy a segment's entire frontier/action batch into the attribute. Full title/labels/history remain in segments. This stamp exists only on plaintext projections; encrypted collections gain no plaintext metadata channel.

An equal-value Current may name its sorted represented revision IDs/locators rather than pretend one revision consumed the others. If any complete represented-state reference exceeds the stamp bound, omit/report the stamp and use normal conservative association; do not truncate its input set, relax the bound or add a sidecar. A merge descriptor/body digest still requires recomputation from validated inputs before acceptance.

Stage the stamp with the exact replacement body before installation; verify both through the verified installed OS file descriptor afterward, as required by [Foundation's post-install verification](../Foundation-Safe-Replacement-Migration.md). This is an opened file handle, not the portable projection descriptor. A stamp failure is not a local segment-durability failure: report/degrade to the unstamped association path, never invent successful stamping. Follow Foundation's existing note-owned metadata contract without adding a post-save identity reassignment. The provider may expose body and metadata independently, omit attributes, or preserve them on a copy; no simultaneous-arrival guarantee is assumed.

Distinguish a known unsupported/omitted advisory stamp from an uncertain file installation. Exact body and mandatory encoding/tag metadata still need their existing verification; a general write/readback error cannot be swallowed as optional metadata loss. Conversely, a verified unstamped file is supported and does not add a new stamp-success gate to local editing or Apple's existing exact-file resolution barrier.

Read body and stamp under the current-file/root fences. Parse/bound/validate collection and locators before requesting objects; compare the exact body digest and verify the referenced state against durable dependency-closed history before association. A matching stamp whose segment is missing means **waiting for referenced history**, not a new Import. Once the exact state is available, associate only under the unique applicable projection policy; no echo `Put`/duplicate birth. A digest mismatch retains current bytes as an external-change/metadata-skew candidate. Its old stamp may locate a possible base, but does not authorize attaching changed bytes without a trustworthy local association or explicit choice. A copied stamp, duplicate candidate, wrong collection or contradictory descriptor is ambiguous, never a reason to merge physical identities or delete a file. Historical `NSFileVersion` bodies still use their captured resolver context, not an assumed stamp.

### Current-file decision matrix

Classify a complete current-visible observation, not its event name or presumed origin. Eligibility, root/store authority, current catalog/file fences and captured model/history generations are prerequisites to admission. Mandatory cases precede the repair heuristic; absence of an advisory stamp alone is not an exception. An established applicable association/handoff may still handle a legitimate external edit whose old stamp no longer matches, but cannot outvote positively contradictory evidence. Explicit Import as New is a fresh-content command, not automatic acceptance of a provenance claim; it still requires readable captured bytes, admissible values and current authorization.

| Observation | Handling |
| --- | --- |
| Segment update; unchanged positively associated local projection | Schedule exact-current safe replacement after local durability |
| Segment update; local file changed concurrently | Preserve/import its current state, then reconcile; never overwrite based on segment authority alone |
| File discloses a specific matching segment/state that is unavailable | Retain a verified snapshot when readable; wait for exact dependencies and rescan/revalidate; do not infer intentional deletion or import by timeout |
| Matching valid stamp but referenced history has not arrived | Retain the file, request bounded exact dependencies asynchronously, and associate/recompute after validation; do not create another birth |
| Stamp absent/stripped/omitted, no contrary evidence | Preserve existing automatic association/handoff handling; otherwise evaluate the narrow repair candidates and import fresh if none qualifies |
| Malformed/foreign/copied/contradictory stamp or body/metadata skew without a trustworthy applicable association | Retain bytes and show the specific provenance ambiguity with explicit association/fresh-import choices; missing exact dependencies stay pending. Do not treat malformed metadata as a valid reference or silently repair it into identity authority |
| Unique live projection descriptor matches path and exact bytes | May associate that represented state under the explicit projection policy; equality is not removal authority |
| Matching old bytes refer only to a deleted birth | Show as a possible stale projection/restoration; do not automatically resurrect, unlink, or suppress it forever. Explicit Import as New creates a fresh birth |
| Obsolete automatic-conflict projection | Preserve and account for its originating history; do not create a fresh birth merely because the derived note disappeared. Changed independent work still requires preservation/reconciliation |
| Unassociated file matches a plausible live repair candidate | Offer each qualifying note and its reason, plus Import as New; even one heuristic candidate requires choice |
| Ordinary eligible unassociated file with no mandatory exception or plausible repair candidate | Automatically admit one fresh ordinary Import, retaining its exact captured value and retry identity. This deliberately permits late duplicates, not a claim that undisclosed history does not exist |
| Ambiguous descriptors, multiple physical claimants, or case/normalization collision | Preserve and expose the specific ambiguity; do not choose an owner by iteration/arrival order or merge identities |
| Provider reports a placeholder | Defer the file-body decision; no inference from its unreadable contents or apparent absence |

There is no finite waiting period or quiet-catalog observation that proves a file has no corresponding segment. Automatic fresh import is an explicit product trade-off after the locally decidable exceptions, not such a proof. A delayed segment may reveal another birth or an old Delete of similar bytes. Preserve both independently admitted births and their later edits; do not retroactively rekey, suppress or delete the fresh import. The old birth's Delete remains scoped to that birth. Do not create an Apple conflict badge for this identity uncertainty. This policy does not promise a new cross-birth merge/alias command; existing independent notes and explicit content recovery remain available.

### Repair candidates and active projection state

Compute candidates individually from one captured reconciliation frame. A **repair-needed relationship** belongs to a live note with a previously established but now missing relationship, or one whose current relationship cannot be re-established under freshly checked evidence. Verified absence requires a complete catalog; an occupied former path may instead be uncertain. A known placeholder, temporarily unreadable known file, initial file write still owed by NV, unavailable root or incomplete scan does not itself qualify. A file obstructing an owed write takes collision handling, not overwrite permission. A note with an accounted-for relationship is not offered simply because an extra file resembles it.

Each candidate must also match **one of its own active projection paths OR exact nonempty active projection byte values**. Never pool the path match for A with a content/date match for B. Keep the actual collision-adjusted direct-child filename and format/encoding with each represented value; reuse NV's filename-comparison and collision policy, rejecting ambiguous physical case/normalization matches. Do not reconstruct a pathname from a title. Compare exact encoded output bytes (using a verified digest as an accelerator), without newline/Unicode/whitespace normalization or platform RTF reserialization. Nonempty refers to the decoded body, not BOM/RTF framing alone. Unknown/unsupported encoding is not a failed-content match that permits fresh import.

The active comparison set consists of the current intended projection for the captured live note generation, including admitted pending edits, and the last accepted projection that an unfinished save/rename/format transition still needs to update or move. The latter is active transition evidence, not a scan of arbitrary historical paths/values. Its prior path/body stops qualifying when the newer exact projection is verified and the transition settles. Example: disk A, pending note B, external rename of A; exact A remains a repair-question clue until B's transition settles. Keep each representation's path/format/bytes coherent, retain the original physical expected snapshot separately, and never interpret a heuristic match as installation proof. If intended bytes are not yet prepared, prepare them asynchronously or defer that comparison; do not guess a negative result. Verified local scope IDs/handoffs and complete unique history-backed represented states retain their existing automatic path before this heuristic.

Concretely, keep a generation-tagged **accepted projection** and the current intended output, not a growing list of prior candidates. A save captures its input receipt/expected file, root/store, note/output generation and any source-path obligation. Installation alone does not advance the accepted projection: verify the exact destination bytes/mandatory metadata and account for the captured rename/move source under the existing safe-operation rules, then publish the new local receipt under fresh file/root/relationship checks. An unresolved source, a failed verification or a stale completion leaves the transition pending; it never permits unlinking an occupant merely to finish the transition. An installed intermediate output is tracked by that pending physical operation, not promoted into arbitrary historical matching evidence.

If A was accepted, B was captured, and the user has since requested C, successfully settling B may advance the accepted representation from A to B while C remains intended and pending. A then leaves the comparison set; B and C are the coherent active representations. Clear only B's exact pending generation, never C. Serialize physical transitions for a note through their source-accounting boundary; a delayed B callback cannot roll an already accepted C back to B. On restart, serialized receipts are observations only: revalidate the accepted file and reconstruct unfinished intended output from recovered note history before using a prior representation as an active candidate. No physical accessor or removal permission is recovered.

Do not add arbitrary historical-path/body searches, partial-text/title similarity, timestamps, raw out-of-scope IDs, or metadata voting to the v1 question predicate. Values filled from the candidate note by `_preparedNoteForCatalogEntry:fallbackNote:error:` are decoding defaults, not independent observed matching evidence. Present candidates separately with the actual reason (matching active filename or exact nonempty contents), even if several qualify or only one remains. Two simultaneous decisions targeting one note must revalidate its relationship/generation at admission; the second cannot attach an additional file or silently become an Import after the first repairs it.

### Pending-file decisions and association

Use a nonblocking pending-file/import indication, separate from Apple's Conflicts badge. **Associate with [note]** preserves that live birth and history; it does not promise to replace the note with the preview. If complete values agree, repair the association without an echo Put. Otherwise process an explicitly associated external edit using the retained trustworthy base and existing reconciliation rules. If that base is unavailable or the result needs review, show Current and the captured file value and obtain an explicit content choice before admitting changes; do not fabricate an ancestor, overwrite implicitly, or import into a deleted birth. A selected file value replaces only the applicable captured Current scope, not every unresolved head. Titles, labels, encoding and format follow existing external-edit semantics, with their consequences and any lossy conversion disclosed. Association itself grants no physical deletion permission.

**Import as New** always uses a fresh ordinary birth; retries of that action reuse it. Automatic ordinary imports have the same value/admission/durability path, with a distinct recorded reason rather than fabricated user consent. A pending snapshot that no longer matches a current readable file can be explicitly recovered as a fresh note, but not automatically imported or attached on the strength of its former path. Reappearance is freshly classified; a new occupant cannot inherit old approval.

Coordinate a plausible replacement's review with its candidate note's unexplained-missing-file decision. Keep the note while that combined decision is pending; do not simultaneously apply an absence-based Delete behind the association choice, including under disabled deletion confirmation. Successfully accepting association clears that missing-file candidate. Importing separately leaves the old note under the existing revalidated confirmFileDeletion policy. An applicable committed Delete supersedes the pending repair rather than being blocked by it; restoration thereafter needs a fresh birth. Unrelated notes, ready history and editing continue.

Closing/leaving the interface means **decide later**; it neither imports nor abandons retained bytes. Reopening re-observes and starts another bounded dependency/validation attempt; elapsed time never converts a known exception into automatic newness. Changed note/file/provenance/history/root inputs refresh the preview and invalidate stale approval before admission. Late completion cannot reopen a dismissed view or alter a newer selection. Explicit abandonment releases only unadmitted recovery material after clear disclosure; it does not delete the external file, cancel admitted work, or create a permanent filename-ignore rule.

### Pending-file retention and retry identity

Keep one **latest pending snapshot** per locally tracked pending file plus exact inputs referenced by unfinished admitted operations. Latest means latest successfully read and validated local observation, not greatest timestamp or globally newest provider state. Replacing a preview is not archiving every intermediate external save. Track a pending item by a private random ID and freshly applicable observations; filename/digest equality alone cannot join contradictory file incarnations. If continuity is ambiguous, preserve the old pending evidence separately from the new candidate.

Use immutable bounded pending BLOBs in the private database for exact source bytes plus observed format/metadata/presence and source scope. Generation-tagged latest/frozen references, status and reservations are required Local State rows. Payload/reference replacement shares a transaction; there is no new NV WAL, provider sidecar or replayable note command. These private recovery buffers are not purgeable cache or backup-excluded staging.

Replacement order is: verify/capture new bytes → atomically commit the new payload and generation-checked latest reference, preserving frozen references → release only superseded unreferenced payloads. Failure/crash before the reference switch preserves the previous snapshot; an unreferenced final snapshot is not consent or the newest preview merely because its timestamp/name is larger. A failed read, eviction or disappearance retains the last readable snapshot. A first retention failure reports the affected item as unsafely retained/unavailable for completion, rather than claiming a durable preview. Budgets bound work/allocation per pass; they cannot silently expire referenced snapshots. Pending-file failure alone must not close the healthy edit gate for unrelated notes.

For a new history operation, reserve the prospective birth (for a fresh import), action identity and operation nonce in the private pending record **before admission**; bind the prepared operation to the exact captured snapshot, note scope and causal inputs. This is a reservation, not consent or a completed note operation. Final admission still revalidates file/root/store/catalog, structural/note/relationship generations and captured history; changed inputs reject stale preparation. Once admitted, the operation's exact inputs remain pinned while newer verified file contents may replace the separate latest-preview slot. Do not overwrite those inputs, reseal different bytes under an existing operation ID, or allocate a new birth merely to retry an uncertain completion.

For an Import or content-changing association, complete the normal immutable operation/action/parent and retained-pin barrier. For a content-neutral association there is no new Put or ActionRecord: require the captured Current's existing represented history/closure to be locally durable instead. Then freshly validate the physical association and durably install its local receipt while settling/removing the corresponding pending reference. A source changed meanwhile is subsequent work; do not falsely record the old snapshot as the current installed file. Until continuity is settled, retain the pending operation link so a rescan cannot import that same observation again. Only release its frozen input after its value is safely represented in durable history and any still-required pending/association evidence has a durable owner.

On restart, recover complete history first and reconcile reservations/pending links against actual committed birth/action/operation evidence before processing fresh-import candidates. A committed import whose receipt/callback was lost resumes association using the existing birth. A reservation or preview with no committed operation reopens as undecided/revalidation work, never replayed manual consent; a newly valid automatic-import decision may reuse the reserved unused birth. Old physical authority never survives restart. Missing or contradictory private evidence is a recovery/association ambiguity, not permission to allocate endlessly or deduplicate all equal-content files.

Pending snapshots remain private recovery buffers until admission, not portable note history. Preserve their references/bytes across ordinary quit, root switch and fresh-sibling private-store repair; closing a view/collection is not abandonment. Provider-only reconstruction cannot recover a snapshot whose external source and private copy are both gone. Report that loss separately without claiming loss of a committed note or discarding other available evidence. Repository-only Save As copies the available repository, not these private buffers; keep the source buffers usable and disclose outstanding local-only pending recovery rather than silently treating a repository copy as their backup.

### Pending-file commit and recovery records

These are required semantic fields within the private database's pending-payload and Local State roles, not another provider protocol. The [format checklist](Format-TODO.md#7-host-private-formats) governs their bounded canonical encoding and vectors; [LocalStore](LocalStore.md) supplies page protection and transaction boundaries.

| Private record | Required contents and meaning |
| --- | --- |
| Immutable pending snapshot | Random snapshot ID, exact source bytes, observed metadata **and presence/absence**, format/encoding validation, collection/local-store scope and captured observation. Record raw observations separately from decoding defaults. A captured path/file token is historical evidence, not portable identity or replayable authority. |
| Pending item in Local State | Random item ID; item generation; latest-snapshot reference; classification/dependency status; outstanding reservation/frozen-input references; any committed-operation link not yet transferred to a durable receipt/settlement record. The item generation fences delayed preview/reference completions. One item may have an admitted older input and a newer preview. |
| Prepared reservation | Decision kind (automatic Import, explicit Import, or association with disclosed content choice); target/fresh birth as applicable; frozen snapshot; references/digests binding the exact resulting note value and represented Current/causal/action inputs. Large values belong in referenced pending payloads or immutable history, not inline in the small Local State record. For a new history operation, reserve action ID and operation nonce and record the canonical semantic identity needed to locate that exact operation after restart. For a content-neutral repair, record the existing represented-state references instead; do not manufacture a note action. |
| Receipt/settlement in Local State | Link to the pending item and admitted operation, or existing represented state for a no-op repair; actual installed/associated projection tuple and local observation; accepted output/relationship generation; remaining subsequent-file work. Settling an observation means it was already admitted, not that its birth must still be live or its file unchanged. |

Prepared process-local validation frames and provisional relationship claims are separate from these durable records. A reservation's decision label is not evidence that a manual command was admitted. A new preparation with different semantic inputs cannot silently reuse an operation ID/nonce for different bytes; reconcile uncertain old completion first. An unused reserved fresh birth can be retained across re-preparation, while the changed operation preparation receives its own identity. Receipt indexes are derivable accelerators over durable item/history records, never the only record of an admitted observation.

**Snapshot/reference transaction.** Bounded encoding/capture precedes a short database transaction that inserts the exact immutable payload and switches the generation-checked latest reference while preserving all frozen references. Commit before making superseded unreferenced bytes collectible. Rollback preserves the prior payload/reference pair; an ambiguous completion is resolved by querying the committed item generation and exact identities. Retain in-flight inputs until resolved. Never treat an unreferenced payload or a reservation as consent, or choose the latest snapshot by timestamp. Receipt installation and pending settlement likewise share one transaction, not separate private file replacements.

**Association admission and completion.** After asynchronous preparation/reservation, atomically revalidate and publish the note mutation (if any), ordinary pending history, and a provisional per-note relationship claim in the existing model-publication transaction. The claim changes the relationship generation, so a second prepared file choice must be reevaluated rather than attaching another file or turning into an Import. It is not an accepted projection receipt. Keep the combined missing-file decision suppressed while this admitted repair is unfinished; a committed Delete is never suppressed. Complete history durability independently of UI visibility. If the source already exactly represents the chosen output, freshly verify it without rewriting it. If keeping Current or merging produces different output bytes/metadata, use the normal expected-snapshot file-save path and verify that result before committing the receipt; a note-history barrier alone does not prove that the physical file contains the chosen result. Receipt installation and pending-item settlement share one database transaction. Publish the completed relationship/missing-file settlement only for that still-current claim.

| Intervention / failure | Required continuation |
| --- | --- |
| Input, target, root, history or another claim changes before admission | Reject that preparation without mutation. Refresh/review; never reinterpret its click. |
| Snapshot/reference/reservation storage fails | Retain the prior durable reference and all still-owned inputs, report/park the affected item, and retry boundedly. Do not claim a safely retained first snapshot or a completed admission. |
| History barrier fails after admission | Keep the exact admitted value in ordinary pending history and its frozen input; normal local durability failure policy applies. Do not install a completed receipt or allocate a replacement birth. |
| Projection changes or cannot be installed after history is durable | Keep the admitted history and pending link. Preserve newer source bytes as subsequent work; reobserve/reconcile, never overwrite with stale approval. Ordinary editing/UI dismissal remains independent. |
| Logical Delete arrives during review | Invalidate the old-birth choice and release its live claim; retain readable input for explicit fresh recovery. |
| Logical Delete arrives after admission, before receipt | Finish durability of the already admitted operation with its captured pre-Delete causal inputs; do not re-admit into the deleted birth or publish its stale association. Normal causal Delete/edit rules decide the note/conflict outcome. The input remains represented in history; any unadmitted newer preview keeps its own retention. |
| Receipt replacement fails after history/file success | Preserve the exact operation link; retry fresh validation plus the same receipt/settlement, not the note mutation. An existing UUID alone is insufficient evidence. |

**Restart and repeat scans.** Before a fresh-import decision for an affected item, validate installed immutable objects and recover the exact operation/action/parent closure, including committed work whose callback was lost. Resolve ambiguous SQL outcomes and drain indexed acceptance work before treating newly applicable input as accepted history. Match the reservation's exact semantic operation evidence; do not ask only whether a live note with that UUID exists. A later edit or Delete of that birth does not make its earlier Import uncommitted. Keep its observation settled and classify an actually changed/restored file separately. Reacquire root/store and current file evidence before any association attempt; never deserialize a usable accessor or consent frame.

If no complete operation exists after that recovery, an uncommitted reservation returns to undecided/revalidation work. Partial/unknown/corrupt evidence parks recovery, not a speculative fresh allocation. A content-neutral repair interrupted before its durable receipt likewise needs fresh automatic evidence or a renewed manual decision; the existence of its old Current is not proof that a click completed. A committed operation with no receipt resumes only association/settlement using that same operation and birth. Atomically transfer the consumed-observation link to the receipt/settlement before removing its pending link; then release obsolete inputs only when their exact values are owned by history or another retained pending reference, or the successfully completed disclosed decision explicitly settled against retaining that input (for example, keeping Current instead of the preview). That last case is not permission to discard a newer unreviewed snapshot. Repeat this procedure after every crash, not only the first restart. Ambiguous physical continuity keeps an item pending; it neither globally deduplicates equal files nor grants permission to revive a deleted imported birth.

### Advisory event prioritization

Current/historical FSEvents can reorder which candidates and dependencies are inspected first, alongside already-known history. They do not change the decision predicate, advance a shared occupancy token, prove continuous incarnation or deletion intent, trigger an extra question, or authorize alias/write/removal. Scope event IDs/paths locally, fall back to normal discovery on missing/gapped/asymmetric replay, and still complete the required inspection. Repeated/late hints alone do not restart an otherwise valid attempt or spend all retries; an actual changed file/root/history observation does invalidate it. No historical event log becomes required durable state.

**Deferred narrow co-add candidate — not enabled by normative adoption.** Two clients could deliberately identify independent imports as one logical slot only when both share the same genesis, the same exact parent token for an unoccupied managed relative path, and the same filename normalization policy. Define that token from the path and the preceding committed occupancy/retirement operation IDs. An initially empty path uses the genesis as parent. Derive the import birth from a domain-separated hash of collection ID, path bytes, and this slot-parent token; truncation/UUID formatting and its distinct namespace must be fixed in codec vectors. Unlike ordinary births this is deterministic. The reserved-UUID classification must come from the creation kind/domain, not simply “all version-8 UUIDs are recovery notes.”

Concurrent imports into that identical slot have one birth and potentially multiple value heads. Different known parents, case-folding ambiguity, rename uncertainty, missing shared bootstrap, or a retired slot do not qualify. They receive separate identities pending explicit reconciliation. Restoring a deleted path never reuses the old slot token. This policy intentionally equates simultaneous additions to one agreed logical path; it does not claim that two physical files were the same file. It requires new tests/models before adoption and does not retroactively alias arbitrary existing UUIDs. Explicit ordinary creates with equal titles always remain distinct and receive collision-adjusted filenames.

The [co-add experiments](../tla/CoAdd-Policy-Experiments.md) now compare intent-preserving matching, occupancy-event versus release tokens, and late deletion/restoration. Their conditional results and counterexamples refine the investigation, not this adoption status. Dynamic occupancy/import composition, concrete encodings, UX consent and an explicit policy decision are still required; do not enable co-add or change Import as New from these model passes alone.

The [historical-hint revalidation follow-up](../tla/CoAdd-Policy-Experiments.md#historical-hints-and-revalidation--coaddrevalidationlab) supports the adopted advisory prioritization rule above. Its experimental episode histories and exact file/root/history fences remain inputs, not a physical-incarnation guarantee or an implementation of occupancy recording. Historical replay itself remains optional.

The [external-import investigation](../tla/External-Import-Policy-Experiments.md) compares the adopted narrow predicate with rejected/deferred wider rules and connects it to admission, late history and crash recovery. Its late-duplicate outcome is intentional. The current decision matrix and retention sections above are the adopted policy; alternative survey rules do not become implementation options. See Verification for the exact updated model boundaries and remaining production tests. Co-add is still disabled.

An NV deletion first records and locally persists `Delete` with its closure. Only the original captured, still-matching source file operation may then remove that local file. An incoming delete may remove the known logical note, but does not issue a blind unlink at its remembered filename. The provider normally propagates the originating physical removal independently. A retained/replaced/stale file is preserved and surfaced as above; no startup tombstone sweep deletes it. The lower-level deletion helper must recheck expected identity/content and root at the final operation, including after a provider callback delay. An old authority token is invalid after a crash.

External deletion confirmed by the user becomes an explicit `Delete`; choosing Restore keeps the birth if there is no committed delete and recreates the file through exclusive creation/safe replacement as applicable. If a committed delete arrived meanwhile, restoration creates a fresh birth instead. With confirmation disabled, an accepted external disappearance may generate `Delete` under that explicit preference. Merely receiving someone else's already committed delete does not generate an echo delete.

## Snapshots, startup, rejoin, and retention

Returning startup loads the private database's complete current-note rows and compact ordinary-edit authoring context. The packed startup cache and its format, construction/publication and delta bookkeeping are removed. The [benchmark](plan/remaining-storage-validation.md#startup-remove-the-packed-cache) found no meaningful benefit from maintaining a second representation.

Use canonical bounded current-cell/context codecs, not archived Cocoa objects or nested provider envelopes. Capture complete rows/context, represented acceptance prefix, scope and view epoch in one read transaction. Construct all current note/search values before input; historical queries and candidate indexes may load relevant evidence later. No asynchronous live search or lazy current-body loading is introduced.

Required history acceptance and derived materialization have separate transactions and failure consequences. Failure to materialize cannot clear pending notes, retract accepted history, permit history pruning, reset settings or fail an otherwise durable quit. Catch up or reconstruct invalid rows before editable reopening. No persisted derived result restores physical authority.

Local State independently persists association/bootstrap pin, retained-history pin, preferences/UI state and generation-tagged receipts in the database. Its pin contains required descriptors and maximal accepted segment locators; that closure must remain retained. Acceptance/pin advancement commit atomically without stale settings replacement. Failed settings updates are reported separately from previously durable history; failed root/key association blocks that transition. Missing/corrupt required state requires its recovery path, never a association inferred from derived rows. Portable undo remains retained history, not private cursor state. [LocalStore](LocalStore.md#database-keys-and-password-free-recovery) defines the public or CK-derived database key and minimal external wrapped-key descriptors. Password-free recovery has no device-secret dependency; the concrete production credential adapter remains a qualification gate.

Acceptance can lag stored candidates, and materialization can lag acceptance. [The startup algorithm](LocalStore.md#concrete-returning-launch-algorithm) drains durable ready work and catches up current rows, including deletions and body-equal authoring-context changes, before a consistent full-row capture. Publication rechecks local owner/history/view generations. Local sequences are private transaction ordering, never causal identities or provider coverage. No full-history scan is mandatory on a healthy returning launch; known damage or invalid materialization uses exceptional repair/rebuild, never editable emptiness.

Exact history acceptance and pin advancement share one local transaction. Stored-but-parked objects may become applicable later; missing known accepted evidence is positive damage and blocks complete editable recovery. Prior validated acceptance is reused without eagerly rereading all history; newly discovered damage cannot be ignored because current rows are healthy. Compact the pin only by removing a locator proven to be an ancestor of another pinned locator; never use a snapshot, upload or derived-view coverage to prune its required closure. Required same-key descriptors remain pinned explicitly.

### Repository and private-store repair protocol

The concrete private SQLite mapping is [backup, salvage and replacement activation](LocalStore.md#sqlite-backup-salvage-and-replacement-activation): consistent keyed backups, preserved original DB/journals, revalidated working-copy salvage, unique private-state retention and reopened fresh-sibling verification before selected-store cutover. SQL recovery output cannot supply trusted acceptance or resurrect old consent. This implements the following common policy without adding a per-edit sidecar pin or provider metadata directory.

Use one value-only health classifier for both storage sides. Its immutable result records side, captured root/store incarnation, non-followed entry kind, readable/materialized/writable status, compatible collection/profile, exact validated objects, invalid/colliding entries, the surviving retained-history pin, missing dependencies, and any positively disclosed newer/required provider item whose exact bytes are not locally readable. Raw `NSError` and provider status accompany the result for presentation/backoff only. Revalidate the captured root/store generations before every repair effect; a stale result installs nothing further.

Form the repair union from exact validated local, provider and explicitly selected backup objects. An object is copied, never decoded/re-encoded or resealed under its old locator. Verify source bytes, then use the destination's qualified durability path: private SQLite acceptance/index/pin transaction, or provider exclusive installation/file/directory barriers and exact readback. The database file itself is never provider transport. A same-name symlink, directory, foreign bytes, incompatible bootstrap or permission-ambiguous entry is not “missing”; preserve it and return a collision/access result. Missing entries never retract accepted history. When the copies are complementary, build the private closure first so further local work has one complete durable base, then republish missing provider objects.

An existing compatible `NV Data` permits automatic exclusive recreation of missing owned protocol subdirectories and exact missing immutable files. Positively observed local loss of the top-level `NV Data` uses that same automatic path when the root is still positively the same, the private retained closure is complete, the parent is writable, and no unread newer/required provider evidence has been positively disclosed. Revalidate same-root ownership and top-level absence, exclusively create it, copy every validated retained descriptor/object, verify the complete known closure, then activate publication. There is no user Restore control or consent state. Crash/retry reuses the exact objects and treats equal verified results idempotently. Appearance of any entry or authority change cancels further installation and returns to classification.

For a captured corrupt or wrong-kind owned entry, build and verify the exact replacement before mutation, preserve the displaced evidence, and compare-and-swap only the captured generation. Never replace a foreign/incompatible, symlinked, identity-ambiguous or concurrently changed occupant. If preservation or installation is impossible, retain the healthy private closure and report the repair error/Save Current Collection As… instead of converting it into Work Offline.

Work Offline is available only during startup when positive item/version metadata already discloses newer/required provider evidence absent from the complete local closure and its exact bytes remain unmaterialized or unreadable. Do not wait for discovery to decide whether this gate exists. Later disclosure cannot revoke active local editing or demand this choice; an evicted provider copy of bytes already retained locally is not missing evidence. It records no claim about that evidence and grants no overwrite/disposition authority; it merely allows the complete private closure to remain editable while materialization is deferred. Generic provider unavailability, quota, permissions, coordination failure or root-identity uncertainty pauses/retries provider effects without showing Work Offline. A compatible repository that later becomes readable is validated and unioned normally.

Never mutate a damaged private store in place. If its parent permits private storage, allocate a fresh sibling `localStoreID`, copy the repair union into a new database, validate complete closure, build its current materialization and durably commit the recovered association/pin before switching the live session with fresh action-origin and writer-epoch allocators. Preserve the old store for explicit later inspection. Loss of Local State requires explicit repository selection/association and fresh settings/physical receipts; orphan segments may join only after collection and closure validation plus user confirmation. Validated revisions, action origins, scope-parent edges and compensation records rebuild Note History and portable causal Undo/Redo. Only native `NSUndoManager` grouping/selection is lost. Derived rows and proven owned disposable staging may be discarded; the database containing retained history/private state may not.

The retained-history pin is independent of that undo decision. It commits the maximal accepted segment closure that this private store must retain; it contains neither an undo cursor nor note values. If Local State is totally lost, no old pin remains to prove which locally accepted but unpublished leaves once existed. Rebuild from the repository's validated disclosed closure, create a new pin for that closure, and preserve all recovered action records as history without claiming undisclosed or erased leaves.

If the Application Support parent cannot host a fresh store, or a required pinned object has no exact copy in any available source, keep new mutation disabled. Offer Retry, another Mac/backup, or a current-notes recovery export only when the live values being exported are complete and explicitly disclose that it creates a fresh collection without old history. Provider-only access/write failure never closes an otherwise healthy local admission gate. Exact ciphertext may be preserved while locked; it does not permit editable activation without the key. No repair claims all-provider completeness, and erasure of the same unrecorded bytes from every source is unrecoverable and potentially undetectable.

Provider snapshots are immutable optional acceleration objects, not the canonical database. A snapshot root names its complete set of bounded snapshot pages, a represented frontier, and exact dependency locators. Pages contain full note state and the causal/retirement indexes required for faithful reduction. A root is usable only when all pages authenticate, counts/hashes match, and the referenced history is available locally or explicitly pending. A newly bootstrapped client may display a complete authenticated snapshot read-only while its closure is fetched; editing begins only after durable local closure, not merely after receiving the page with the selected note.

Do not choose a “latest” snapshot by wall time, sequence, or filename. Any complete valid snapshot can accelerate reconstruction of its stated frontier; union additional disclosed branches. Never roll back below a surviving retained-history pin or other independently established accepted-history evidence. After total private-state loss, the newly selected repository's validated disclosed closure seeds a fresh pin but cannot prove that the provider is not hiding another valid branch. UI must say “available history,” not “all devices synchronized.”

Initial import uses a pinned genesis plus dependency-linked import batches, an `ImportComplete` operation, and a final complete snapshot root. Before creating genesis, capture the initial note values and compute their canonical count/digest; verify that commitment against the completed import closure. A large collection is not split into partially editable unrelated genesis files. The descriptor pins genesis, `ImportComplete` depends on the import batches, and the snapshot frontier includes that completion: there is no reference back from completion to the snapshot hash. New changes may be learned later, but an interrupted *initial collection creation* is not a valid empty or partial success.

The [executable initial-import validator](plan/first-save-reopen-contract.md#executable-initial-import-validation)
now checks this initial evidence across real envelopes, action groups and snapshot
pages. Its result is not local durability, selection authority or a complete
current view when later history exists. General reduction and Runtime activation
remain separate gates; returning launch keeps its indexed current-row algorithm.

Rejoin is fully app-level: restore the local snapshot/segments, allocate a fresh writer epoch, discover and union available remote immutable history, and reduce from exact parents. With no history collection or membership protocol, an old authorized replica remains a legitimate branch source; it cannot resurrect a deleted birth once it has accepted its delete, but concurrent unobserved work remains preservable. No File Provider API can supply a global join barrier. Device loss before any copy was published loses unpublished data unless a backup survives; do not imply otherwise.

V1 retains all final accepted/sealed local history, provider segments, and descriptors. New snapshots can reduce launch replay cost; they do not bound total storage or file count. Limit only individual object sizes, in-memory batches, concurrent downloads, and untrusted unread objects. A user-authorized migration to a **new collection** can discard old logical history by exporting complete current state; old clients remain attached to the old collection and must explicitly switch. In-place pruning, device acknowledgments, membership leases, and old-writer fencing are separate future protocols, not hidden implementation tasks.
