# Introduction

This is Notational Velocity, a legacy Objective-C Cocoa note-taking app targeting macOS 11 through the latest version of macOS. It currently uses manual reference counting (MRC). The script `build.sh` builds the app using the current Xcode workspace and outputs any errors and warnings; run it after completing any significant set of changes. `docs/IntegrationTests.md` describes the integration test suite and how to run it. The `tests` directory contains the source code for the integration tests, which are built and run using the provided Makefile commands.

The goal of Notational Velocity is to offer extremely low latency note-taking with a keyboard-centric experience with search being the primary interface; the UI is a single window with a search field at the top and a note list below it. The note list is filtered in real-time as the user types in the search field, and the selected note is displayed in an editable text view. The reasoning behind this design is to allow notes to become self-organizing, by showing related notes as the user types the title of a new note. For a rationale of why NV lacks other features, see `NV_Philosophy_Interview_QA_2010.txt`. Secondary goals include security, privacy, and data durability. Data is expected to be sensitive, and not visible to other applications by default.

# Implementation details and Rationale

To these ends, the app keeps all note data in memory, enabling a scenario where cleartext note data never need touch the disk. NV's in-memory data store is authoritative even when the option to store notes as plain text files is enabled (changes to separate files are synced transactionally back to the in-memory data store -- see `NotationDirectoryManager.m`), and the authoritative in-memory data store is serialized atomically to disk (the "Notes & Settings" file) upon quitting, with a write-ahead log ("Interim Note-Changes") checkpointing mechanism to ensure that no data is lost in the event of a crash or power failure. All file access is intentionally path-independent, permitting for the notes directory to be moved anywhere on the volume with no PATH_MAX limit, and at any time without breaking file reading, saving, or renaming (see `NVRootedDirectory.m`). See `docs/Atomic-Note-Saves.md` for the "compare-and-swap" algorithm currently implemented in that class and the various file system limitations. Note that the implementation described therein shall be superceded by the one in `docs/Foundation-Safe-Replacement-Migration.md`.

Search results are currently updated as the user types, within the same runloop/view-refresh cycle, and the in-memory search algorithm is more than fast enough to support this. Any form of asynchronous/background search implementation decoupled or debounced from user input is strictly prohibited and is to be considered a violation of the app's design principles. Likewise, the app must be ready to accept user input as quickly as possible upon launch, and show its notes immediately. This combination of in-memory loading and searching generally rules out loading the full contents of all individual note files from disk at launch. The "Notes & Settings" file facilitates quick launch by way of its fast NSKeyedArchiver deserialization.

# iCloud Drive synchronization

`docs/iCloud-Drive-Support-Spec.md` is the normative design for first-class iCloud Drive support, including immutable history, local durability and recovery, plaintext projection reconciliation, causal deletion/conflicts, private startup state, provider fencing, quit ordering, and storage transitions. `docs/adr` records the architectural decisions and rationale behind that design. `docs/tla/README.md` is the entry point for the associated TLA+ models, their coverage boundaries, configurations, exhaustive checks, and model-specific negative controls. `CONTEXT.md` defines the canonical storage and reconciliation vocabulary used by the specification, ADRs, models, and implementation.

Changes affecting iCloud Drive synchronization or durability must be checked against all four sources. Keep their terminology and assumptions aligned, update the relevant written requirements and models together when behavior changes, and run the applicable TLA+ configurations described in `docs/tla/README.md`; do not weaken or remove a modeled safety condition merely to make TLC pass.

Additionally, check `docs/Apple-API-Contract-Validation.md` whenever a change relies on or alters an Apple/File Provider behavior or fallback, and check `docs/Foundation-Safe-Replacement-Migration.md` whenever a change affects existing-file replacement or a checkpoint-installation caller. These are conditional implementation-contract checks, not additional normative authorities for unrelated synchronization edits.

The current work-in-progress implementation design is under `docs/impl-proposal-5/README.md` and follows the adopted immutable-segment specification and ADRs with an implementation plan for an NVStorage portable Swift library currently underway at `docs/impl-proposal-5/plan/swift-storage-implementation-plan.md`. swift-storage-conformance-testing-strategy.md defines contract IDs and their testing strategy. Proposal 4 and its checkpoint/WAL-specific models are retired references, not modern implementation authority. The earlier implementation description above still describes the legacy source path; segment collections use local immutable history, private derived current rows and required private state in SQLite.

These are major refactors to modernize the codebase and Swift may be used for brand new abstract/model classes of large complexity, especially where its more advanced static typing can be used to encode consistent and correct business logic at the compiler level. However, SwiftUI *shall never be used for note interaction* and any code dealing with note searching, editing, table selection/interaction, NSResponder chain use, or other any other core keyboard-centric interactions shall not be touched. Any code that could have an effect on these UI concerns requires explicit human sign-off, review, and testing to ensure behavioral correctness.

New code, especially the NVStorage library, should make maximum use of the Swift language's strong typing to ensure correctness and consistency of the business logic. NVStorage in particular already has a proposal along these lines specified at `docs/impl-proposal-5/plan/swift-storage-library-proposal-v2.md`.

# Backward compatibility

There is no intermediate epoch-5 or segment-collection-based compatibility necessary; the last public release used the epoch-4 Notes & Settings file as the authoritative note store and was years ago. As a rule, if you don't see a commit on origin/master, then it hasn't been incorporated into a public release and no one is using it. Keep epoch-4 Notes & Settings opening/recovery and explicit legacy-export compatibility, tested by `tools/test-epoch4-v5-compatibility.sh`. New segment history, private state and current-row formats have no epoch-4-readability requirement and create no live compatibility archive. No safe mixed-version writing to a segment collection is promised.
