# Reuse the existing sync quit barrier for iCloud upload

iCloud checkpoint availability and upload status will participate in `SyncSessionController`'s existing uncommitted-change waiting, status, error, and explicit quit-override behavior rather than introduce a second quit UI. Termination first rejects new edits and sync work, lets already admitted model mutations finish, drains presenter callbacks and provider work through a stable final reconciliation barrier, settles journal and separate-file durability, and installs the single exactly verified quit checkpoint. It then uses `waitForUncommitedChangesWithInvocation:` to await upload confirmation.

On macOS 26 and later, NV prefers an explicit ordering path when the checkpoint advertises pause-sync and fail-upload-on-conflict support: pause `Notes & Settings`, install it through a short coordinated replacement, explicitly upload that stable version with fail-on-conflict policy, verify its returned `NSFileVersion` and `checkpointID`, resume with preserve-local-changes behavior, and only then coordinate deletion of the WAL. The network upload never runs inside a coordinator accessor. This establishes server acceptance of the database before NV issues the separate WAL deletion without claiming a cross-file cloud transaction.

Unsupported controls or failure to acquire the pause fall back to ordinary coordinated installation and File Provider synchronization rather than failing quit. After a successful pause, NV attempts resume on every path. Upload conflict, upload failure, returned-version mismatch, resume failure, override, or ambiguous status retains the WAL and active record for that quit attempt; if synchronization can run, it continues normally, and a later exact upload may clean up the retained WAL through recovery. A resume failure may leave the item paused across process death, so startup checks the native paused-state resource value and resumes before evaluating checkpoint freshness; if the user works offline, the existing sync controller retries resume. No custom pause ledger is introduced.

Older systems may qualify only a complete post-install not-uploaded/uploading-to-uploaded transition followed by exact coordinated local read-back; this is compatibility evidence rather than documented version-bound server proof, and any ambiguity remains unknown. Confirmed or permitted qualified upload allows WAL removal. Every failure before checkpoint installation uses the same retry-or-explicit-override result while preserving the previous checkpoint, journal, and active record. Because the checkpoint is currently written later in `applicationWillTerminate:`, that write must move before the iCloud wait and must not be repeated by a reentrant termination callback or after upload confirmation.
