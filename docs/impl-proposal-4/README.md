# iCloud Drive implementation proposal 4

Status: retired implementation reference. The current normative specification and ADRs adopt [proposal 5](../impl-proposal-5/README.md). This document's active-WAL/shared-checkpoint/automatic-absence rules are not instructions for segment collections; retain it only for source/migration comparisons and the explicitly retired model suite.

This proposal implements the normative [iCloud Drive specification](../iCloud-Drive-Support-Spec.md), including ADR-0013's host-local WAL and ADR-0014's current-visible synchronization with explicit embedded conflict disposition.

## Design in one page

Keep the existing live in-memory store, separate-file writer, pending-write sets, merge logic, `SyncSessionController`, and rooted-directory abstraction. Add one private `NVRootSession` to serialize provider access and stale-completion fencing. Move modern WAL files to a dedicated local Application Support directory and keep WAL append/barrier work on an independent serial queue.

Routine provider reconciliation reads only current visible note files. It takes a coordinated shallow catalog, reads selected current files, takes a second catalog, and publishes only when catalog, root session, structural generation, and note UUID/LSN fences match. It never enumerates `other` or nonlocal history and never automatically resolves an `NSFileVersion`.

When Apple reports unresolved versions for a visible note file, NV shows an alert badge. Clicking it swaps a read-only `ConflictResolverView` into the editor split-view subview in place of `LinkingEditor`. **Use this version** sends the previewed body through the original note's existing mutation/save path; **Save as new note** creates one deterministic ordinary conflict note. The applicable disclosed members are marked resolved only after the resulting note generation is both WAL-durable and exactly installed as a separate file. Per-version work may continue after the resolver is dismissed; NV never removes provider history.

The local WAL is self-describing through its header bookmark and checkpoint base. Startup locks the already-open root-directory descriptor before scanning the Application Support recovery directory for matching WALs; there is no lock file, `CFPreferences` registry, active/retained role, shared journal, upload-qualified cleanup, or cross-Mac WAL recovery. A locally verified covering checkpoint is sufficient to delete the local WAL, but directory-lock ownership continues through cleanup and final teardown.

Provider identity is positive-only. `NVRootSession` stores an opaque item/domain pair when forward lookup succeeds and otherwise remains unclassified; it never attempts to prove ordinary-local storage or reverse-resolve an item identifier. Root disturbances either revalidate the same rooted object from existing candidate-URL evidence or enter a nonterminal unavailable state. An unavailable session is restored only by positive recovery and ended only by an explicit user choice; a positive authority change still fences it into the provisional-successor path below.

If a closing checkpoint attempt returns `NVCheckpointInstallCurrentChanged`, use the exact current checkpoint only as a three-input note reconciliation source: retained accepted checkpoint, complete live note set, and captured complete current checkpoint. Infer a branch deletion only when its exact base contains the UUID and that complete branch omits it, union the two retired deterministic conflict identity sets, ignore the competing checkpoint's preferences and other database-level metadata, settle every published note/deletion obligation, and retry once against the captured exact predecessor.

## Components

### `NVRootSession`

One instance represents one active authority incarnation and owns:

- the `NVRootedDirectory` owner of the already-open, exclusively locked notes-directory descriptor, plus its file-reference URL and bookmark; no separate lock-file descriptor;
- positive provider-managed authority plus opaque item/domain identity when available, otherwise unclassified authority;
- one serial `NSOperationQueue` backed by one serial dispatch queue for presenter callbacks and provider operations;
- one root-directory presenter registration, root vnode source, FSEvents stream, ubiquity-identity notification token, and operation-local URLs supplied by presenter move callbacks;
- note and artifact dirty generations, the last accepted catalog and retained presenter-move candidates, one structural generation snapshot, and cancellation/closing state;
- the current host-local WAL descriptor and independent WAL queue;
- non-owning notification/UI target links cleared before teardown.

It may retain an in-flight disposition operation only until that operation succeeds, fails, parks until resolver re-presentation, or the root session ends. It does not own a persistent provider-version set, resolution map, journal claim registry, upload receipt, or provider profile.

Create a fresh `NSFileCoordinator` for every operation. Never block the provider queue waiting synchronously for an asynchronous Apple completion. Completion blocks retain only immutable inputs plus the root session and reenter the provider queue before publication.

Only the main thread mutates or constructs `NotationController`, `NoteObject`, `DeletedNoteObject`, the retired deterministic conflict identity set, `NotationPrefs`, selection, or search state. Provider/WAL work returns copied immutable values for fenced main-thread publication; it never dereferences a mutable live note after dispatch. Under MRC, queued blocks copy their immutable inputs and retain the root session that owns the operation, while UI/notification targets remain non-owning and are cleared before teardown. A coordinator accessor copies every needed byte/value before returning and never dispatches later filesystem access through its borrowed URL. Every presenter accommodation and asynchronous Apple completion is invoked exactly once on every success, failure, cancellation, and exception path.

Keep the root session's callable surface limited to opening/positive authority discovery, capturing or enqueueing prepared current-visible and note-write attempts, marking note/artifact state dirty, quiescing, installing a checkpoint, and closing. Reconciliation remains private to `NotationDirectoryManager.m`; WAL implementation remains private to `WALController.m`. Do not restore proposal 3's provider participant or version-history interfaces.

The one presenter covers the root directory and implements `presentedItemURL`, `presentedItemOperationQueue`, root move/change/deletion accommodation, direct-child appear/change/move/delete, version gain/loss/resolution, and applicable ubiquity-attribute callbacks. Each callback does only bounded bookkeeping and schedules later observation. Implement reader/writer relinquishment as an immediate acknowledgement with a nil reacquirer while NV has no temporary in-memory ownership to surrender; invoke each supplied block exactly once. Do not register per-note presenters.

### Root-event ownership and lifecycle

All root-scoped event inputs enter the root session's serial provider lane. They are wakeups and candidate evidence only; no callback or elapsed time is a visibility, deletion, or completion fence.

| Input | Ownership and immediate response | Later proof/action |
| --- | --- | --- |
| FSEvents | `NVRootSession` owns the stream on its provider queue. Remove `kFSEventStreamCreateFlagIgnoreSelf` when writes move off-main; an event from NV's own write schedules at most an idempotent follow-up. | Advance the applicable dirty generation and require a fresh coordinated catalog. `RootChanged` rebuilds the stream from positively revalidated candidate evidence, never from a stored path. |
| Presenter create/change/move/version callback | The root-session presenter records direct-child move URLs as operation-local candidates and advances note or artifact dirty state. A version gain/loss/resolution callback for the selected visible note also schedules the advisory conflict probe. | Current visibility comes only from a later stable catalog/read transaction. Callback URLs join the authoritative candidate set but do not bypass identity matching. |
| Root vnode `RENAME` | A `DISPATCH_SOURCE_TYPE_VNODE` source watches the already-open descriptor on the provider queue. | Evaluate rooted, presenter, file-reference, and bookmark candidate URLs with the forward-provider/root matrix. |
| Root vnode `DELETE` or `REVOKE`, or presenter deletion accommodation | Freeze provider publication and begin positive continuity evaluation. Invoke the accommodation completion after local state is safe; never hold it across UI or network work. | Positive same-root evidence restores the session; positive changed authority creates a provisional successor; every other outcome is root-continuity-unavailable. No result proves deletion automatically. |
| `NSUbiquityIdentityDidChangeNotification` | Mark provider authority unknown and invalidate authority-scoped publication without persisting or logging the identity token. | Rediscover positive authority. Editing continues when rooted identity and local WAL durability remain valid; a positive authority change takes the provisional-successor path. |

Final resource teardown follows the checkpoint/WAL close flow below. Mark the session closing, cancel the vnode source and FSEvents stream, remove the presenter and identity observer, and drain owned operations through a barrier. The vnode cancellation handler acknowledges cancellation but must not close the shared root descriptor. Only after it and the other owned completions finish, and local WAL cleanup or evidence-preserving close is settled, may the root's single owner close the descriptor and release its lock. Cancel/retry retains that owner. An authority handoff instead transfers the continuously locked `NVRootedDirectory` owner, WAL, and pending obligations to the provisional successor, cancels only old observation, and promotes after namespace/authority revalidation; old-incarnation cleanup must not release transferred resources.

### `NotationController`

Retain the existing authoritative note collection and `pendingFileWrites`/`pendingJournalWrites` sets. Add:

- one structural generation incremented for note creation/removal, note-file rename, and format/serialization changes;
- one checkpoint-scoped dirty generation, initialized from the accepted checkpoint and advanced by any live-store change that can alter later `Notes & Settings` bytes;
- one main-thread edit-admission bitmask with independent lifecycle and WAL-durability reasons;
- immutable UUID/LSN snapshots for detached reads/writes;
- initialization from exact accepted checkpoint bytes and ID;
- one compact monotonic retired deterministic conflict identity set;
- one detached checkpoint-current complete-note-set/base-relative-deletion publication path that does not mutate live preferences.

"Admission" means that the one main-thread mutation check accepted a logical change, updated the live model, incremented its LSN/structural generation as applicable, inserted the note or UUID/LSN deletion record in the existing pending sets, and advanced checkpoint-scoped state. Deleting a reserved version-8 deterministic conflict note also inserts its UUID into the retired set. Admission does not archive, append, synchronize, or access the provider. At capture time the object's current UUID/LSN names the pending generation; no second generation registry is added. Normal WAL-record capture and note-file export remain coalesced; explicit durability boundaries force immediate asynchronous capture/barrier. A completion may clear membership only if the still-pending live UUID/LSN equals its captured generation.

### `NVRootedDirectory` and `NotationDirectoryManager`

Keep descriptor-relative and path-independent operations. Add a private acquisition helper that applies `flock(LOCK_EX | LOCK_NB)` to the existing validated read-only, close-on-exec directory descriptor; do not open another descriptor or expose a raw ownership handle to callers. Root-session retention keeps its `NVRootedDirectory` owner alive. Catalog scans may retain their existing independent `openat(fd, ".", ...)` descriptors, but no scan, vnode handler, URL/bookmark refresh, or controller replacement closes/unlocks the owning descriptor. A same-root successor receives that owner, not a pathname to reopen. Do not create `.nv-root.lock` or add a WAL-lock fallback.

Extend the rooted catalog to return one immutable shallow snapshot with:

- current direct-child name, regular-file status, stable identity when available, and cheap revision metadata;
- exact checkpoint/legacy-WAL/residue status in a separate artifact projection; no lock artifact;
- no content reads and no Spotlight dependency.

Retain the existing expected-byte note-file compare-and-swap and `NVMergedText` behavior. Move provider-facing work to the root-session queue without duplicating the pending-write registry. Use the Foundation safe-replacement backend only through the migration plan's gates.

Refactor the existing private `NVDirectoryTransaction` rather than introduce another reconciliation engine. A private immutable current-visible input copies the two catalogs, selected file snapshots, root/session and dirty/structural generations, and affected live-note UUID/LSN/name/base values. One deterministic private decision function consumes only those values and returns the existing transaction's prepared updates, additions, conflict notes, logical deletions, identity updates, and expected publication fences. The main thread maps UUIDs back to still-matching live notes, constructs or updates `NoteObject`/pending `DeletedNoteObject` records, and uses the existing all-or-nothing `_commitDirectoryTransaction:` path. The provider phase never stores a live note as a transaction key or constructs a note object.

Filesystem identity is optional equality evidence, not durable note identity. Use a nonzero `(volume UUID, document ID)` only when both sides' volume UUIDs match, then a nonzero file ID only within the active root session. Each identifier must occur exactly once on both sides before it may associate candidates. Generation count is revision/invalidation metadata, never identity. Do not assume any of these values survives provider eviction, rematerialization, replacement, or authority change; absence, change, or ambiguity falls through to unambiguous filename/content matching and finally conservative import/preservation.

Do not write NV UUID xattrs or sidecars. An ordinary UUID may arrive from another client only inside a complete accepted checkpoint. A file not associated with an already-live note by the supported current-visible tiers receives a fresh random version-4 UUID; its name, content, or foreign metadata never reintroduces an absent UUID.

Keep note-file migration similarly small: add a private immutable `NVNoteFileWriteIntent`/result pair in `NotationDirectoryManager.m`. The intent copies root-session incarnation, structural generation, note UUID/LSN, desired and prior names, encoded bytes, format/encoding, labels/tags, dates, expected snapshot, and trustworthy merge base. The provider lane performs the existing compare-and-swap/merge/write and returns an immutable result; it never retains or dereferences a live `NoteObject`. Main-thread publication verifies the captured fences before updating observed physical state or clearing the exact pending generation.

Reuse the existing UUID/LSN `DeletedNoteObject` only as the pending/WAL removal record for every intentional logical deletion, even when `syncServicesMD` is empty. Modern code neither copies nor consults service metadata when deciding deletion retention; preserve its keyed/non-keyed field only for legacy decoding. Add no filename, digest, filesystem/provider identity, or path fields. Replace `_purgeAlreadyDistributedDeletedNotes` with exact checkpoint-coverage cleanup: a verified complete checkpoint omits an ordinarily deleted UUID, then its pending removal record disappears with the covered WAL instead of entering the next checkpoint.

The user's delete path separately captures the represented file's root-session incarnation, note UUID/LSN, associated current URL/name, and exact accepted or installed snapshot. It removes that file only after coordinated revalidation; a mismatch preserves/imports the visible state. No later deletion record or checkpoint omission can remove a current file. A later current file is always preserved/imported under a fresh UUID rather than removed because its name or contents resemble a deleted note.

Reserve RFC 9562 UUID version 8 for the two deterministic conflict-note algorithms; ordinary note creation/import continues to use random version 4. `NotationController` owns a monotonic `retiredDeterministicConflictIDs` set. Deleting a version-8 note admits the same UUID/LSN WAL removal and adds its UUID to that set. Every valid positively associated modern WAL projects a version-8 `DeletedNoteObject` into the set regardless of base relation; exact-base recovery may additionally apply logical deletion, while base-mismatch recovery applies only the additive retirement. A live exact-body deterministic candidate remains reusable; an absent UUID in the retired set is occupied forever, while an absent nonretired candidate is unused. The set never applies to ordinary UUIDs and never authorizes a file deletion.

`FrozenNotation.retiredDeterministicConflictIDsV1` is optional keyed-archive `NSData`: concatenate the unique raw 16-byte UUIDs in unsigned-byte lexicographic order. Decode only a length divisible by 16 with strictly increasing, RFC-variant version-8 entries; reject the checkpoint on malformed input. Epoch 4 ignores the unknown key. Modern freezing passes an empty legacy `deletedNoteSet`, while modern decode accepts legacy `DeletedNoteObject` values only to normalize their UUIDs to note absence. Do not carry their `syncServicesMD` into new removal records or use it as acknowledgement evidence.

Set insertion is idempotent. The encoded payload grows by exactly 16 bytes for each distinct deleted deterministic conflict-note identity before archive overhead; ordinary deletions add nothing. Keep the set monotonic and add no compaction/acknowledgement protocol in this implementation. A later format may add garbage collection only with a new synchronization proof that cannot permit deterministic recreation.

Once an ordinary deletion is covered by checkpoint omission, do not retain a UUID denial record. A later complete checkpoint record that is not a base-relative deletion, or a later unmatched visible file, is possible user work and must be preserved rather than filtered through deletion history. The unmatched file receives a fresh random version-4 UUID.

### `WALController` and `StartupRecovery`

Use Foundation's user-domain `NSApplicationSupportDirectory`, appending the exact components `Notational Velocity/Recovery Journals`. Create that directory with mode `0700` where supported. Modern WALs are `Interim Note-Changes.<uppercase UUID>` mode `0600` files. Apply the same documented local backup-exclusion metadata already used for sensitive Application Support scratch storage; failure to set unsupported advisory metadata does not substitute for permissions or durability checks.

`WALController` owns:

- version-2 header encoding/validation;
- exclusive random creation with a fresh never-reused ID for every attempt, header barrier, and Recovery Journals directory synchronization before append publication; a collided or failed ID is burned;
- the existing record framing/CRC reader corrected to stop at the first invalid record;
- immutable record submission, ordered append, outbox draining, and barrier synchronization;
- close/delete plus Application Support directory synchronization.

Version 2 changes the file location and header only. Record bodies remain the existing keyed `NoteObject`/`DeletedNoteObject` archives, shared zlib stream, per-record encryption, and framing/checksum format; new removal records carry UUID/LSN with empty ignored legacy service metadata. Centralize replay projection in one helper. For an ordinary UUID, it applies logical deletion only on exact-base replay. For a reserved version-8 UUID, it always unions retirement after structural validation and positive root association; exact-base replay may additionally apply logical deletion, while base-mismatch replay must not remove or suppress a note or file. Preferences, selection, and other database-level metadata do not otherwise become WAL records. The plaintext header contains only journal ID, exact checkpoint-base identity, and root bookmark—never note title, body, or labels. It has no mutable state and is never rewritten after append begins. A stale bookmark can identify the root when Foundation still resolves it; the next session's WAL receives refreshed data.

Normal typing only changes the pending sets. At the existing coalescing boundary, the main thread captures the newest immutable archive bytes for each pending UUID/LSN and submits them in order to the durability queue; the existing idle file-write and 15-second maximum/outbox behavior remains. Resolver actions, external-editor handoff, lifecycle quiescing, and any explicit durability barrier bypass the delay and request immediate asynchronous capture plus barrier synchronization. A pending-journal entry clears only when that exact submitted UUID/LSN has left the short-write outbox, its barrier succeeds, and the live pending entry still names that generation. A newer edit remains pending. If failure arrives during an AppKit mutation callback, admit that callback once, then select the durability gate and urgently submit every pending generation.

Startup scans all filenames of the exact modern shape plus the selected root's legacy exact-name WAL, validates modern headers before resolving bookmarks, and compares resolved directory identity with the selected root. Unrelated, unavailable, or malformed files are preserved. Every positively matching file must be recovered or proven represented before editing. Preserve record order within each WAL but infer no order between the legacy and modern WALs; “legacy before fresh host-local WAL” describes discovery/migration, not cross-WAL replay precedence. Build one detached recovery result and checkpoint it once.

There are no current-host preference helpers, active/retained claims, coverage advancement, provider coordination for WAL files, or remote-writer classification.

### `SyncSessionController` and `AppController`

Keep the existing synchronization status, uncommitted-change waiting, and retry/override UI. Upload status is presentation only; it does not authorize local WAL cleanup or provider-version resolution.

`AppController` owns startup/rebuild/recovery sheets, the **Conflicting Versions Available** badge and editor/resolver view swap, root-unavailable choices, and the single monotonic quit/folder-switch state. It does not receive raw provider identifiers or WAL contents.

## Startup flow

1. Off-main, open and validate the selected root through `NVRootedDirectory`, then apply `flock(LOCK_EX | LOCK_NB)` to that already-open directory descriptor before registering observers, discovering/associating/recovering any WAL, or permitting mutation. Lock contention, unsupported directory locking, or any other failure leaves the startup session unattached and offers Retry, choose another directory, or quit; neither **Work Offline** nor fallback locking admits a writer. The nonblocking lock does not imply a bounded provider-backed directory open. Use existing asynchronous startup ownership/cancellation rather than a main-thread wait.
2. Discover positive provider authority asynchronously. Failure or ambiguity leaves authority unclassified and grants no provider-specific or ordinary-local shortcut, but does not block local WAL durability.
3. Check/materialize/read the canonical checkpoint through coordinated access. Preserve its exact checkpoint-current witness: accepted bytes, the existing `NVFileObservation`, and the current local `NSFileVersion.persistentIdentifier` when available, plus the decoded checkpoint ID. The witness is valid only for that root session.
4. Scan the local Recovery Journals directory and the selected root's legacy exact-name WAL. Validate every candidate before associating it with the root.
5. Replay an exact-base valid prefix. For base mismatch, preserve differing nondeletion states as deterministic conflict notes and union reserved version-8 retirement assertions, but never apply their deletion meaning or restore settings. A WAL is cleanup-only only when the accepted checkpoint represents every valid note/removal result and contains every version-8 retirement asserted by it.
6. For several matching WALs, preserve each WAL's internal order and infer no cross-WAL order. Build one detached recovery result, admit every derived note/removal/automatic-preservation/version-8-retirement result through the ordinary pending machinery, settle its applicable WAL and separate-file obligations, and install one exactly verified checkpoint before deleting any required member. This also applies after a crash interrupts checkpoint-current reconciliation: accepting the then-current checkpoint does not waive settlement of work reconstructed with the surviving WAL, and settlement captured for an older current checkpoint is not reusable after a further replacement. When step 3 accepted an existing checkpoint, its exact retained bytes and available local version are the recovery install's expected predecessor; only the already specified new-collection/rebuild paths may use expected absence.
7. Delete settled WALs locally and synchronize the Recovery Journals directory. On any failure, preserve evidence and do not publish editing.
8. Exclusively create and synchronize one fresh host-local WAL, then publish the editable store. Begin routine current-visible reconciliation in the background.

`AppController` owns this asynchronous state machine and its unattached root session until step 8 transfers the accepted session, including its continuously locked rooted-directory owner, to `NotationController`. It receives immutable checkpoint bytes from the provider lane and never causes the controller to reopen the checkpoint or root path. No correctness deadline exists: status changes and callbacks are wakeups, cancellation waits for accessor/completion ownership to return, and elapsed time publishes no partial or read-only store.

### Startup outcome table

| Established checkpoint/WAL evidence | Required behavior and choices |
| --- | --- |
| Root open/validation or directory-descriptor lock acquisition fails, including contention or unsupported locking | Stay unattached; do not discover/recover WALs, initialize the collection, or admit editing. Offer Retry, another directory, or quit. No lock-file/WAL fallback and no Work Offline bypass. |
| Provider-current, materialized, exact readable and decodable checkpoint; every matching WAL settled | Accept those exact bytes and continue through fresh-WAL creation. A note catalog is not a prerequisite for showing the live store. |
| Stale, unmaterialized, downloading, or otherwise not yet exact-current checkpoint | Request exact-item materialization/update, show app-owned progress when Apple supplies meaningful progress, and wait for a coordinated exact read. Retry, quit, and choose another directory remain available. |
| Materialization/update fails, but complete local checkpoint bytes and every matching modern/legacy WAL remain readable and recoverable | Enable explicit **Work Offline**. Preserve visible offline status while current-visible reconciliation catches up; do not create a separate read-only mode. |
| Materialization/update fails and the complete local checkpoint/WAL condition is not met | Disable **Work Offline**; retain Retry, quit, and choose another directory. Preserve every local recovery artifact. |
| Checkpoint absent in a directory exclusively created by this new-collection operation | Create the initial empty checkpoint silently through an expected-absence `NVCheckpointTransaction`, verify it, then continue. “Created by this operation” is transient and never persisted. |
| Checkpoint absent in any preexisting selected directory, including one that appears empty | Do not initialize implicitly. Offer **Create a New Notes Collection Here** only as an explicit action whose transaction revalidates expected absence. Offer rebuild separately when readable note files exist. |
| No acceptable checkpoint can produce a store, but a complete stable current-visible note snapshot is available | Offer **Rebuild from Note Files** using the detached rules below. Preserve rejected checkpoint/WAL evidence until an explicit disposition authorizes otherwise. |
| A WAL has a torn, corrupt, undecodable, or semantically invalid suffix or otherwise uncertain evidence | Stop at the valid prefix, preserve the artifact, create no fresh WAL, and offer Retry, **Save Current Collection As…** from the recoverable state, or explicit abandonment of that evidence. |
| Rebuild's expected-absence/exact-predecessor checkpoint install returns current-changed, or its catalog/input changes | Publish nothing, discard the detached candidate, and restart checkpoint/root discovery. The root-closing checkpoint-current merge is not available to rebuild. |

If the checkpoint cannot produce a store, **Rebuild from Note Files** uses the same current-visible double-catalog fence as routine reconciliation. It enumerates current nonhidden direct-child regular files after removing the exact artifact set, never Apple history. Seed one operation-local decoder map with plain text (`txt`, `text`, `utf8`, `taskpaper`), RTF (`rtf`), and HTML (`html`, `htm`); group every other extension for one explicit Plain Text/RTF/HTML decoder or Ignore choice and never sniff bytes. Unresolved decoder choice, unreadable input, cancellation, or a changed fence publishes nothing.

Construct the store detached with safe non-format defaults and no inferred deletions or recovered settings. A first-class provider-managed target converts every selected note through the existing plaintext writer and formatting/attachment-loss disclosure before checkpoint installation. Outside that contract, uniform recognized input retains its format; mixed recognized input requires an explicit target format and the same detached conversion. Install one expected-absence or exact-predecessor checkpoint and verify it before step 8.

## Current-visible reconciliation

Maintain one note dirty-generation high-water mark and one independent artifact-status generation. A callback advances the relevant generation and schedules one coalesced provider-queue transaction. Retry delays remain `0.1`, `0.5`, `2`, `10`, and `30` seconds, reset after visible progress; delay never becomes correctness evidence.

For one transaction:

1. Capture the active root-session incarnation, structural generation, serviced note generation, and affected UUID/LSN values.
2. Obtain a complete coordinated shallow note catalog. Form the authoritative candidate set from its current nonartifact children, identities/names retained by the live model and last accepted catalog, and direct-child note URLs retained from presenter move callbacks. Exclude the checkpoint, legacy WAL, hidden replacement residue, directories, and unrelated hidden files. There is no lock-file child to exclude. The root session owns the last accepted catalog and callback candidates until a later complete transaction supersedes or consumes them.
3. Associate candidates first by unique volume-qualified document ID, then by unique session-local file ID, and only then by existing unambiguous filename/content fallback. Treat generation count as revision metadata. Paths and timestamps alone are insufficient, and no filesystem identifier is required to survive eviction, rematerialization, replacement, or a root-session boundary. A callback URL does not establish identity by itself.
4. Read only new, changed, unmatched, or merge-required current files through coordinated access. Use batch preparation when AV-04 passes; otherwise use serial per-URL coordination.
5. Apply the existing current-file decision matrix in a detached candidate: fast-forward, local win, safe merge, conflict-note preservation, rename combination/race, logical deletion with a pending UUID/LSN removal record, or unmatched import. Routine conflict notes use fresh ordinary version-4 UUIDs. Do not consult checkpoint-current/WAL automatic-preservation candidates or the retired deterministic set to suppress a required conflict, including the still-local edited/renamed state in a current-file deletion race. Do not overwrite such a candidate either; these are separate identity domains.
6. Obtain a second complete current catalog and compare it with the first plus the selected immutable current snapshots.
7. Reenter the main thread and publish atomically only if the root session, structural generation, note UUID/LSN inputs, and serviced dirty generation still match. Otherwise retain dirty and retry. An ordinary conflict note or write-recovery artifact already made durable is additive user data and may remain; never roll it back merely because a later fence failed.

The deletion row preserves a changed/renamed state only when that state still differs from the last accepted current-file snapshot available to the transaction. Once the edit itself is the accepted current-file snapshot, a later provider deletion with no Apple-reported unresolved member is indistinguishable from an intentional deletion after that edit and is accepted. Do not search history or manufacture a conflict note. The checkpoint-current path can still preserve the edit when two complete checkpoint branches disclose it.

Routine code does not call historical/nonlocal enumeration, persist `NSFileVersion.persistentIdentifier`, or create resolution eligibility. `currentVersionOfItemAtURL:` remains available only as supplemental evidence in the existing-file/checkpoint witness; it is not treated as a content-generation counter. The mandatory same-accessor `NVFileObservation` supplies the host-local replacement/revision fields.

The last exact accepted note-file snapshot remains the preferred three-way merge base. `captureFileMergeBaseIfNecessary` may seed a plaintext base from the accepted checkpoint only for a represented note whose exact separate-file obligation was settled before that checkpoint was serialized. A later successful reconciliation/write replaces it with the exact accepted file snapshot. Without that boundary, preserve the alternate state instead of manufacturing a base.

## Checkpoint-current note reconciliation

`NVCheckpointTransaction` returns `NVCheckpointInstallCurrentChanged` without invoking replacement and, when possible, includes one exact coordinated checkpoint-current witness: complete bytes, `NVFileObservation`, and the available current local version identity. Treat missing, changing, unreadable, or invalid returned evidence as a no-write close failure.

For one valid result:

1. Retain the exact accepted predecessor bytes used by the failed attempt, the frozen complete live note set and retired-identity set, and the captured exact complete current bytes as immutable inputs. Failure to decode any complete input makes this a no-write close failure.
2. Decode the current checkpoint's complete note set and `retiredDeterministicConflictIDsV1`. Do not import its `NotationPrefs`, selection/UI state, or other database-level metadata. Normalize any decoded legacy `deletedNoteSet` entries to absence and do not serialize them forward.
3. Compute `mergedRetired = liveRetired ∪ capturedRetired` before allocating or reusing any deterministic conflict identity. Because membership is permanent, no branch may remove an entry.
4. Associate records by note UUID. For UUID `u` and branch `X`, classify deletion only when `u` exists in the accepted predecessor and is absent from complete `X`. Absence without predecessor membership is not a deletion. Collapse equality and one-sided changes; use `NVMergedText` only when the predecessor is a trustworthy record base.
5. For a deletion against an unchanged note, omit the source UUID. For a deletion/edit or deletion/rename race relative to the same accepted predecessor, omit the source UUID and preserve the edited state as an ordinary note through the automatic conflict-preservation identity, consulting `mergedRetired`. Once an edited state is itself the accepted predecessor, a newer complete checkpoint's base-relative omission is a later deletion rather than that race and may remove the last current-visible copy before the note-file view catches up. For unsafe concurrent nondeletion changes, keep the live note and preserve the current-checkpoint state through that same identity. Repeated processing reuses an exact live candidate; a changed candidate or retired deterministic UUID is never overwritten or automatically recreated, and any other identity inconsistency fails closed.
6. Publish the detached transaction on the main thread through the existing non-undoable synchronization path. Publish `mergedRetired` as checkpoint-scoped state. Insert every changed/imported note and UUID/LSN deletion result into the existing pending WAL and separate-file sets. For every UUID in `mergedRetired`, allocate a fresh local LSN and insert one `DeletedNoteObject` archive into the pending WAL set as a retirement assertion; do not schedule note-file deletion merely because this record exists. Reassert the whole union because the accepted predecessor is no longer current and either checkpoint branch may omit identities known by the other. Do not add a coverage index merely to suppress these exceptional duplicate, idempotent records.
7. Barrier-synchronize all new WAL note/removal/retirement work, finish current-visible reconciliation/file settlement, serialize the resulting complete live note set without general tombstones and with the compact retired set, and create a fresh single-use checkpoint transaction whose expected current is exactly the captured bytes/version identity. If a second current change prevents installation, the retirement assertions remain recovery evidence and project the complete union into the retired set even though their WAL is now base-mismatched.

Perform at most one automatic checkpoint-current merge and retry in one root-closing operation. If the current checkpoint changes again, leave it untouched and return to the close UI. A later user Retry begins a fresh operation with fresh exact evidence; it never blindly rebases an already serialized checkpoint.

Base-mismatched local-WAL nondeletion salvage uses that same automatic conflict-preservation identity and candidate-integrity rule. Resolver recovery keys remain a separate identity domain with their existing explicit-action slot semantics.

## Embedded unresolved-version resolver

Add an alert badge to the selected note's editor chrome and one `ConflictResolverView` as a sibling of `LinkingEditor` within the existing editor split-view subview, following [the conflict-resolver layout](conflict_resolver.pdf). Keep `LinkingEditor`, its text storage, undo manager, selection, and scroll position allocated while it is hidden; swapping views must not reconstruct editor state. `ConflictResolverView` owns a separate noneditable `NSTextView`, or another text-presentation control with equivalent fidelity, scrolling, selection, copy, and accessibility behavior. It never shares or overrides `LinkingEditor`'s text storage, undo manager, delegates, or persistence callbacks. Never show the resolver automatically. Clicking the badge swaps in `ConflictResolverView`; its close **×** is always enabled and swaps `LinkingEditor` back immediately. The resolver is nonmodal, so the note list and search remain usable. Do not add separate **Edit Current**, **Done**, or **Retry** controls. Dismissing the resolver does not cancel an admitted disposition, clear conflict evidence, or release its root-session-owned operation.

Probe the unresolved-conflict resource value only as advisory status. Schedule an event-driven probe when selection changes to a note with an installed visible file, when a successful reconciliation changes that selected file's current snapshot, and when its presenter reports version gain/loss/resolution or applicable item change. Do not poll periodically. When the advisory value is positive—or a presenter version callback independently supplies the wakeup—coordinate the current visible file and call only `unresolvedConflictVersionsOfItemAtURL:`. A nil/error result remains ambiguous; a nonempty result shows/retains the badge, and only a fresh empty result clears it. Clicking the badge presents or re-presents the resolver, attaches it to the current root-session operation, and automatically starts one new bounded pass for every parked operation on that note. An operation already running is only reattached, not submitted again:

1. Capture an operation object containing the selected note UUID/LSN, structural generation, title, labels, separate-file format, root/session incarnation, source URL identity, the returned unresolved `NSFileVersion` members, and a frozen copy of the authoritative in-memory current body. Include admitted unsaved edits; do not reread the current file to construct **Current**. The root session/provider queue, not `ConflictResolverView`, owns any running operation so it can finish after the resolver is dismissed.
2. Populate the popup with **Current** followed by the captured unresolved members. Selecting **Current** immediately shows its frozen read-only body. Selecting another member asynchronously coordinates and reads that member's supplied version URL, decodes it using the captured source-note format rather than the provider version URL's apparent extension, then publishes the preview only if the operation and selected member are still current. Never block the main thread or substitute the current file URL.
3. Store preview, disposition, waiting, and error state in the transient resolver-member model keyed by the captured member; `NSMenuItem`/`NSPopUpButton` only render and select that model. Show the selected member's state beside the shared preview/actions. Disable that selected member's disposition buttons while its preview is unavailable or its action is in flight; keep the **×** and other item selection/previews available. Disable **Save as new note** for **Current**. An exhausted item displays **Retry when reopened** without a button. A nil query, unreadable member, changed root/session, or stale completion is retryable ambiguity and cannot authorize resolution.

Serialize same-source disposition work on the existing provider lane. Another item may be previewed while one operation runs; a later disposition begins from a fresh unresolved snapshot after earlier same-source work reaches a stable stage. This avoids a second scheduler or persistent operation registry.

**Use this version** captures the previewed body and revalidates the operation's note UUID/LSN, structural generation, and root/session incarnation on the main thread. A mismatch applies nothing and refreshes the resolver. Otherwise, for a conflict member call the original note's existing `setContentString:`/ordinary mutation path; for **Current**, make no body mutation. Preserve the original UUID, filename, title, labels, and other database metadata. Wait for that exact note generation's WAL barrier and exact separate-file installation. Then use a short `NSFileCoordinatorWritingForMerging` accessor on the source, revalidate the root/session and exact installed current-note generation, and set `resolved = YES` on every still-applicable member of the captured snapshot. If the ordinary file-write implementation can run the resolution continuation inside the same accessor after verified installation, reuse that accessor; otherwise the second accessor must repeat exact-current validation. Do not include versions first observed after the snapshot.

**Save as new note** computes one stable recovery key from a fixed versioned domain separator, the source note UUID bytes, and the previewed body in NV's canonical NFC-normalized UTF-8 encoding. The v1 byte input is `"NV unresolved recovery key\0v1\0"`, the 16 source-UUID bytes, the body length as unsigned 64-bit big-endian, and the body bytes; SHA-256 of that input is the 32-byte recovery key. Do not include title, labels, extension, filename, provider identifier, or collision suffix. These are mutable presentation/output attributes and would make a retry choose a different identity.

Derive each candidate note UUID from SHA-256 of `"NV unresolved recovery slot\0v1\0"`, the recovery key, and the slot ordinal as unsigned 64-bit big-endian; use the leading 16 bytes after setting RFC 9562 variant/version-8 bits. Slot zero is the ordinary path. Pin cross-language test vectors before implementation. Scan slots from zero and:

- reuse the first live candidate whose canonical body still equals the preview, settling its current WAL/file obligations if necessary;
- skip a live candidate whose body has changed and skip any UUID in the retired deterministic conflict identity set; never overwrite or resurrect either;
- otherwise create the first unused slot as an ordinary collision-adjusted `Title (conflict).ext` note using the operation's captured title/labels and previewed body.

This makes a repeated operation reuse the same note across a crash, filename collision, rename, duplicate click, silent resolution failure, or duplicate Apple versions with equivalent decoded bodies. Including the source UUID prevents equal bodies from different source notes from collapsing. A later explicit save allocates another deterministic slot only when the earlier recovery note was changed or deleted before resolution, because that earlier note no longer preserves the selected body.

Insert a new candidate through the existing creation, pending-WAL, and pending-file paths. A UUID match alone is insufficient: immediately before provider resolution, require a live note with the expected canonical body, the exact WAL-durable generation, and exact current separate-file installation. Then coordinate the source with `NSFileCoordinatorWritingForMerging`, revalidate the operation/root and member applicability, and set `resolved = YES` only on the selected member. Once a fresh query confirms resolution, later editing or deletion of the ordinary recovery note has no resolver consequence.

After either disposition, freshly call `unresolvedConflictVersionsOfItemAtURL:` rather than trusting the setter, menu, or completion callback. The `resolved` property has no error result and cannot be changed back to `NO`, so the fresh result is the sole success evidence. If members remain, replace the operation snapshot, keep the badge, and rebuild the menu with **Current** selected when the resolver is presented; if the result is empty, clear the badge and restore `LinkingEditor` if necessary. A nil/error result keeps a retryable conflict state. A partially successful sequence remains safe because the fresh result discloses the remaining members.

### Partial failure and resolver-view behavior

One disposition remains pending through four ordered stages: ordinary mutation/WAL, exact separate-file installation, coordinated `resolved = YES`, and fresh unresolved query. Its operation and status are attached to the transient resolver-member model, not an AppKit menu item or the resolver view's lifetime. The close **×** remains enabled at every stage; dismissing the resolver detaches its observations while the root-session operation continues in the background. The resolver never advances a stage from elapsed time or a callback and never claims success merely because the note was created.

| Last established stage | Required state and retry behavior | Per-version/resolver behavior |
| --- | --- | --- |
| Mutation was not admitted | No note state is retained and no version is resolved. | Keep the same preview selected, show the error on that item, and re-enable its action. The resolver may be dismissed. |
| Mutation was admitted but its WAL barrier failed or is unknown | Keep the exact pending generation in the existing WAL outbox; resolve nothing. Retry resumes that generation rather than creating another note. A crash before durability may lose the mutation, but the provider member remains unresolved. | Show **Saving conflict note…** or **Saving chosen version…** on that item and disable only its actions. The resolver may be dismissed; the separate global WAL-durability suspension still blocks edits and exposes its existing application-level Retry/Save-As choices outside the resolver. |
| WAL is durable but exact separate-file installation failed or is ambiguous | Preserve the ordinary note/current-note mutation and its existing file obligation; resolve nothing. Retry exact installation/read-back for that same generation. For **Save as new note**, find it by deterministic slot rather than allocate another. | Show **Waiting to write note file…** on that item while its background attempt runs. The resolver may be dismissed, and another item may be previewed. A definitive failure changes that item to **Retry when reopened**; it does not add a resolver Retry button or offer another copy action for the same pending generation. |
| WAL and file are exact, but coordination, generation/member revalidation, or `resolved = YES` did not take effect | Keep the installed note state; resolve nothing else. A fresh query determines whether the selected member remains. If it remains, a later explicit disposition reuses the exact matching recovery slot; a changed or retired slot is skipped without overwrite and a new explicit save uses the next slot. | Rebuild from the fresh result and show **Saved locally; conflict still unresolved** on the affected item. Its actions become available; the resolver may remain dismissed. |
| `resolved = YES` ran, but the fresh query is nil, errors, or is interrupted | Treat the result as ambiguous. Do not repeat note creation or claim success. Retry only the fresh query through the current bounded attempt; after relaunch, ordinary conflict discovery starts a new operation with no persisted provider-version intent. | Show **Checking conflict status…** on the affected item. Other items and the **×** remain usable. If the attempt exhausts, change only that item to **Retry when reopened**. |
| Fresh query excludes the selected saved member but returns others | The selected **Save as new note** disposition succeeded; remaining members form a new snapshot. Partial **Use this version** resolution is likewise represented only by the returned remainder. | Remove resolved members, clear their transient state, retain the badge, and select **Current** if the resolver is presented. |
| Fresh query is empty | The user disposition is confirmed complete for every currently reported conflict. | Clear the alert badge and restore `LinkingEditor` if `ConflictResolverView` is presented. |

For conflict-disposition provider work, one automatic attempt consumes at most one pass through the existing `0.1`, `0.5`, `2`, `10`, and `30` second delays. Dismissing the resolver does not stop that pass. Exhaustion performs no more timed work. Each transition from `LinkingEditor` to `ConflictResolverView` automatically starts a fresh pass for all parked items on that note and coalesces with any already-running attempt. There is no retry gesture or control while the resolver remains presented. This bounds invisible activity without treating elapsed time as resolution evidence.

If a recovery note is edited or deleted while its disposition is pending, invalidate that candidate's install evidence immediately. Deletion admits its UUID/LSN removal record and retires the candidate UUID. Do not overwrite or recreate it, or resolve from its UUID. The current operation returns to the unresolved state; only a new explicit **Save as new note** action may select the next nonretired deterministic slot. Switching to another note does not convert a pending or ambiguous action into success; returning to the source first performs a fresh unresolved query.

If the resolver is dismissed during **Use this version**, ordinary source-note editing resumes unless the independent WAL safety gate is active. Any newer source LSN/generation makes the pending exact-generation revalidation fail, so the operation leaves the provider members unresolved and never overwrites the newer edit. If coordinated revalidation completed first, the later edit is simply a newer ordinary mutation. **Save as new note** can continue independently of later source-body edits, but still requires the captured source/member/root applicability and exact unchanged recovery-note evidence.

Do not persist a recovery ledger or provider identifier. Do not wait for upload. Never call `removeOtherVersionsOfItemAtURL:`, an individual version-removal API, or `replaceItemAtURL:options:error:` on an `NSFileVersion`; resolution does not remove Apple's retained history. Do not add **Merge** initially. A future reviewed merge may reuse the ordinary mutation path only when a trustworthy base exists and receives the same snapshot-scoped resolution authority as **Use this version**.

`Notes & Settings` conflicts are not inputs to this UI. Remove the old **Recover Notes** and **Discard** routes.

## Local edit and note-file write flow

1. The main-thread admission check accepts one logical mutation, updates the live note set, increments its note LSN/structural generation as applicable, and inserts the note or UUID/LSN deletion record in the existing pending sets. Deleting a reserved version-8 deterministic note also inserts its UUID in the retired set. It performs no archiving or I/O and adds no second generation registry.
2. At the normal coalescing boundary—or immediately for resolver, external-editor, lifecycle, or durability-suspension work—the main thread snapshots only the newest pending UUID/LSN state into immutable WAL bytes and `NVNoteFileWriteIntent` values.
3. Submit WAL bytes to the independent durability queue and file intents to the serial provider lane. Never make either queue wait for the other.
4. The WAL lane appends in order, drains its short-write outbox, and barrier-synchronizes when requested. The provider lane discards already-superseded intents, then performs the existing expected-byte compare-and-swap/merge/write through the rooted directory and Foundation backend selected by the migration gates.
5. Each lane returns an immutable result to the main thread. WAL success clears only the exact pending-journal UUID/LSN after its barrier; file success updates observed physical state and clears only the exact pending-file generation. A newer generation remains pending.
6. A file conflict schedules current-visible reconciliation; a failed fence or stale completion changes no live state. All note construction, merge-result publication, label attachment, search refresh, and selection updates stay on the main thread.

If append, outbox drain, or barrier synchronization fails, select the WAL-durability reason in the shared admission mask, urgently submit every pending record, and block later edits. Resume only after the Application Support WAL descriptor/header/root association and a barrier sync are revalidated.

### Existing mutation-path adaptations

- Route text/title/label edits, creation, deletion, rename, external-editor ingestion, and undo/redo through the one main-thread admission check before they change the model or increment an LSN. If undo or redo is blocked, reject it before asking `NSUndoManager` to transfer or invoke the stack entry, so both stacks remain unchanged.
- Treat fenced current-file, checkpoint-current, WAL-recovery, and resolver publication as non-undoable external synchronization. Reuse `applyPreparedFileStateFromNote:` and the existing non-undo-registering import path rather than registering user undo actions for provider state.
- Convert `makeNoteDurableForExternalEditing:` from a synchronous Boolean boundary to a completion-based exact-generation WAL barrier. `ExternalEditingSession` retains its scratch file and pending accepted bytes until that completion succeeds, then replaces/removes the scratch file. It never waits synchronously on the main or provider queue. Direct editing of an installed separate note file continues through current-visible reconciliation.
- Before quit, folder switching, Save As, or controlled storage conversion freezes a final model, reuse the existing external-editing suspension/final-read flow and wait for its model mutations and WAL barriers. Canceling that lifecycle action re-enables external editing only if no commit boundary was crossed.

No new mutation registry, undo subsystem, or external-edit scheduler is introduced.

## Checkpoint installation and quit

Keep one private, single-use `NVCheckpointTransaction`. Its immutable input contains serialized bytes, fresh checkpoint ID, the exact expected-current checkpoint witness (complete bytes, `NVFileObservation`, and current local version identity when available) or expected absence, settled pending obligations, and caller context. Its current-changed result may carry an immutable exact checkpoint-current witness; it never performs decoding or reconciliation itself.

Inside a short coordinated accessor, recheck expected evidence relative to the rooted directory and invoke the Foundation replacement backend. Afterward require the migration plan's applicable root-directory synchronization, exact byte read-back, decode, checkpoint ID, and local version checks. Return typed success only after that full `DUR-01` boundary; otherwise return current-changed/no-write, definite failure, or possible-install ambiguity.

Quit/folder switch:

1. Set lifecycle quiescing and drain already admitted main-thread mutations.
2. While the presenter remains registered, service through-generation callbacks and finish one stable current-visible barrier.
3. Drain pending note writes and synchronize the local WAL.
4. If the checkpoint-scoped dirty generation still equals its accepted-checkpoint baseline and the WAL is exactly header-only, close/delete it locally and skip checkpoint creation. Otherwise serialize once and invoke the checkpoint transaction.
5. On the first `NVCheckpointInstallCurrentChanged`, run the complete-note-set/base-relative-deletion reconciliation and retired-set union above, redrain all resulting obligations and the current-visible barrier, serialize again, and invoke one fresh transaction against the captured current checkpoint. A second mismatch or invalid current snapshot returns to Retry/override without writing.
6. After exact local verification, close/delete the WAL and synchronize the Recovery Journals directory.
7. Remove the presenter and observers, await vnode cancellation and all owned operation completions through the serial operation barrier, then close the owning root-directory descriptor to release its lock. Steps 1–6, including WAL unlink/directory-sync failure and Retry/Cancel UI, never release that lock early.

Provider upload status may remain pending in the existing quit UI, but it does not affect step 5. A pre-verification failure or ambiguous possible installation preserves the WAL. An explicit override closes the descriptor but leaves the local file for startup recovery. `applicationWillTerminate:` never performs another checkpoint write.

If root continuity is unavailable, do not run the old-root checkpoint steps above. Retry may first restore positive continuity. **Re-open from Disk** or quit explicitly ends the session by closing the unavailable WAL descriptor while preserving its file for later association. **Save Current Collection As…** may retire that WAL only after the independent destination's exact checkpoint and required files are verified. The root-unavailable and WAL-durability-suspension presentation both expose Retry, **Save Current Collection As…**, **Re-open from Disk**, and quit; neither becomes a persistent read-only mode.

Delete the macOS 26 pause/fail-on-conflict upload/resume branch, legacy upload-transition qualification, checkpoint resolution/journal coverage, active-to-retained fallback, retained backlog retry checkpoints, and provider-version cleanup.

## Root moves, unavailability, and transitions

A verified move of the same rooted directory updates the current root URL/bookmark and future WAL bookmark, rebuilds the FSEvents watch, and retains the session/structural generation when any available provider item/domain pair also remains equal. Candidate URLs come only from presenter, rooted descriptor, file-reference, or bookmark evidence; forward File Provider lookup validates a candidate but never locates one. The open WAL header is not rewritten.

Authority change fences the old session, transfers the already-locked rooted-directory owner/open local WAL/pending sets to a provisional successor without closing, unlocking, reopening, or duplicating them, reattaches observation, and promotes only after namespace/authority revalidation. It does not increment structural generation; the new root-session incarnation is the invalidation fence. Authority uncertainty alone freezes provider publication but does not block editing while local WAL durability remains healthy. A different directory recreated at the old pathname has an independent lock and is never an automatic successor. An unusable/revoked descriptor follows the existing positive-continuity and root/WAL-association gates, not a silent pathname reopen.

A vnode delete/revoke, deletion accommodation, missing path, stale bookmark, or failed provider lookup never proves deletion. When positive same-root continuity cannot be established, mark the session unavailable and freeze provider publication. Revalidation uses only existing rooted/candidate evidence and optional forward item/domain equality; there is no domain enumeration, reverse lookup, negative error taxonomy, saved-delete promotion, or automatic `confirmedGone` state.

Root unavailability blocks editing only when the root/WAL association cannot be positively validated; a healthy association and local WAL may continue accepting edits while only provider authority is uncertain. Retry reruns the positive checks. **Re-open from Disk** or quit explicitly ends the old session, closes but preserves its unavailable local WAL, and uses ordinary startup when reopening.

**Save Current Collection As…** freezes the live store, exclusively creates an unattached destination, and independently locks its directory descriptor before bootstrap or export. Retain the old root's locked owner until its covered-WAL cleanup or evidence-preserving close and teardown finish. Clone source settings into detached target preferences but never copy the source `keychainDatabaseIdentifier`. A remembered encrypted destination first obtains or reauthenticates the passphrase, creates a fresh add-only target Keychain item, burns and retries an identifier collision, reads the item back, and validates it against the target KDF/verifier; no target checkpoint may name it earlier. An unremembered or unencrypted target clears the identifier. Save As never updates or deletes the source item.

Install and verify a complete single-database bootstrap before optional separate-file export and final-format checkpoint installation. Before bootstrap verification, remove only residue/credentials proven exclusively owned and unreferenced; an ambiguous install retains them. After a verified bootstrap, a later failure leaves a complete detached destination for ordinary reopening/conversion retry. Create the target's fresh local WAL and publish the target controller only after the final accepted checkpoint. Then explicitly end the old session and close/delete its covered old WAL. No WAL is copied or transplanted between roots.

Controlled passphrase/encryption/storage-format changes retain the existing staged checkpoint and copy-on-write Keychain cutover. Entering provider mode first quiesces edits/external editing, settles current work, installs and verifies a complete old-contract checkpoint, and removes its covered old WAL through the local directory-durability boundary. Show the cleartext disclosure and, for RTF/HTML, the formatting/attachment-loss warning. Export all live notes through the existing plaintext writer, verify the same current catalog token before and after export, install and verify the unencrypted plaintext target checkpoint, and restart with a fresh local WAL. The complete old-contract checkpoint is the sole restart marker; retry is idempotent and no migration ledger is added.

Positive discovery that an active incompatible root has become provider-managed invokes that same blocking conversion, with convert/restart, choose another folder, or quit choices. The forward-provider matrix supplies only the positive authority fact; it neither performs conversion nor broadens negative-result inference.

A controlled same-root storage restart retains/transfers the locked rooted-directory owner across old-WAL cleanup, export/checkpoint work, and fresh-WAL/controller publication. It must not close/reopen the directory between controllers. A true process exit releases its lock; the next process follows ordinary acquisition and recovery.

## Diagnostics boundary

Do not add a diagnostics subsystem. New provider/recovery/storage leaves return typed results plus `NSError` and do not interpolate raw values into `NSLog`. One private root-session reporting function accepts only a closed operation/phase enum, item count, status enum, and error domain/code; its signature accepts no free-form message, URL, name, `localizedDescription`, `userInfo`, bookmark, provider identifier, account identity, WAL bytes, or note content. UI error presentation remains separate. Tests inject sensitive sentinel values and assert that none reach captured diagnostic output.

### Forward-provider/root evaluation matrix

Implement the `NVRootSession` disturbance decision as one pure function declared in `NVRootSession_Private.h` with closed input/output enums and copied opaque values. Production forward-lookup/root evidence and one table-driven deterministic test call that same function; do not add a provider protocol or alternate production implementation solely for mocks. Provider pairs are opaque complete `{ item, domain }` values; a partial pair is nonpositive. “Provider-managed without a pair” below requires separate current positive ubiquitous-item evidence; a failed forward lookup alone never creates or removes that classification. Every row also asserts that the operation/session generation is still current before its outcome is applied.

| Root-session state | Candidate rooted identity | Forward result at candidate | Expected result |
| --- | --- | --- | --- |
| Initial, unclassified without a stored pair | Not disturbed | Complete `P1` | Record positive provider-managed authority `P1`; do not create a new incarnation |
| Initial, unclassified without a stored pair | Not disturbed | Negative, error, timeout, cancellation, or partial pair | Remain unclassified; authorize no ordinary-local or provider-specific shortcut |
| Initial, provider-managed without a stored pair | Not disturbed | Negative, error, timeout, cancellation, or partial pair | Preserve only the independent positive provider-managed classification; derive no pair or other inference |
| Active, with or without independent provider evidence but no stored pair | Same rooted object | Complete `P1` | Retain the incarnation and record `P1`; no earlier contrary pair existed |
| Active, unclassified without a stored pair | Same rooted object | Negative, error, timeout, cancellation, or partial pair | Retain the positively rooted incarnation but keep authority unclassified; authorize no provider-specific shortcut |
| Active, provider-managed without a stored pair | Same rooted object | Negative, error, timeout, cancellation, or partial pair | Retain the positively rooted incarnation and only the independently established provider classification; derive no pair or other inference |
| Active with stored `P0` | Same rooted object | Complete `P0` | Retain the incarnation and restore/continue publication |
| Active with stored `P0` | Same rooted object | Complete `P1`, where `P1 != P0` | Fence the old incarnation and enter the provisional-successor path |
| Active with stored `P0` | Same rooted object | Negative, error, timeout, cancellation, or partial pair | Keep the descriptor, lock, and local WAL attached; enter root-continuity-unavailable and freeze provider publication without inferring deletion |
| Active or unavailable | Different rooted object | Any result, including a complete pair | Enter or remain root-continuity-unavailable; do not follow or retarget to the candidate |
| Active or unavailable | Missing, stale, revoked, or otherwise not positively comparable | Any result | Enter or remain root-continuity-unavailable; do not infer deletion or end the session |
| Unavailable with stored `P0` | Same rooted object | Complete `P0` | Restore the same incarnation |
| Unavailable with stored `P0` | Same rooted object | Complete `P1`, where `P1 != P0` | Enter the provisional-successor path |
| Any | Any | Completion belongs to a stale/canceled operation or superseded incarnation | Discard it without changing authority, availability, root URL, or publication eligibility |

Run the disturbance rows once for each permitted candidate provenance: presenter callback, rooted descriptor, file-reference URL, and resolved bookmark. Reject stored-path reconstruction, directory/path search, provider-domain enumeration, and reverse item lookup before evaluation even if their synthetic URL would otherwise match. Re-running **Retry** uses this same matrix and grants no additional inference.

Each nonpositive-result row must additionally assert: no ordinary-local classification, no deletion classification, no path retargeting, no automatic session termination, and no provider identifier persistence or diagnostics. A valid root/WAL association keeps editing available even when provider publication is frozen; an invalid association independently selects the edit-admission durability suspension.

Keep Apple behavior at the boundary: extend the live-provider harness only to forward-query the URL supplied by each permitted candidate mechanism, compare the complete pair before and after a same-root move, observe a genuinely different pair across a provider/authority fixture, and deliver positive, negative, delayed, and failed outcomes to the deterministic matrix. The live harness does not decide application state.

Run `build.sh` after each implementation slice and the applicable integration/TLA+ checks before merging behavior changes.
